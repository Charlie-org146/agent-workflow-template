# Operation

Milestone: https://github.com/jcl2018/agent-workflow-template/milestone/6

Review: **Unreviewed** <!-- kept merge-private-lane-import@45fb2810 -->

How to use: [How-to-use-Operation](How-to-use-Operation)

## Problem

- One session governs: it starts every ready goal in its own worker, passes my answers along, runs unattended and never builds.

## Requirements

### Functional

- OPS-1: **Reviewed 2026-11-19** The operation session governs, re-plans and cleans up <!-- reviewed 9afc870c -->
  - One command starts the operation session and drives the whole process the same way every time. It governs only: it never builds. [OPS-1]
  - Three layers. Top is the owner's only session: governance only, the only reader of the owner and the only publisher of the board and the Loop Board, every 5 minutes. A machine session (one per machine) assigns goals, schedules sessions and memory, runs auto, check-ins, dry-runs and merges, and reports up to top. A worker has one goal and one worktree and talks only to its machine session. [OPS-1]
  - A machine session governs every repo in its pod directly; there is no per-repo operation session. Several pods may run at once, independently. [OPS-13]
  - On start the operation session runs a self-check and lists what is missing, each with its fix. It re-creates its check-in timer before the timer expires, and warns before the app's limit on unanswered messages is reached. [OPS-23]
  - agent_command passes the tool list as one --allowedTools=<list> token; a check reports the two-token form, and applying the fix stays the owner's. [OPS-23]
  - At each check-in the operation session re-reads every goal's progress and re-plans to finish soonest: it merges goals that do the same thing, splits a goal that blocks others, and puts the critical path first. It never stops a running goal to re-plan, and every change is logged with its reason. [OPS-10]
  - A worker with no report for 30 minutes shows under Needs you. [OPS-8]
  - Each item under Needs you says what it holds up and whether it is on the critical path to the next release, and items are sorted with the one holding up the most goals first. [CHK-7]
  - When a goal merges, its worker session is given the next ready goal or archived, and its worktree and branch are removed. [OPS-6]
  - (v2.0 planned) A process finding the top or a machine session makes while scheduling, merging or deciding is filed by default, without asking, as an issue labelled ops-finding on the owning feature's Backlog milestone, linking the TOP-DECISION or record that found it. [OPS-1]
  - (v2.0 planned) A finding that repeats an open issue (the same normalised title, or the same IDs in the title) is refused, not filed twice; the check-in lists what was filed since the last check-in. [OPS-1]
  - (v2.0 planned) A safety-class finding is filed only with the owner's words. The delivery loop's own findings stay separate. [OPS-1]
- OPS-2: **Reviewed 2026-11-19** Live communication on a fixed protocol <!-- reviewed dbb71bf2 -->
  - A worker reports each change of step or status as it happens, and its result when it ends; the operation session sends a worker its answer or a follow-up. [OPS-2]
  - Background processes are used only when a session can't be started or reached, and the board says so. [OPS-2]
  - Messages and fields. STATUS (machine to top, on change and every 30 minutes) carries main per repo, PR numbers, running, parked and idle sessions with reasons, and worker lines; PR per goal; merges; needs-owner with the exact words to answer and a recommendation. ASK, OWNER-WORDS and PRIORITY go between top and machine; MERGE-REQUEST and MERGE-GO go machine to machine, copied to top. A worker never talks to top or to another machine. [OPS-2]
- OPS-16: **Reviewed 2026-11-19** Every ready goal starts within capacity limits <!-- reviewed 9218e38e -->
  - When goals are ready and slots, sessions and memory are free, every one starts in the same pass; budgets still hold. [OPS-16]
  - A ready goal waits while live goals, weekly plan usage or free memory are past their limits, and the check-in names the limit. [OPS-16]
  - Make every machine busy and be aggressive about time and token: a machine raises its own time and token budgets within the caps, and the caps are operation-top's to decide; raising a package limit still takes my own words (GRD-21). [OPS-16]
  - The operation session plans queued goals as a dependency graph and gives every goal whose dependencies are met its own worker session, in parallel. A goal waits only on goals it truly depends on; sharing files is not a reason to wait. [OPS-20]
  - The operation session keeps a pool of idle worker sessions, sized by one setting, and hands each ready goal one from the pool. When the pool runs low it asks me to fill it, at the desktop. When I've chosen app sessions, a goal never falls back to a background worker: it waits and says so. [OPS-12]
  - No goal or test lane starts while free memory is below one setting, 3 GB by default and stated here only. A machine may set its own value locally. A lane already running is never stopped. [GRD-12]

### Non-functional

None

## Non-goals

- The operation session never builds; workers do.
- It never merges unless auto_merge is on (OPS-7, OPS-15); the delivery loop merges and releases.
- Full auto never answers for me on destructive, money, security or owner-contradicting decisions.

## Success metrics

- Every ready goal gets its own worker session within one check-in, and no goal waits on a goal it doesn't depend on.
- With full auto on, a run needs me only for the safety-class decisions OPS-11 excludes.
