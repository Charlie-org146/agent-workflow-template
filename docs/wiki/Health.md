# Health

Milestone: https://github.com/jcl2018/agent-workflow-template/milestone/4

Review: **Unreviewed** <!-- kept fast-3min@d4d7dad03 -->

How to use: [How-to-use-Health](How-to-use-Health)

## Problem
- My rules, requirements and standards are spread across many pages and sometimes conflict, and I can't see where the repo falls short of its own PRDs.
- I want a reviewer that reads everything (every PRD page, the README, milestones, open issues, tests and code) and tells me per feature what conflicts, what's missing and what's slow, alongside fixed checks that give the same answer every time.
- I work feature first: its findings should read as one table naming each one's feature, and land as issues tagged with their group and their feature (or Other), previewed first, so I can triage them in one place later.


## Runbook

### health-round
- **Serves:** HLT-2, HLT-2, HLT-4, HLT-4, AUT-1, AUT-1, CHK-1.
- **Schedule:** on the owner's Mac only (AUT-1, AUT-3): the one launch agent `com.workflow-loop.schedule` runs `automation.py local tick` every 4 hours by default (`health_cron` in `.loop/config.json`; an every-N-hours or fixed-hours shape, `off` stops it). To run a round by hand use `python3 skills/workflow-health/scripts/automation.py local tick --repo PATH` (a hand run of one repo that is not due still runs). There is no health workflow in GitHub Actions: a leftover `.github/workflows/health.yml` is a WARN of the `scheduled` rule, remove it with `git rm`.
- **Steps:** `local tick` does the whole round in order, one command each, in a checkout of `origin/<base>` under the schedule home (the working tree is never touched): probe `gh auth status` and the API; Check (`health.py check`, every group the Mac can read); File (the same command with `file`); Judge (`health.py judge`, on the Mac's own `claude` login); Digest (`automation.py digest`); Mail (`mail.py send`). Start it with `automation.py local tick`, preview with `--dry-run`. Do not rebuild the round from separate commands: a hand digest with a token posts for real on the pinned issue.
- **Full run:** a full run reads the live repo and its live open issues, runs all twelve groups (performance, controls, Mine and hygiene read the Mac's own records and files, which only the Mac has), runs the full regression live for a private repo (`regression_runs` is `mac`) or takes the newest suite time for a public one, and ends with the real `HEALTH:` verdict line. It files every finding as one issue tagged with its group (and with `feature:<Page>` only when `feature_labels` is true, off by default), re-checks the open review issues against this run's findings, posts the digest comment and mails it. The judge is skipped, and the report says `JUDGE: skipped, ...`, only when `claude` is not logged in; the round is still a full run. The judge is not run on the runner: no health workflow runs in GitHub Actions and the runner holds no `ANTHROPIC_API_KEY` or `claude` login, so the judge runs only on the Mac, through `judge_command` in `.loop/config.json` when no session gives the answer. Each repo's tick is capped by `LOOP_TICK_MINUTES` and the whole tick by `LOOP_TICK_TOTAL_MINUTES`, within AUT-7's budget. The Adoption group also reads `.loop/matrix-runs.tsv` (the `matrix` rule): a cell of agent by machine that never ran is a WARN pending, one with no pass in 7 days is a WARN not proven, and a V1-required cell that ran and failed or went stale is a FAIL.
- **Output:** one digest comment on the pinned Automation digest issue, and one email of that same comment when `~/.workflow-loop/schedule/mail.env` (mode 0600, `DIGEST_TO=...` lines; `LOOP_MAIL_ENV` names another file, and Windows has no mode check) exists, through `digest_mail`. On a Windows PC (the always-on machine), `automation.py local register` writes the registry (no launch agent) and the PC's own scheduled task runs `local tick --scheduled`. The tick prints `SKILLS:`, `JUDGE:` and `REGRESSION:` lines and writes its log in the schedule home. The comment's Findings section is check's findings table (built by report.py, its issues read by issues.py) with each Issue cell from the table file printed after filing, read back from the saved report by automation.py.
- **Never:** never send a fixture, a sample or a test mail in place of the round's digest; never run `preview` or any dry run as the scheduled round; never skip a group to save time; never invent the verdict or the issue list; never fake a skipped judge or an off mail to make the round look complete; never push, merge or release; never put the address or a key in any text.
- **Check:** the tick printed a real `HEALTH: green|not green (...)` line and `local status` shows `last_run` as this round and `OK` for the plist, gh and claude (`OVERDUE`, `MISSED` and `SKIPPED` mean the Mac slept, was offline or logged out); the digest comment names this run's id and its cost line (the suite time in it is the newest suite-time artifact, which can belong to an earlier regression run); the mail step prints one `MAIL:` line: `MAIL_SENT`, or `MAIL_ALREADY` on a rerun, are done, while `MAIL_OFF` (`digest_mail` is off in the config), `MAIL_SECRETS` and `MAIL_NOT_SET_UP` mean no mail is set up, and `MAIL_FAILED`, `MAIL_REFUSED` and `MAIL_UNKNOWN` mean the send did not go: report the code and never send by another route; `DIGEST_ALREADY` and `DIGEST_STALE` mean this round was already posted or an older run came in, so post nothing again; an issue the report names exists on GitHub with its group tag. A repeated finding whose issue differs only in the body's trailing newline is the same issue: the round files `SAME #<n>`, not an update. The Adoption group's `migration` rule also lists each owner-only step as an INFO row (the same list migration-check prints) and warns on a hook installed twice or a scheduled prompt beyond its Runbook pointer.

## Non-goals
- It never changes code, pages or requirements; it reports and files issues.
- The review's suggestions never change the verdict.
- It prints the commands that remove stale worktrees and branches and never runs them.

## Success metrics
- Two rule checks on an unchanged repo print the same lines.
- After the first full review, every feature's findings are issues tagged with that feature, each with its evidence, and none is a duplicate.
- The verdict is never green while a rule could not be read. Requirement consistency checks read canonical definitions from each PRD’s Requirements section; How-to references do not create duplicate definitions. Judge savings findings use a stable subject independently of issue feature resolution.
