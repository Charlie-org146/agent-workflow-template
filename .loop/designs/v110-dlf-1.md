# Design: v110-dlf-1 (DLF-1, deliver first)

Status: DRAFT (idea step, recommended answers taken; nothing owner-only is open).
Goal: .loop/goals/v110-dlf-1.md. Its three done lines are frozen; this design meets them and changes none.
Source of the requirement text: the owner-approved DLF-1 unit in reviewed-features-2026-11-23-reworded-DRAFT.md (DLF-1.1 to DLF-1.5).
Mode: Intrapreneurship (an internal change to the loop, shipped fast).

## Problem Statement
Every v1.1.0 goal built and reviewed overnight on 11-22 to 11-23 and none merged for about 14 hours, because each waited for the
owner's word on a red-team break, a review-cap approval, a budget or a test-row choice. None of those choices loosened a check.
An interim by-hand mode took 37 acceptances in one sitting. The loop must do this by default: a goal goes from plan to merge
without waiting, except at the safety list, and the owner reviews the whole batch once, at the release cut.

## Constraints
- Frozen done lines: (1) each DLF-1 test case is a real test linked to its requirement, passes, and fails on a fixture that
  breaks only that rule; (2) a goal at its time or token budget keeps working: the budget rises to measured spend plus the
  estimate of what is left, up to 2x the goal's estimate, each raise logged with old and new figures, and past the cap the
  owner is asked as one line on the release issue while the goal keeps working at the cap; (3) the package stays under the
  size cap, no test is loosened, no row turns red, committed text never names the service repo.
- Deliver-first never skips the safety list (DLF-1.3): the safety classes, a change to what a feature promises, a loosened or
  deleted test, the leak read before any push, the full test run on GitHub before a merge.
- The goal's declared touches are the delivery, monitoring and release skills, the toys, and the regression rows file.
- No new file under the package's file-count cap unless it replaces one; new tests live with the toys.
- Text cites the requirement file by name only; no repo facts, file:line references or uncovered paths in committed text
  (they go in a private build brief).

## Premises (taken as true)
1. The stops DLF-1.1 names are exactly five: a red-team break, a plan past its review cap, a budget the goal has outgrown, a
   test failing outside the goal's own rows, an open design choice. Each is a place where the loop today refuses or waits.
2. One tracked issue per release can hold the lines. A line carries the goal, which of the five it was, the exact words that
   settle it, a recommendation and an open or accepted state.
3. The loop holds a goal's estimate and its measured spend; the "estimate of what is left" is derived by the budget rule from
   them (estimate minus the spend on steps already recorded done), so the raise is arithmetic and nothing new is measured.
4. Owner words already travel as a recorded owner reference. The setting in DLF-1.5 changes only through that path.
5. The release cut already refuses on conditions; reading the deliver-first issue there adds one more refusal, not a stage.
Premises 3 to 5 were checked against the repository before this design was written; the evidence and what is missing (a
derived remaining estimate, a ledger reader at the cut) are in the private build brief, and the build budgets for them.

## Approaches Considered
### Approach A: one stop table, one ledger function, one budget rule (minimal in files, complete in coverage)
Every one of the five stops calls one small "file this as a line and continue" routine instead of waiting; the routine decides
by one table (class -> line, or class -> still waits because it is on the safety list). One budget function applies the
raise and the cap wherever a budget is checked. The release cut reads the ledger once. One scoped setting turns it off.
Effort M, risk low-medium. Pros: no stop can be missed because the table is the only place stops are classified; the safety
list is one enumerated set the tests pin. Cons: touches three skills.
### Approach B: patch each stop where it happens
Edit each of the five sites to continue and file a line, add the budget raise where the budget stops, add a release check.
Effort M, risk medium. Pros: smallest conceptual change per site. Cons: five places can drift, a sixth stop added later is
missed silently, and the safety list has no single definition to test.
### Approach C (lateral): standing answers
Record a standing recommended answer for every question so nothing ever asks. Effort S, risk high. Rejected: a standing
consent is not "the exact words that settle it", hides the choice from the owner, and cannot honour the safety list.

## Recommended Approach
Approach A. It maps one to one onto DLF-1: the table is DLF-1.1 and DLF-1.3 together (what turns into a line, what still
waits), the budget rule is DLF-1.2, the cut check and the one list with an accept-all line are DLF-1.4, the scoped setting
is DLF-1.5. Reason mapped to the goal: the owner wants zero minutes of waiting outside the safety list, and a single table
is the only structure whose coverage can be proven by test.

## The stop table (the one place a stop is classified)
Classify by the SUBJECT of the stop, not by its kind. A stop whose subject is on the safety list WAITS; every other stop becomes
a line. Safety list (DLF-1.3, exactly): the safety classes (deleting what cannot be restored, money, security and sandbox
settings, private data, steward merges); a change to what a feature promises; a test loosened or deleted; the leak read before
any push; the full test run on GitHub before a merge. A stop that cannot be classified waits and the board names it (fail
closed). Table:
| Stop | Becomes a line unless its subject is... | Then it waits |
|---|---|---|
| red-team break | a safety class, private data, a loosened or deleted test, a change to what a feature promises | yes, board names the class |
| plan past its review cap | (never a safety subject by itself) | no: line, goal continues |
| budget outgrown | (see Budget below) | no |
| test failing outside the goal's own rows | a loosened or deleted test (the failure is the loosening) | yes |
| open design choice | one that changes what a feature promises | yes |
The leak read and the full GitHub run are not stops this goal can turn into lines; they stay gates before a push and a merge.

## Behaviour (what the build must produce)
- Stop classes (DLF-1.1, DLF-1.3). A stop on the safety list still stops and the board names the class as the reason. Any
  other stop becomes one line on the release's deliver-first issue with the words that settle it, the goal records the
  line's id on its run record, and the goal continues. A goal with three red-team breaks, a plan past its cap and a budget
  overrun therefore reaches its merge on green, and the issue holds five lines.
- Budget (DLF-1.2). At the budget: new budget = measured spend + estimate of what is left, never above 2x the goal's
  estimate. The log records the old and new figures for every raise. A raise inside the cap is logged only: the goal never
  stopped, so there is nothing to settle and no issue line. Past the cap the goal keeps working at the cap and exactly one
  line on the release issue asks the owner. "A budget overrun" in the DLF-1.1 scenario therefore means a budget that needed
  more than the cap; that is the budget line among the five.
- Release cut (DLF-1.4). The cut is refused while any line is open. The refusal prints the whole list once, grouped by goal,
  each line with its recommendation, and one line that accepts them all. A line the owner does not accept becomes a patch
  goal before the cut.
- Setting (DLF-1.5). One setting with scope goal, task or release; default on; written only with a recorded owner reference.
  Scopes nest: a goal belongs to a task, a task to a release; the most specific scope that holds a value wins (a goal's value
  beats its task's, a task's beats its release's); a scope with no value inherits. Off means that scope behaves as today (its
  first break waits) while scopes outside it do not.
- Line lifecycle. A line is open, accepted or converted. Accepted lines let the cut proceed. A converted line (the owner did
  not accept it) names a patch goal and stays open for the cut until that patch goal has merged. Every raised cap line is
  closed by the owner accepting it or by the goal finishing within the cap.

## Tests (one per requirement case, each also red on a fixture that breaks only that rule)
- DLF-1.1: three red-team breaks, a plan past its cap and a budget overrun -> merges on green, one issue with five lines each
  carrying a settle line. Red fixture: one stop class still waits.
- DLF-1.2: 240 of 240 minutes with 100 left -> 340 without stopping, log shows 240 and 340. Red fixture: the raise exceeds
  2x, or the log omits a figure.
- DLF-1.3: a goal whose only break loosens a test does not merge and the board names that reason. Red fixture: a safety
  class turns into a line.
- DLF-1.4: three goals merge with five open lines -> cut refused, one list of five plus one accept-all line. Red fixture:
  the cut proceeds, or the list is split.
- DLF-1.5: off for one goal -> its first break waits, the others' do not. Red fixture: the setting changed without a
  recorded owner reference takes effect. Overlap case: release off, one task on, one goal off inside it: the goal waits, the
  task's other goals do not, and the release's other tasks wait. Red fixture: the wrong scope wins.
- Table: every row of the stop table has a case that sends its subject through it (safety subject waits, any other becomes a
  line); an unclassifiable stop waits. Red fixture: a row removed from the table.
- Lines: a converted line keeps the cut refused until its patch goal merges.

### R2-1 — consistency (minor)

**Problem**

> The line lifecycle names three states (open, accepted, converted) but says a converted line 'stays open for the cut'. Whether the converted state itself blocks the cut or the line reverts to open is worded ambiguously, though the Tests section (a converted line keeps the cut refused until its patch goal merges) pins the intended behaviour.

**Remedy**

> State that a converted line blocks the cut while its patch goal is unmerged and becomes closed when the patch goal merges.

### R2-2 — clarity (minor)

**Problem**

> 'Raised cap line' is undefined wording, and the DLF-1.1 test still describes 'a budget overrun' without saying it is a budget needing more than the cap, which the Budget bullet now defines as the only budget case that yields a line.

**Remedy**

> Say 'cap line' (the one budget line filed past the cap) and word the DLF-1.1 test fixture as 'a budget that needed more than the cap'.
