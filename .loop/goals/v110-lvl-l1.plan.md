### What the code does today (read on main f7f86150d) and what is not on main yet

- The pull request run is the workflow `regression-pr.yml`, generated from the template in `lanes_cli.py` (lines 206-212): eight shards and a tree job each run `regression.py run nightly --reuse --tier goal` with a time budget `B=866` seconds (`B=-1` when the row tables change), then the `affected` job runs `cutgate.py` over the shard time files and fails on a row that was cut, left or not run. The `merge_group` trigger has one job (`if: github.event_name == 'merge_group'`) that runs no row.
- `runs.chosen(rows, target)` (runs.py:276) selects rows by the OLD level words: `land` is the rows with level `land`, `nightly` those with `land` or `nightly`. `tiers.plan` (tiers.py:273) then picks from them the rows the change reaches. A budget cut (`runs.execute`, runs.py:191, and the `BUDGET ... LEFT` line) drops rows that do not fit.
- `levels.py`, the record `.loop/regression-relevel.tsv` and the marker row `lvl-armed` are G1/G2 work and are NOT on main: this plan is written against G1's plan (6236d4104, with the four binding build rules of its brief: a covered row is never L0, the record has a `cmd` column, no `.gitattributes`, placeholder repo names in fixtures). ### The steps

1. L1 picks (done lines 1 and 4). `levels.py` gets `pick(rows, level, root)`: for the target `L1` it returns the rows whose stage is L0 or L1, plus every row tagged `security` or `private` whatever its stage; for `L0` the rows of stage L0; for `L2` every row (G3 uses it). `runs.chosen` calls it for the three new target words `L0`, `L1`, `L2` (and still serves `land` and `nightly` as today, because the scheduled run is moved onto the record by G3, not here). `tiers.plan` then picks from that set the rows the change reaches, as it does today, so a change reaching one L0, one L1 and one L2 row runs the first two and not the L2 one (done line 1). The security and private rows are in the picked set whatever the change reaches, so a change that reaches no private row still runs every private row (done line 4). The page says "plus every security and private-data row"; this plan reads that as always, which is stricter than done line 4 and includes it.
2. The pull request workflow runs L1 (done lines 1, 3 and 6). The template in `lanes_cli.py` changes `run nightly` to `run L1` and drops the time cut for L1: `B` is `-1` for every shard, because done line 6 wants every chosen row to run, never cut (a cut row is what `cutgate.py` already fails). The `merge_group` job and the `if: github.event_name == 'merge_group'` job text stay byte for byte, and `regression.py workflow` regenerates `regression-pr.yml` from the template.
3. The miss report (done line 6). `cutgate.py` gets a `missed(shard_files, minutes)` step run by the `affected` job after its checks: the L1 time is the longest shard's summed row seconds (the shards run at once; the page measures the run a pull request waits for), and when it is over `l1_minutes` (a setting, default 10, registered in `settings.py` with its one-line meaning) it prints `missed: <cause>` followed by the three slowest rows with their seconds, and exits 0 unless a row was cut or not run (that failure stays as today). The cause is one plain sentence: the slowest row's share of the run (`the three slowest rows took 7 of the 11 minutes`) or `one shard ran N rows past the others`. An 11-minute run therefore shows `missed:` with three rows while every chosen row ran.
4. Security rows that flip (done line 5). `levels.py` gets `retry(row, first, run_again)`: for a row tagged `security` that FAILs on its first attempt in an L1 run, `runs.execute` (runs.py:191) runs it once more on the same tree; a pass the second time is state `FLAKY`, not `PASS`. `FLAKY` is counted with the failures (the `RESULT` line, the exit code and the `affected` check treat it as not a pass), the row prints `FLAKY <id>: failed then passed`, and `runs.sync_issues` (runs.py:110) opens one issue for it (it already keeps one issue per failing row; a FLAKY row is keyed the same way, and a second FLAKY run comments on that issue and opens none). A GitHub write stays a preview without `--live`, as `sync_issues` already does. The existing REG-9 flag (`tiers.flaky_apply`, a flip across runs on one commit) is left as it is.
5. The goal's test step (done line 2). At a goal's test step (`qa`, `ship`, `pr`) whose pull request will get L1, cover's rule skips the covered L1 rows; this goal makes the local lane run the goal's L0 rows only (`lane.py` passes the target `L0`), records no local L1 lane record, and prints `COVERED by L1`: cover's record name is the constant `L1` in `cover.py` (cover's own plan already names it so; if cover merges with another name, this goal renames the one constant, a one-word edit the build checks). A goal whose pull request will not get L1 (cover's predicates fail) runs as today.
6. The merge queue (done line 3). Nothing in the queue path is edited. A toy parses the generated `regression-pr.yml` and asserts that the `merge_group` job has no `regression.py run`, no row command and the same `if` and steps as the golden text taken from main f7f86150d, and that the `shard` and `affected` jobs both carry the `github.event_name != 'merge_group'` condition. The queue's required checks (the ruleset) are not edited.
7. The marker row `lvl-armed` (G1's brief: "the marker row `lvl-armed` is G2's"). This goal adds the row to `.loop/regression.tsv` so G1's refusals arm: with it a table row with no record entry is refused. Its command is G1's merged `levels` check; the build uses G1's merged command name and a toy asserts that the table is armed and valid. The `lvl-armed` row's addition is the only change to the table's existing meaning; the rows are only added.
8. Docs, text only: the two SKILL.md command maps and `commands.md` get the `L0`, `L1`, `L2` targets, `l1_minutes`, the `missed:` line and the FLAKY security line, one line each.
