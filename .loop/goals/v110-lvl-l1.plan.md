### What the code does today (read on main f7f86150d) and what is not on main yet

3. The miss report (done line 6; answers d4, d8, d12, d13, d32). `cutgate.py` gets a `missed(files, minutes)` step run by the `affected` job after its checks. Two numbers are kept apart: the EXECUTION time (the longest job's summed seconds of the rows that RAN in THIS run: status RAN in the shard time files; a cached or reused time, status SEL or a cache hit, is never added; the tree job included, from `tree.tsv`) and the TURNAROUND (the required check's elapsed time, from the workflow run's own created and completed stamps that the `affected` job reads with `gh run view`; setup, queue and runner waits are shown as `setup <n> min` and `rows <n> min`). `missed:` is judged on the TURNAROUND, because the page's L1 goal is the wait for the required check; the row times attribute the cause. When the turnaround is over `l1_minutes` (a setting, default 10, in `settings.py` with its meaning) it prints `missed: <cause>`, the three slowest rows with their seconds, the line `l1_minutes is <n> (settings.py); the check took <m> minutes (setup <a>, rows <b>)`, and the action line `fix: move the slowest row to L2 with regression.py level <id> --stage L2, or raise l1_minutes in settings.py (owner)`, and exits 0 unless a row was cut, left or not run. The cause is one plain sentence (`the three slowest rows took 7 of the 11 minutes`, `setup took 6 of the 11 minutes`, or `one job ran N rows past the others`). A repeated miss (two consecutive pull requests on the base) is named in the line `missed twice: the owner of the slowest row decides: move it or raise l1_minutes`; the owner of a row is the author recorded in G1's record. `l1_minutes` is validated BEFORE any work: a whole number of at least 1, booleans and anything else are refused with the line `l1_minutes: <value> is not a whole number of at least 1. Fix: set l1_minutes to a whole number such as 10 in settings.py`, the stable code `L1_MINUTES_BAD`, on stderr and a nonzero exit; there is no silent fallback. The old repair text of the cut gate is replaced by `L1 has no time cut; the row <id> did not run: rerun the shard, or see the log of job <name>`. A cache-write failure (all.tsv, the times cache) keeps the nonzero exit visible: the CLI prints on stderr `times cache not written (<error>): <the filesystem cause>. Fix: free space or fix the write access on <path>, then rerun the affected job (owner if the path is not yours)`, names the temporary file it left or removed, retries the write once, and still fails the check when the retry fails; it never leaves the check green on a failed write. The hard ceiling `timeout-minutes` is derived as `max(30, 3 * l1_minutes)` in the template, not a bare literal.
4. Security rows that flip (done line 5; answers d5, d7, d15, d17, d27, d28). `runs.execute` (runs.py:191) retries a security-tagged row that FAILs ONCE, only when the row is ELIGIBLE: the retry runs in a FRESH temp HOME and a fresh `TOY_SKIP_FILE`/row scratch directory (the first attempt's are kept for the log and never reused, so a leftover cannot make attempt two pass), and a row carrying the tag `noretry` (read by `execute`, set through G1's `level` command) is never retried, nor is a first attempt that timed out or ended with unknown effects (killed, signalled): its first failure is retained and the row stays FAIL with no retry. Before attempt two the shard prints `attempt 1 side effects are not reconciled; attempt 2 runs in a fresh HOME`. A pass the second time keeps the state `FAIL`, sets the existing `flaky` mark and the new field `retried`, and prints `FLAKY <id>: failed then passed (rerun once in a fresh HOME). Fix: find the first failure in the shard log, then fix the row or the cause; a flip is a failure until then`. The within-run evidence is carried by `tiers.flaky_apply` and the record serialization: a first-ever fail-then-pass with no previous record keeps `flaky` and `retried` in the saved record (the historical post-processor no longer overwrites the within-run mark), and `shown()` enforces the attempt limit of two. Because the state stays FAIL, `regression.py`'s `failed` list, the `RESULT` line, the exit code, `runs.write` and `lanes.py`'s status assert count and record it as failed with no edit to `regression.py` or `lanes.py`; the row is never reused. A non-security row that fails stays FAIL with no retry.
5. The one issue, in its OWN job (done line 5; answers d3, d6, d9, d16, d18, d19, d20, d22, d23, d24, d25, d29, d30; the owner's word o1063, ledger o991: the issue write in its own job that runs no pull request code, `issues: write` on that job only). The shard and `affected` jobs hold NO write permission (they keep their current permissions) and write no issue. Each matrix leg, the tree job included, uploads `t.tsv`, `tree.tsv` (tree job) and `flaky.tsv` with a versioned, redacted evidence file `evidence.json` (schema version, row id, both attempt outcomes, the first failure's escaped last 20 lines, job name, run id, commit sha, repository); `affected` reads `s/shard-*/` for every leg and the tree. A new job `filer` (`needs: affected`, same `merge_group` exclusion) checks out ONLY the BASE ref's commit (`github.event.pull_request.base.sha`), never the pull request head, downloads the artifacts as DATA, validates them (schema version, size bounds, repository, run id and commit sha equal to the run's own, row ids that exist in the base table) and runs `cutgate.py file` from the base checkout; it alone holds `issues: write`, and the template passes `--live` and `GH_TOKEN: ${{ github.token }}` there. The issue is keyed by a hidden marker `flaky:<id>`: the filer searches for it before creating (and before printing the hand-filing line), opens ONE issue titled `FLAKY security row <id>` (or comments on the open one: never a second issue), retries once on a transient error, serializes concurrent creators (re-search after create; the oldest issue wins, a duplicate is closed with a comment), and distinguishes a definite failure (`issue not filed (<error>): file it by hand: FLAKY security row <id> on <pr>`, job fails) from an unknown outcome (`issue state unknown: search for flaky:<id> before filing by hand`, job fails). A fork pull request gets a read-only token: the filer previews and prints the hand-filing line without failing the run. The base ref has no filer until this goal merges: while the base lacks `cutgate.py file` the job prints `filer not on the base yet: file by hand` and exits 0 (this case ends at the merge). The first-failure tail rides in `evidence.json`, so the issue contains it (the shard log is not needed). The toy renders the workflow and proves: `filer` has no checkout of the head, runs no `package.py` or `cutgate.py` from the head, and holds the only `issues: write`; a pull request that changes `cutgate.py` or `dev/package.py` cannot run in the filer; missing, malformed or mismatched evidence is refused; a stateful fake `gh` shows live creation, deduplication under two concurrent reports and an ambiguous success.

A goal whose pull request will not get L1 runs as today. `COVERED by L1` also needs proof that L1 ran: the ship step reads the `affected` check of the head SHA and, when it is missing or cancelled, prints `L1 did not run on <sha>: rerun the regression-pr workflow` and does not call the goal covered (answers d10, d31).
