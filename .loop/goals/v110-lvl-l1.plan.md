### What the code does today (read on main f7f86150d) and what is not on main yet

- The pull request run is the workflow `regression-pr.yml`, generated by `lanes_cli.workflow()` (lanes_cli.py:293) from the NARROW template in `lanes_cli.py`. Its eight shards and a tree job each run `regression.py run @LEVELS@ --reuse --tier goal` (lanes_cli.py:209; `@LEVELS@` is replaced at lanes_cli.py:321 from the setting `ci_levels`, default `nightly`) with a time budget `B=866` seconds (`B=-1` when the row tables change). A docs-only change exits the shard before any row runs (`documents and goal records only: no rows to run`, exit 0). Then the `affected` job runs `cutgate.py` over the shard time files and fails on a row that was cut, left or not run. The `merge_group` trigger has one job, `if: github.event_name == 'merge_group'`, that runs no row. The scheduled workflow `regression.yml` is rendered by `actions.py`, also from `@LEVELS@`, and refuses words other than `land` and `nightly`: it is G3's and this goal does not touch it.
- `runs.chosen(rows, target)` (runs.py:276) selects rows by the OLD level words. `tiers.plan` (tiers.py:273) then keeps only the rows the change reaches (and reuses a passing row from the branch record under `--reuse`), `regression.py cmd_run` drops rows listed `nightly` in the limits file (`completion.off_pr`, completion.py:26) on the PR path, and `runs.execute` (runs.py:191) runs what is left within the budget.
- `regression.py` ends a run with `failed = [... state == "FAIL"]` (regression.py:~365), prints `RESULT`, exits 1 when `failed` is not empty, and calls `runs.sync_issues` only when the run is NOT `--reuse` (the PR shards ARE `--reuse`, so they open no issue today). `lanes.py` asserts every recorded status is one of PASS, FAIL, KNOWN, LEFT, SKIPPED (lanes.py:81).
- `levels.py`, the record `.loop/regression-relevel.tsv` and the marker row `lvl-armed` are NOT on main: this plan is written against G1's plan (6236d4104) and its brief (a covered row is never L0, the record has a `cmd` column, placeholder repo names in fixtures, refusals print the row id and a code). ### The steps

1. L1 picks and the mandatory set (done lines 1 and 4). `levels.py` gets `pick(rows, level, root)`: for the target `L1` the rows of stage L0 or L1; for `L0` the rows of stage L0; for `L2` every row (G3 uses it); and `mandatory(rows, root)`: every row tagged `security` or `private`, whatever its stage. `runs.chosen` calls `pick` for the new target words `L0`, `L1`, `L2` and still serves `land` and `nightly` as today (the scheduled run moves onto the record in G3). The mandatory rows are added AFTER planning and filtering, so no later step can drop them: `tiers.plan` adds the mandatory ids to its `todo` and removes them from `reused` (a mandatory row is never satisfied from an old record, and is never `--reuse`d); `completion.off_pr` leaves a mandatory id out of the nightly exclusions; and the sharding, the budget and the `--tree` split treat them like any picked row. So a change reaching one L0, one L1 and one L2 row runs the first two and not the L2 one (done line 1), and a change that reaches no private row still runs every private row (done line 4). The page says "plus every security and private-data row"; this plan reads that as always, which includes done line 4's narrower case. Cost: the owner decides the reading (below); the toy asserts the mandatory rows are in every L1 run.
2. The pull request workflow runs L1 (done lines 1, 3 and 6). The PR template gets the word `L1` directly (`run L1 --reuse --tier goal`), NOT through `ci_levels`, which G4 retires and which the scheduled workflow still reads, so `actions.py` is untouched and the scheduled runner keeps `land` and `nightly`. The L1 shard has no time cut: `B` is `-1` for every shard, because done line 6 wants every chosen row to run, never cut; the hard bound is the job's own `timeout-minutes: 30`, which stays, and a cut row is still what `cutgate.py` fails. The docs-only short circuit no longer exits 0: it sets `LOOP_L1_MANDATORY_ONLY=1` for the run, `pick` then returns only the mandatory rows, and the shard runs them (a documents-only change still runs the security and private rows; it reaches no other row). The `merge_group` job and the `if: github.event_name == 'merge_group'` text stay byte for byte; `regression.py workflow` regenerates `regression-pr.yml` from the template.
3. The miss report (done line 6). `cutgate.py` gets a `missed(files, minutes)` step run by the `affected` job after its checks. The L1 time is the longest job's summed seconds of the rows that RAN in THIS run (status RAN in the shard time files; a cached or reused time, status SEL or a cache hit, is never added), the tree job included (the shard files plus `tree.tsv`). When that is over `l1_minutes` (a setting, default 10, registered in `settings.py` with its meaning, an integer of at least 1, any other value falls back to 10 with the note `l1_minutes: <value> is not a whole number of at least 1; using 10 (settings.py)`) it prints `missed: <cause>` followed by the three slowest rows with their seconds and the line `l1_minutes is <n> (settings.py); the run took <m> minutes`, and exits 0 unless a row was cut, left or not run (that failure stays as today). The cause is one plain sentence: `the three slowest rows took 7 of the 11 minutes` or `one job ran N rows past the others`. The old repair text of the cut gate, `raise the shard budget (owner)`, is replaced by `L1 has no time cut; the row <id> did not run: rerun the shard, or see the log of job <name>`. A cache-write failure in `cutgate.py` (all.tsv, the times cache) prints `times cache not written (<error>): the next run starts without row times; rerun the affected job` and does not fail the check.
4. Security rows that flip (done line 5). `runs.execute` (runs.py:191) runs a security-tagged row that FAILs once more, on the same tree and in the same row environment and temp HOME as the first run (the same way it already reruns a failing row to read its tail); a pass the second time keeps the state `FAIL` and sets the existing `flaky` mark and the new field `retried`, and prints `FLAKY <id>: failed then passed (rerun once on the same tree). Fix: find the first failure in the shard log, then fix the row or the cause; a flip is a failure until then`. Because the state stays FAIL, `regression.py`'s `failed` list, the `RESULT` line, the exit code, `runs.write` and `lanes.py`'s status assert already count and record it as a failed row with no edit to `regression.py` or `lanes.py`; the row is also never reused (the existing flaky rule). The retry reruns only the failed row's own command; a row whose command is not safe to run twice is the row author's to tag, and the toy shows a retry cannot leave state behind in the temp HOME. A non-security row that fails stays FAIL with no retry.
5. The one issue (done line 5; the shard cannot write issues and `sync_issues` does not run under `--reuse`). The shard writes `flaky.tsv` (`id TAB seconds`) next to its times file and uploads it with them; the `affected` job's `cutgate.py` reads the shard files and, for each flaky id, opens ONE issue titled `FLAKY security row <id>` (or adds a comment to the open one for that row: never a second issue) with the pull request, the commit and the first failure's last 20 lines (the shard prints them to its log; the issue names the job), through `gh issue` as `sync_issues` does, a preview without `--live` and a write with it. A failed `gh` call prints `issue not filed (<error>): file it by hand: FLAKY security row <id> on <pr>` and fails the job; it never prints a success. The `affected` job needs `issues: write` (job-level permission) for that write: a workflow permission edit, listed for the owner below; the toy proves the path with the fake `gh`.
6. The goal's test step and the cover (done line 2). At a goal's test step (`qa`, `ship`, `pr`) whose pull request will get L1, cover's rule skips the covered L1 rows; this goal makes the local lane run the goal's L0 rows only (`lane.py` passes the target `L0`), records no local L1 lane record, and prints `COVERED by L1`: cover's record name is the constant `L1` in `cover.py` (cover's plan already names it so; if cover merges with another name, this goal renames the one constant). `COVERED by L1` is printed only when `levels.pick(rows, "L1")` plus the mandatory rows contain every row the goal's change reaches that is not L0 (a function in `cover.py`, about 100 B): a goal whose reached L1 rows would not run on the pull request (for instance a docs-only change that reaches an L1 row) runs them locally and prints `NOT COVERED by L1: <ids>`. A goal whose pull request will not get L1 runs as today.
7. The merge queue (done line 3). Nothing in the queue path is edited. A toy parses the generated `regression-pr.yml` and asserts the `merge_group` job has no `regression.py run`, no row command, and the same `if` and steps as the golden text from main f7f86150d, that the `shard` and `affected` jobs both carry `github.event_name != 'merge_group'`, and that the only new permission is `issues: write` on the `affected` job. The queue's required checks (the ruleset) are not edited.
8. The marker row `lvl-armed` (G1's brief: the marker is G2's). With it a table row with no record entry is refused (G1's refusal, with the row id and its code; `LEVELS_NO_RECORD` when the record is missing). Adding it would refuse every pull request that carries a table row with no record entry, so this goal (a) adds a record entry (`regression.py add ... --stage ... --risk ...`, G1's merged form) for each row it adds in the same commit, (b) adds the marker row LAST in the goal's own row commit, (c) runs `relevel`'s dry run on the table and the record before the marker row goes in (it prints any row without an entry), and (d) a toy asserts the table is armed and valid, that a row without an entry is refused by G1's code with its repair, and that this goal's own rows all have entries. The repair a goal sees is G1's: add the entry with `regression.py level ID ...`.
9. Docs, text only: the two SKILL.md command maps and `commands.md` get the `L0`, `L1`, `L2` targets, `l1_minutes`, the `missed:` line, the FLAKY security line and its repair, and the `flaky.tsv` file, one line each.
