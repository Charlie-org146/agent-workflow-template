3. The miss report (done line 6). `cutgate.py` gets a `missed(files, minutes)` step run by the `affected` job after its checks. Each leg writes the epoch seconds of its start and end into its times file (a `# span <start> <end>` line, tree job included); `affected` takes the TURNAROUND as the latest end minus the earliest start of the legs (no API call and no permission; the wait for a runner before the first leg is not measured, which is said in the output and in the owner items) and the EXECUTION as the longest job's summed seconds of the rows that RAN in THIS run (status RAN; cached or reused rows, status SEL, are never added; `tree.tsv` included). `missed:` is judged on the TURNAROUND. When it is over `l1_minutes` it prints `missed: <cause>`, the three slowest rows with their seconds, `l1_minutes is <n> (settings.py); the legs took <m> minutes (rows <b>; runner wait not measured)` and `fix: move the slowest row to L2 with regression.py level <id> --stage L2, or raise l1_minutes in settings.py (owner)`, and exits 0 unless a row was cut, left or not run. The cause is one plain sentence (`the three slowest rows took 7 of the 11 minutes`, or `one job ran N rows past the others`). `l1_minutes` is ONE rule, used by `settings.py` and `cutgate.py` alike: a whole number of at least 1 (default 10). Anything else, booleans included, is refused before any work on stderr with the code `L1_MINUTES_BAD`, the line `l1_minutes: <value> is not a whole number of at least 1. Fix: set l1_minutes to a whole number such as 10 in settings.py` and a nonzero exit; there is no fallback anywhere. The old cut-gate repair text is replaced by `L1 has no time cut; the row <id> did not run: rerun the shard, or see the log of job <name>`. A cache-write failure (all.tsv, the times cache) is never green: stderr says `times cache not written (<error>): <the filesystem cause>. Fix: free space or fix the write access on <path>, then rerun the affected job`, names the temporary file it left or removed, retries the write once, and fails the check if the retry fails. The 10-minute goal is REPORTED, not enforced (the only enforced ceiling is the 30-minute job limit): an owner item. A repeated-miss escalation would need a store across pull requests and a permission to read it, so it is a follow-up, not in this goal.

Fix: find the first failure in the shard log, then fix the row or the cause; a flip is a failure until then`. No judgement is made when the first attempt timed out or was killed (effects unknown): that row stays FAIL with no flaky mark; a row tagged `noretry` through G1's `level` command is judged by its first run only. The environment of the rerun is the one `shown` already uses; the same-environment limit is stated in the FLAKY line, and a row author whose command is not safe to run twice tags it `noretry`.
