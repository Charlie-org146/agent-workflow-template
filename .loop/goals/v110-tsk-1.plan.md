# Plan: v110-tsk-1, the operation schedules the owner's tasks ahead of fixes to its own tools

## Implementation plan

Goal: when the operation picks the next goal for a worker, a goal from a task in the owner's selected release brief comes before a fix, patch or tool goal; a fix goes first only on a named reason; a tool bug that hits a task goal uses a recorded workaround at once, which really frees that task goal to start, while the real fix queues behind the task goals; a red main that is red only on rows that pass on PR runs does not stop task merges; and the board shows the schedule in order, each goal marked task or fix, with the reason any fix is ahead and one owner line to reorder it. The requirement text is the reviewed TSK-1 unit (TSK-1.1 to TSK-1.5), copied from the owner-approved reworded features file by name; its words are not changed here.

Size of the change: medium. Three new modules under skills/ hold the logic and are the single place that reads the queue, the briefs and the two small state files; each existing queue reader calls the loader and drops its own parse; one new toy proves the five requirements; one new row is added to the regression table. No existing script grows and none crosses a size line.

### Depends on (order)
The text goal for tasks 12 to 14 merges first, so the TSK page exists on main when this goal's rows are merged. This goal also sequences behind v110-fast-clock and v110-fast-steps-2, which edit some of the same queue readers: the build starts after they have merged, runs the lane overlap check on the files below first, and re-measures bytes after its own merge-up, so no edit of a sibling is left in a parser this goal deletes. If the order cannot be kept, the loader move lands as its own first pull request and the policy follows.

### What exists
- The queue is one tracked file with one line per goal. Several readers each parse it on their own (the start path, the monitor plan, the board status used by the board and the check-in, the JSON board, the replan view) and all take the goals in file order. The start path fills the free worker slots in that order. A goal waits only for a dependency, an assigned session, full slots or low memory, and each wait already has a reason that the boards print.
- Task briefs (one file per task, from the task-list goal) name the goals that carry each task out, name the release they belong to, and have a state. Nothing marks a queued goal as a task goal or a fix, nothing carries a priority, and no tool bug leaves a record.
- The boards print the queue as numbered rows ("N. slug | waits for ... | ETA") and a "Queued goals" section; the check-in and the JSON board project the same queue items.
- A merge goes ahead once the required checks on the pull request's own head are green; a check that is red only on rows already known red on main is let through. The release workflow has its own hold for publishing. TSK-1.4 is a statement about this existing path.
- Several queue-reading scripts are already above the 19,000-byte line (below the 20,480 hard line) and about as many more sit within a few dozen bytes below it. Real per-file sizes are re-measured at build; a script that is over the line may only shrink.

### Design (A to K)
A. One shared loader, in three modules so each stays well under the size line: `schedule_load` (parse, classify, sort, eligibility), `schedule_state` (the two state files, the lock, atomic writes) and `schedule` (the command line and the workaround verbs). `load(root)` is the only reader of the queue lines, the task briefs, the owner order and the workaround record. It returns one result: the goals in schedule order, each with its kind, task name, priority, order reason, held reason, workaround mark and the exact strings the boards print (J), plus diagnostics and an `incomplete` flag. Every consumer calls it and drops its own parse: the start path, the monitor plan, the board status (and through it the board and the check-in), the JSON board and the replan view. Because each consumer's own parser moves into the loader, each hook is a net shrink. Before any code, the build writes a per-consumer table of bytes removed against bytes added (the call, the import, the diagnostics handling and the mark rendering), measured on the real files; rendering lives in the loader, never in a consumer, and a consumer that would still grow gets its hook moved to a file that has room. The size row asserts every touched script before and after.
B. The one source of the owner's selected release R. R is one value per repo, independent of any goal: the release the owner's release brief names for the release that is not yet published (read by the loader; with none, or with several, R is unset). The effective selection is shown, as `release: R (source: brief)`, by `show` and in the board's status area. A goal carries membership through the `release:` key of its queue line; the real creation interfaces supply it: `goal.py new --release` and the queue command that appends a line (which gains the same `--release` option and keeps the release-approval semantics it has today; its file is on the touch list), so membership is acquired at creation with no hand-written metadata, and a toy goes from creation through dispatch with the real command to prove it, on a mixed queue with matching briefs for the selected and an unselected release. Names are normalised (trimmed, case-folded, one optional leading `v`). A batch heading, if it names a release, is only a default for lines under it; the line's own key wins. A goal is a task goal when its line carries R (equal to the selected release) and a live, non-replaced, non-patch task brief whose release line equals R lists it. When a line's release and its brief's release differ the goal is a fix and the loader prints one diagnostic naming both; when no queue line carries a release, or briefs exist and none matches any queued line's release, every goal is a fix (today's order) and the loader prints one warning that classification is idle. Patch briefs, briefs of other releases and replaced briefs make nothing a task goal; a goal listed in several briefs takes the selected-release one; two selected briefs with different priorities resolve to the lower number, then the brief's file name, named in the reason. A brief may carry one optional line `- Priority: N` (a whole number, lower first); without it the brief sorts by file name.
C. Order. The key is: safety goal, then owner order, then a fix that blocks a queued task goal, then task goals before fixes, then the brief's priority, then fewest unmet dependencies, then queue-file order. Safety sorts above owner order, so an owner line never buries a safety fix; when a safety goal would sit behind an owner-ordered one the loader prints a loud line naming both. The sort is stable, so with no briefs and no other input the order is exactly today's. The seven-level key and the single goal are kept (see Alternatives); the policy has its own off switch (the setting `schedule_policy`, default on) so it can be turned off apart from the loader move, and with it off the loader returns file order and no marks.
D. A fix goes first only on a stored reason (TSK-1.2). A fix may sort ahead of a task goal only for one of four reasons: it blocks a queued task goal (directly or through other goals) that no activated workaround covers; it carries the optional queue key `first: TASK_SLUG: WHY`; it carries `first: safety: CLASS` naming a class on DLF-1.3's safety list (a deletion, money, security, private data, a steward merge, a leak, a loosened test); or the owner order places it (TSK-1.5 makes the owner's line an explicit additional reason, shown as "ordered by owner (RECORD)"). A fix with none of these stays behind the task goals ("after task goals"). A `first:` naming a goal that is not queued is ignored, with one warning on stderr, in the frozen run record and in `show`'s list of ignored keys. A fix passed over by more than five task goals, or whose workaround is older than seven days or used by more than three goals, is shown as overdue with its count or age and the command that closes or retires it.
E. Workarounds (TSK-1.3). A record outside the repo's tracked files (under the git common directory's loop folder next to run records) holds one line per tool bug: key, the queued fix goal, the goals it applies to, its kind (`tool` obstruction or `dependency`), the stored words, the first goal, the issue number, the review date, an attempt count and a state (`pending`, `done`, `failed` or `closed`). `workaround add KEY --fix SLUG --applies GOALS --kind tool|dependency --feature PAGE --found REF [--owner-record ID] "words"` requires the fix to be a queued or running goal and the kind to be given (an absent kind is refused; a `dependency` never waives anything). Before it writes anything it validates what the existing finding command needs (provenance, feature mapping and, where required, a scoped owner authorization) and screens the words: words that skip anything on DLF-1.3's list, or contain secret-shaped values (tokens, keys, credentials), are refused with a code that names the class and never the value. Under the lock it writes a `pending` line, files the one issue through the existing finding command, then marks the line `done` with the issue number. The issue title is derived only from KEY and the fix slug, so a retry cannot file a second issue. `workaround reconcile KEY` is the recovery command: it looks the issue up by that title across open and closed issues, page by page, with three outcomes: found (the line is completed), none (a create is allowed again) and unknown (the lookup failed: the line stays pending, nothing is created). Automatic retries are counted in the pending line and stop after three, with a refusal printing `workaround reconcile KEY`. A pending record never waives anything.
F. Activation and eligibility. `workaround use KEY --goal SLUG` checks applicability (the goal is in the record's list and the live queue, and the kind is `tool`), runs the words through the existing safety checks the operation already applies (decision kinds, risky paths, always-ask), delivers the words by printing them (stored words are text for the session to read, never run by this module) and only then writes the activation for that key and goal. Only an activation waives: for that goal the named fix no longer blocks it and its wait on that fix is waived, while the original dependency and the waiver's provenance stay recorded and any other prerequisite stays. `workaround fail KEY --goal SLUG --reason` records a failed use and restores the wait for that goal; `workaround close KEY --reason` retires a record so it waives nothing; both go through the same lock and atomic write and print their side effects. At schedule time the record's goal list is re-checked against the live queue; a merged, renamed or unknown goal's waiver is dropped with one note. The loader exposes one eligibility function that the start path's freeze and assignment call, enforcing holds and activated waivers; the toy proves it through a real freeze and assignment (a pending, an unused and a refused-use record leave the task goal waiting; an activated one starts it while the fix is unmerged). When `fail` or `close` revokes an activation for a goal that a worker already holds, the running goal is not killed: it keeps its slot, its row shows `workaround KEY revoked: wait restored`, its run record gets a waiting note naming the fix at its next step boundary through the existing waiting mechanism, no further goal that depends on it starts, slot accounting is unchanged and the goal resumes once the fix has merged; activations for other goals are untouched, and a toy revokes after a real assignment and checks all of that.
G. A red main does not stop tasks by itself (TSK-1.4). Nothing in the merge path is changed. The first build step is a read-only probe of the merge entry point, the known-red allowance and the safety-approval boundary, written to the private build brief; if any of the three does not exist for the case, the build stops there. The toy then drives the real merge entry point and its real gate (nothing in the gate is replaced by a stand-in in the gh stub or the CI helper), in a temp repo with a stub remote and a temp HOME, no network, on a repo whose main run is red on one row and a pull request that is green on every required check with no new red: it merges, and a batch's eligibility is told apart from an individual merge. The known-red allowance has its own cases. Negative controls: a red that reaches the pull request's own run, and a pull request that touches a safety class, are refused, the safety case naming the real approval boundary it exercises; if no such boundary exists the toy reports that plainly and the build stops before any gate file is edited. Merge-gate files this goal touches: none is edited; the toy reads the merge command, the automatic-release gate and the known-red list.
H. Owner order (TSK-1.5). `order SLUG [SLUG ...] --by RECORD` first checks that RECORD is a real owner record in scope through the existing owner-record lookup (an unknown or out-of-scope record refuses before anything is written), then writes the order file and a last-good copy together under the lock by atomic rename. Those goals sort after safety goals and before everything else. Merged or unknown slugs are pruned on read with one printed line. `order --clear` removes the order file and its last-good copy without parsing either, so it works on a torn or malformed file.
I. Unreadable input fails safe, visible, and recoverable. An absent optional file is normal. An unreadable or malformed one (a brief, the workaround record, the order file, a queue line) is never read as "nothing": the loader marks the result `incomplete` with the input, the cause and an input-specific code, fix and recovery. Dispatch is conservative per input and degrades only what depends on the failed input: an unreadable brief set drops classification and priority but keeps valid safety goals and the owner order (starts the failure could affect are held and named); an unreadable workaround record assumes no waiver; an unreadable owner order falls back to its last-good copy with a loud note, and with no usable copy holds new starts with the reason and the exact repair (`order --clear`) on every board, the hold clearing itself once the file reads cleanly. Every consumer propagates incompleteness: the human boards and the check-in print one persistent schedule-status line at the top (J), the JSON board carries `incomplete: true`, and every command line consumer, including one-shot watch, board, check-in and `show`, writes the cause to stderr and exits non-zero (3), keeping any partial output without reporting success. State files are written by temporary file and rename under a lock; the lock has a bounded wait of five seconds, refuses on timeout with no write, and a lock older than a minute whose owner is gone is broken with a note. A torn file reads as unreadable.
J. Exact strings, one grammar. The loader produces every string and all four consumers (queue view, live board, check-in, JSON board) take them from it; a toy compares the four. A row has one fixed cell order: `  N. slug | KIND | PLACEMENT | HOLD | WORKAROUND | existing cells`, and a cell that does not apply is omitted, never blank. KIND is `task NAME` or `fix`. PLACEMENT is for a fix one of `after task goals`, `ahead of SLUG (blocks SLUG)`, `ahead of SLUG (first: SLUG)`, `ahead of SLUG (safety: CLASS)` or `ahead of SLUG (ordered by owner (RECORD))`, where SLUG is the first task goal the fix sits ahead of, and for a task goal moved by the owner line `ordered by owner (RECORD)`. The board prints only these reason classes, never the free WHY text of a queue key, and a toy proves that WHY text appears in no board, check-in or JSON string. An overdue fix adds a suffix to its placement, count first, then age when both apply: `overdue: passed over by N task goals; workaround KEY is N days old (workaround close KEY --reason)`. HOLD is `held: REASON (repair: COMMAND)`. WORKAROUND on a freed task goal is `workaround KEY (fix SLUG pending)`; a pending record also shows on the board. Two persistent lines sit at the top of the boards and the check-in, each only when it applies: `schedule incomplete: INPUT (CAUSE); dispatch: FALLBACK; repair: COMMAND` and `schedule notes: N (schedule.py show)` (the count of diagnostics that are not incomplete-input ones: classification idle, a release disagreement, a safety goal behind an owner-ordered one, an ignored `first:` key, pruned slugs, dropped waivers); when briefs exist but nothing classified, one `classification idle: REASON` row prints once. Marks may co-occur in the fixed order above; one toy fixture renders a row with every mark and compares the four consumers byte for byte. Worked example, two briefs, three goals:
```
Queue, in order:
  1. v110-a | task Task-first | waits for: -
  2. v110-b | task Task-first | waits for: v110-a
  3. v110-fix | fix | after task goals | waits for: -
```
With an owner line moving v110-fix first the first row becomes `  1. v110-fix | fix | ahead of v110-a (ordered by owner (o123))`. The marks and both top lines are left out when the repo has no task briefs and no notes, so every existing board fixture prints today's text byte for byte.
K. Errors and diagnostics, agent-ready. Every refusal and every incomplete-input diagnostic prints one line to stderr with a stable code (SCHED-E01 and up, each with an anchor in the monitoring skill's command reference), what happened, the fix, the recovery, the dispatch behaviour that applied, the effective context (the module versions, the state and config locations, the relevant environment variable names and the sanitized underlying cause), the phase, the side effects (none, partial, complete or unknown) and how certain the outcome is. Workaround words and queue WHY text are never echoed beyond the key and the line number. An unknown key in `use` names the attempted operation and the sanitized key and lists the known keys or says to ask the owner; a duplicate key names the existing line and the reuse command; an unknown slug in `order` names it and lists the queued slugs. An unexpected failure exits non-zero with its own code (SCHED-E99), the phase, the certainty, a compact sanitized trace (or with `LOOP_DEBUG` set the trace file's path), a safe next action and a retry bound; an uncertain remote effect is reconciled before any retry.

### Signatures
- `load(root) -> result` (goals in order with kind, task, priority, reason, held, workaround mark, strings; diagnostics; `incomplete`); `eligible(goal, result) -> (ok, reason)`.
- CLI: `workaround add|use|fail|close|reconcile|list`, `order SLUGS --by RECORD | --clear`, `show`. Exit 0 on success, 2 on a refusal, 3 on an incomplete read.
- Queue key (optional, additive): `first: TASK_SLUG: WHY` or `first: safety: CLASS`. Brief line (optional, additive): `- Priority: N`. Setting: `schedule_policy` (on or off).

### Hooks and byte rule
Each existing consumer replaces its own queue parser with one call to the loader, so every script gets smaller, never larger; every script that is over 19,000 bytes stays at or below its current size, none that was under it crosses it, and none passes 20,480. Where a consumer's parser is shared with other callers, the shared function moves whole and unchanged into the loader with a test that calls it from there, and its old name stays importable where a toy imports it. No hook is paid for by trimming or reformatting (TD1026). The behaviour-neutral move is proved, not assumed: for each consumer a golden comparison runs the old parser's output against the loader's on the same inputs, including malformed lines, comments, unknown keys and the keys other callers use, and the policy off switch returns today's order. The build writes the per-consumer table (before coding) and the real before and after bytes in the PR notes; the size row asserts per file.

### Tests (each a real test linked to its requirement; each passes and fails on a fixture that breaks only its rule)
TSK-1.1: with a ready task goal and a ready patch goal that does not block it, the slot goes to the task goal and the frozen record names the reason; with the order function replaced by file order the same fixture picks the patch. Ties go by priority, then closest to merging. Creation to dispatch with `--release` and no hand-written metadata; a patch brief, a brief of an unselected release, a release disagreement, R unset and briefs matching no line each give the stated result and diagnostic.
TSK-1.2: a fix that blocks a queued task goal sorts ahead and names it; a fix with an activated workaround for that goal, or with no reason, sorts behind; a `first: safety:` fix sorts first of all, above an owner order; the owner line is an accepted reason; a `first:` naming an unqueued goal is ignored with the three visible warnings; an overdue fix shows its count and its close command.
TSK-1.3: the first goal to hit a bug records a workaround and opens exactly one issue, also when `add` is interrupted after the pending line or after the issue, with a lost creation response, with a changed goal list and on a concurrent second `add` and concurrent `reconcile`; the unknown lookup outcome creates nothing; a secret-shaped value reaches no file, issue body, stdout, stderr or trace; the second `use` returns the same words without a second issue; a pending, an unused and a refused-use record leave the task goal waiting, an activated one starts it through a real freeze and assignment while the fix is unmerged, a failed or closed one restores the wait, a `dependency` is never waived; words that skip a safety item or fail the safety checks at use time are refused.
TSK-1.4: the probe result recorded; main red on one row, a pull request green with no new red, the real merge entry point merges; red on a row that is green on main, or a safety class, still refuses; the known-red allowance has its own cases; batch eligibility and individual merge are told apart.
TSK-1.5: the four consumers show each goal marked task or fix with the exact strings and the fixed cell order (one fixture with every mark, byte for byte, and no WHY text anywhere) and agree with `show`, the start path's freeze and the frozen record; the owner line moves a fix behind or ahead as written, an unknown record refuses before writing, stale slugs are pruned with one line; with no briefs every board prints today's text byte for byte; the policy off switch returns file order.
Unreadable input: a malformed brief, workaround record, order file and queue line each give the stated diagnostic code, the conservative behaviour (a malformed brief with valid safety and owner order keeps both), the banner on the boards and the check-in, stderr and exit 3 from every command line consumer and `incomplete` in the JSON; a torn file reads as unreadable; `order --clear` works on a malformed file and the hold clears; a lock timeout refuses with no write and a stale lock is broken. Done line 3 is covered by the existing size, no-loosened-test, no-red-row and private-name checks, plus the byte checks above.

### NOT in scope
A change to the release workflow's publishing hold; a classification of goals beyond task and fix; automatic detection of a tool bug (the operation names it); a priority for fixes; a new wiki page (the text goal owns the TSK page); any change to how pull requests are ordered for merging; any edit to a merge-gate script.

### Decisions (the planner's, for review)
1. Priority is an optional line in the task brief, not a new file: additive, and a brief without it keeps today's behaviour.
2. The workaround record and the owner order live in the git common directory's loop folder next to run records, because text there never merges and the touch list has no tracked state files. State is local to the operating machine, which is how run records already work; one operation session owns it.
3. A fix is "ahead" only for a stored reason, written as text on the goal, so the boards never invent one.
4. TSK-1.4 is a proof by test, not a new gate: the merge path already goes on a green PR run, and a new hold would add the thing the requirement removes.
5. One loader for every reader removes the hooks, fixes the byte problem by shrinking scripts and makes start order, boards and `show` agree by construction.
6. Only an activated workaround waives; recording one never does.

### Alternatives weighed and set aside
Sorting inside the start path only (the boards would disagree with it). A smaller key made only of the owner-order verb (the requirement text asks for tasks first with ties by priority and closeness to merge). Splitting the loader move and the policy into two goals (kept as one: the done lines and the done check cover the whole behaviour; the policy off switch and the golden comparison give the same safety, and the first-pull-request fallback in "Depends on" remains if the sibling order cannot be kept). A priority for every goal. A daemon that reorders on its own. Proving that task-first improves release completion before building (the owner reviewed the requirement; the metric is minutes a ready task goal waits behind a non-blocking fix, and the start path logs it for each start).
