# Plan: v110-tsk-1, the operation schedules the owner's tasks ahead of fixes to its own tools

## Implementation plan

Goal: when the operation picks the next goal for a worker, a goal from a task in the owner's selected release brief comes before a fix, patch or tool goal; a fix goes first only on a named reason; a tool bug that hits a task goal uses a recorded workaround at once, which really frees the task goal to start, while the real fix queues behind the task goals; a red main that is red only on rows that pass on PR runs does not stop task merges; and the board shows the schedule in order, each goal marked task or fix, with the reason any fix is ahead and one owner line to reorder it. The requirement text is the reviewed TSK-1 unit (TSK-1.1 to TSK-1.5), copied from the owner-approved reworded features file by name; its words are not changed here.

Size of the change: medium. One new module holds the logic and is the single place that reads the queue, the briefs and the two small state files; each existing queue reader calls it and drops its own parse, so every hook shrinks its script; one new toy proves the five requirements; one new row is added to the regression table. No existing script grows, and none crosses a size line.

### Depends on (order)
The text goal for tasks 12 to 14 merges first, so the TSK page exists on main when this goal's rows are merged. Nothing else is required: the queue, the task briefs and the board already exist. v110-fast-clock and v110-fast-steps-2 are independent; whichever lands second re-measures bytes after its own merge-up.

### What exists
- The queue is one tracked file with one line per goal. Several readers each parse it on their own (the start path, the monitor plan, the board status used by the board and the check-in, the JSON board, the replan view) and all take the goals in file order. The start path fills the free worker slots in that order. A goal waits only for a dependency, an assigned session, full slots or low memory, and each wait already has a reason that the boards print.
- Task briefs (one file per task, from the task-list goal) name the goals that carry each task out, name the release they belong to, and have a state. Nothing marks a queued goal as a task goal or a fix, nothing carries a priority, and no tool bug leaves a record.
- The boards print the queue as numbered rows ("N. slug | waits for ... | ETA") and a "Queued goals" section; the check-in and the JSON board project the same queue items.
- A merge goes ahead once the required checks on the pull request's own head are green; a check that is red only on rows already known red on main is let through. The release workflow has its own hold for publishing. TSK-1.4 is a statement about this existing path.
- One queue-reading script is already above the 19,000-byte line (below the 20,480 hard line); the others sit within a few dozen bytes below it. Real per-file sizes are re-measured at build and written in the PR notes; a script that is over the line may only shrink.

### Design (A to H)
A. One shared loader. `schedule.load(root)` is the only reader of the queue lines, the task briefs, the owner order and the workaround record. It returns one result: the goals in schedule order, each with its kind (`task` or `fix`), task name, priority, an order reason (text), a held reason when one applies, and a list of diagnostics plus an `incomplete` flag. Every consumer calls it and drops its own parse: the start path, the monitor plan, the board status (and through it the board and the check-in), the JSON board and the replan view. Because each consumer's own queue parser moves into the loader, each hook is a net shrink (a function larger than the call that replaces it). The start path, the boards and `show` read the same result, so they cannot disagree; a toy asserts that agreement for every consumer, including the JSON board and the check-in projections, and that the frozen run record carries the kind and reason.
B. Classification (TSK-1.1). A task goal is a queued goal whose line carries release R (the owner's selected release) and that is listed in a live, non-replaced task brief whose release line is R and that is not a patch brief. Patch briefs, briefs of other releases and replaced briefs make nothing a task goal. A goal listed in more than one brief takes the selected-release brief; two selected briefs with different priorities resolve to the lower number, then the brief's file name; the resolution is named in the goal's reason. Everything else is a fix. A brief may carry one optional line `- Priority: N` (a whole number; lower first); a brief without it is still valid and sorts by file name.
C. Order. The order key of a queued goal is: safety goal, then owner order, then a fix that blocks a queued task goal, then task goals before fixes, then the brief's priority, then the goal closest to its merge (fewest unmet dependencies), then queue-file order. Safety sorts above owner order, so an owner line can never bury a safety fix; when a safety goal would sit behind an owner-ordered one the loader prints a loud line naming both. The sort is stable, so a repo with no briefs and no other input gets exactly today's order. The seven-level key is kept as planned (the review's challenge was weighed and set aside; see Alternatives).
D. A fix goes first only on a named reason (TSK-1.2). A fix may sort ahead of a task goal only for one of three stored reasons: it blocks a queued task goal (that goal depends on it directly or through other goals) and no workaround covers that goal; it carries the optional queue key `first: TASK_SLUG: WHY` naming the blocked goal and why no workaround fits; or it carries `first: safety: CLASS` naming a class on DLF-1.3's safety list (a deletion, money, security, private data, a steward merge, a leak, a loosened test). A fix with none of these stays behind the task goals and its row says "after task goals". A `first:` that names a goal that is not queued is ignored, and one warning line says so on stderr, in the frozen run record and in `show`'s list of ignored keys. A fix passed over by more than five task goals, or whose workaround is older than seven days or used by more than three goals, is shown as overdue on the board with its count or age, and its workaround gets a review date shown by `workaround list`.
E. Workarounds (TSK-1.3). A record outside the repo's tracked files (under the git common directory's loop folder, next to run records) holds one line per tool bug: a key, the queued fix goal it belongs to, the goals it applies to, whether the bug is a tool obstruction or a mandatory dependency, the workaround words, the first goal, the issue number, the review date and a state (`pending` or `done`). `schedule.py workaround add KEY --fix SLUG --applies GOALS "words"` requires the fix to be a queued or running goal. It writes a `pending` line first, then files the one issue through the existing finding command (which already dedupes on a title hash), then marks the line `done` with the issue number; a repeated `add` of a pending key reconciles first by looking up the existing issue and never files a second one, and automatic retries stop after three with a refusal that prints the reconcile command. `workaround use KEY --goal SLUG` first checks applicability (the goal is in the record's list and the key is a tool obstruction, never a mandatory dependency), then runs the words through the existing safety checks the operation already applies (decision kinds, risky paths, always-ask), then records the use and prints the words; the stored words are text for the session to read, never run by this module. A recorded workaround changes scheduling: for a goal it applies to, the named fix no longer counts as blocking it and its wait on that fix is waived, while any other real prerequisite stays. The toy proves that the task goal is selected and resumes while the fix is still unmerged. `add` refuses words that skip anything on the DLF-1.3 list, naming the word and the class.
F. A red main does not stop tasks by itself (TSK-1.4). Nothing in the merge path is changed. The toy drives the real merge entry point and its real gate (no stand-in for the gate in the stub or the CI helper) on a repo whose main run is red on one row and a pull request that is green on every required check with no new red; it merges, and the toy distinguishes a batch's eligibility from an individual merge. Separate cases cover the known-red allowance. Negative controls: a red that reaches the pull request's own run, and a pull request that touches a safety class, are refused, and the safety case names the real approval boundary it exercises; if that boundary does not exist for the case, the toy reports the absence plainly and the build stops before any gate file is edited. Merge-gate files this goal touches: none is edited; the toy reads the merge command, the automatic-release gate and the known-red list.
G. See and change the order (TSK-1.5). The queue view and the live board, and the check-in and JSON projections, add after the slug cell a `task NAME` or `fix` mark and, for a fix ahead of a task goal, the reason from D; a fix behind the task goals says so; overdue fixes show their count or age. The marks are left out when the repo has no task briefs, so every existing board fixture prints byte for byte what it prints today. One owner line reorders: `schedule.py order SLUG [SLUG ...] --by RECORD` validates that RECORD is a real owner record through the existing owner-record lookup (an unknown or out-of-scope record refuses before anything is written), then writes the order file; those goals sort after safety goals and before everything else, the board shows "ordered by owner (RECORD)", slugs that are merged or unknown are pruned on read with one printed line, and `schedule.py order --clear` removes it.
H. Unreadable input fails safe and visible. An absent optional file is normal. An unreadable or malformed one (a brief, the workaround record, the order file, the queue line itself) is never read as "nothing": the loader marks the result `incomplete` and records which input and why. Dispatch is conservative per input: an unreadable brief set leaves the queue in file order and names the problem; an unreadable workaround record assumes no workaround; an unreadable owner order holds new starts with the reason named, because the owner's order is authoritative and guessing could invert it. `show` exits 3 when any input was skipped, prints each skipped input and cause on stderr, and the JSON board carries `incomplete: true`. Both state files are written by writing a temporary file and renaming it, under a short lock with a bounded wait, so a reader never sees a torn file; a torn or partial file reads as unreadable and is handled as above.

### Signatures
- `load(root) -> result` (goals in order, each with kind, task, priority, reason, held; plus diagnostics and `incomplete`); pure apart from reading; stable.
- CLI: `workaround add|use|list`, `order SLUGS --by RECORD | --clear`, `show`. Exit 0 on success, 2 on a refusal, 3 on an incomplete read.
- Queue key (optional, additive): `first: TASK_SLUG: WHY` or `first: safety: CLASS`.
- Brief line (optional, additive): `- Priority: N`.

### Errors, agent-ready
Every refusal prints one line to stderr with a stable code (SCHED-E01 and up, each with an anchor in the monitoring skill's command reference), what happened, the fix, the recovery, the side effects (none, partial, complete or unknown) and the channel. Workaround words and queue WHY text are never echoed beyond the key and the line number. An unknown key in `use` names the attempted operation and the sanitized key, and lists the known keys or says to ask the owner; a duplicate key names the existing line and the safe reuse command; an unknown slug in `order` names it and lists the queued slugs; the retry-bound refusal names the reconcile command. An unexpected failure exits non-zero, prints a compact sanitized trace and the effective context, or with `LOOP_DEBUG` set the trace file's path, and says what was and was not written.

### Hooks and byte rule
The new module is one new file under skills/, within the file count the package allows, stdlib only, sibling imports only, answering `--help` alone. Each existing consumer replaces its own queue parser with one call to the loader, so every script gets smaller, never larger; the script that is already above 19,000 bytes stays at or below its current size. Where a consumer's own parser is shared with other callers, the shared function moves whole and unchanged into the new module with a test that calls it from there, and its old name stays importable where a toy imports it. No hook is paid for by trimming or reformatting (TD1026). The build writes the real before and after bytes of every touched script in the PR notes; no script crosses 19,000 that was under it, none passes 20,480, and a size row proves it.

### Tests (each a real test linked to its requirement; each passes and fails on a fixture that breaks only its rule)
TSK-1.1: with a ready task goal and a ready patch goal that does not block it, the slot goes to the task goal and the frozen record names the reason; with the order function replaced by file order the same fixture picks the patch. Ties go by priority, then closest to merging. A patch brief and a brief of an unselected release make nothing a task goal; overlapping briefs resolve as written.
TSK-1.2: a fix that blocks a queued task goal sorts ahead and names it; a fix with a recorded workaround for that goal, or with no reason, sorts behind; a `first: safety:` fix sorts first of all, above an owner order; a `first:` naming an unqueued goal is ignored with the three visible warnings; an overdue fix shows its count.
TSK-1.3: the first goal to hit a bug records a workaround and opens exactly one issue (also when `add` is interrupted after the line or after the issue, and on a concurrent second `add`); the second `use` returns the same words without a second issue; with the workaround recorded the blocked task goal is actually selected and starts while the fix is unmerged, and a mandatory dependency is never waived; a workaround that skips a safety item, or fails the existing safety checks at use time, is refused.
TSK-1.4: main red on one row, a pull request green with no new red, the real merge entry point merges; red on a row that is green on main, or a safety class, still refuses; the known-red allowance has its own cases; batch eligibility and individual merge are told apart.
TSK-1.5: the queue view, the live board, the check-in and the JSON board show each goal marked task or fix with the reason and agree with `show` and with the start path; the owner line moves a fix behind its task goal, an unknown record refuses before writing, and stale slugs are pruned with one line; with no briefs every board prints today's text byte for byte.
Unreadable input: a malformed brief, workaround record, order file and queue line each give a diagnostic, the stated conservative behavior, exit 3 from `show` and `incomplete` in the JSON; a torn file reads as unreadable. Done line 3 is covered by the existing size, no-loosened-test, no-red-row and private-name checks, plus the byte checks above.

### NOT in scope
A change to the release workflow's publishing hold; a classification of goals beyond task and fix; automatic detection of a tool bug (the operation names it); a priority for fixes; a new wiki page (the text goal owns the TSK page); any change to how pull requests are ordered for merging; any edit to a merge-gate script.

### Decisions (the planner's, for review)
1. Priority is an optional line in the task brief, not a new file: additive, and a brief without it keeps today's behaviour. Alternative: the brief's file order.
2. The workaround record and the owner order live in the git common directory's loop folder, next to run records, because text there never merges and the touch list does not include tracked state files. Clone-local state is a stated limit: one operation session on one machine owns it, which is how run records already work. Alternative: a tracked file; set aside because a workaround for one goal must not be a tracked change in another.
3. A fix is "ahead" only for a stored reason; the reason is text on the goal, so the board never invents one.
4. TSK-1.4 is a proof by test, not a new gate: the merge path already goes on a green PR run, and a new hold would add the thing the requirement removes.
5. One loader for every reader (the review's main structural finding): it removes five hooks, fixes the byte problem by shrinking scripts, and makes start order, boards and `show` agree by construction.

### Alternatives weighed and set aside
Sorting inside the start path only (the boards would disagree with it). A smaller key made only of the owner-order verb (the requirement text asks for tasks first, ties by priority and closeness to merge, so the owner verb alone does not meet TSK-1.1). A priority for every goal (the brief names the tasks, everything else is a fix). A daemon that reorders on its own (the owner's line is the one way to change the order). Proving that task-first improves release completion before building (the owner reviewed the requirement; the metric is minutes a ready task goal waits behind a non-blocking fix, and the board shows it).

### Revisions after the first review round
The first review round (CEO, DX and Eng, two voices each) found: a wrong byte premise, more queue readers than planned, classification from any brief instead of the selected release, owner order above safety, workarounds that did not free a task goal, unreadable input read as success, an unrecoverable two-step write, no locking, no stable error codes or example, a safety control with no named boundary, and no starvation or aging rule. This text carries all 36 accepted fixes (design A to H, the error section, the hooks section and the tests); the four challenges to the plan's direction were kept as stated.

### Risks
Byte room is the dominant risk: each consumer must really shrink, and the script already above the line may only shrink. Existing board fixtures must stay byte for byte (marks omitted with no briefs). A brief priority line must not make the task list flag a brief as incomplete. Classification depends on the release lines of real briefs, which the build reads before coding. A new toy and row must run inside the row time limit. The safety negative control depends on a real approval boundary existing; if it does not, the plan says to report that and stop.
