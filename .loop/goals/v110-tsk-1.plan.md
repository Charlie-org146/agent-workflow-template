# Plan: v110-tsk-1, the operation schedules the owner's tasks ahead of fixes to its own tools

## Implementation plan

Goal: when the operation picks the next goal for a worker, a goal from a task in the owner's release brief comes before a fix, patch or tool goal; a fix goes first only on a named reason; a tool bug that hits a task goal uses a recorded workaround at once while the real fix queues behind the task goals; a red main that is red only on rows that pass on PR runs does not stop task merges; and the board shows the schedule in order, each goal marked task or fix, with the reason any fix is ahead and one owner line to reorder it. The requirement text is the reviewed TSK-1 unit (TSK-1.1 to TSK-1.5), copied from the owner-approved reworded features file by name; its words are not changed here.

Size of the change: medium. One new module holds the logic; five existing scripts each get a one-line hook; one new toy proves the five requirements; one new row is added to the regression table. No existing script grows past its size line.

### Depends on (order)
The text goal for tasks 12 to 14 merges first, so the TSK page exists on main when this goal's rows are merged. Nothing else is required: the queue, the task briefs and the board already exist. v110-fast-clock and v110-fast-steps-2 are independent; whichever lands second re-measures bytes after its own merge-up.

### What exists
- The queue is one tracked file with one line per goal. Every reader of it takes the goals in file order, and the start path fills the free worker slots in that order. A goal waits only for a dependency, an assigned session, full slots or low memory, and each wait already has a reason that the board prints.
- Task briefs (one file per task, from the task-list goal) name the goals that carry each task out, and each task has a state. Nothing marks a queued goal as a task goal or a fix, nothing carries a priority, and no tool bug leaves a record.
- The board prints the queue as numbered rows ("N. slug | waits for ... | ETA") and the live board prints a "Queued goals" section. Both read the same queue items.
- A merge goes ahead once the required checks on the pull request's own head are green; a check that is red only on rows already known red on main is let through. The release workflow has its own hold for publishing. TSK-1.4 is a statement about this existing path.

### Design (A to E)
A. Classification and order (TSK-1.1). A new module `schedule.py` reads the task briefs and returns, for each queued goal, a kind (`task` when a live, non-replaced brief lists the goal, else `fix`), the task's name and its priority. The order key of a queued goal is: owner order first (E), then a safety goal (B), then a fix that blocks a queued task goal (B), then task goals before fixes, then the brief's priority (lower first; a brief with no priority line takes its place by file name), then the goal closest to its merge (fewest unmet dependencies), then queue-file order. The sort is stable, so a repo with no briefs and no other input gets exactly today's order. The order is applied once, where the three queue readers finish parsing, so the start path, the monitor plan and the board all follow it and cannot disagree.
B. A fix goes first only on a named reason (TSK-1.2). A fix goal may sort ahead of a task goal only for one of three reasons, each stored with the goal as text: it blocks a queued task goal, meaning that goal depends on it directly or through other goals, and no workaround is recorded for the tool bug; it carries one optional queue key `first:` that names the blocked task goal and why no workaround fits; or it carries `first: safety: CLASS` naming a class on the safety list of DLF-1.3 (a deletion, money, security, private data, a steward merge, a leak, a loosened test). A fix with none of these keeps its place behind the task goals and its row says "after task goals". `first:` is read by the new module straight from the queue line; the parser's other keys are unchanged.
C. Workarounds (TSK-1.3). A record outside the repo's tracked files (under the git common directory's loop folder, next to the run records) holds one line per tool bug: a key, the workaround words, the first goal that used it, the issue number and the date. `schedule.py workaround add KEY "words" --goal SLUG` writes the line and files the one issue through the existing finding command; a second `add` with the same key is refused, naming the line. `schedule.py workaround use KEY --goal SLUG` prints the words and appends the goal, so the second goal to hit the same bug uses them without asking while the fix stays queued behind the task goals. `add` refuses words that skip anything on the DLF-1.3 list (skipping a check, a scan or a test, loosening a test, deleting one), exiting non-zero with a one-line refusal. The operation session runs these commands; the no-model loop does not.
D. A red main does not stop tasks by itself (TSK-1.4). Nothing in the merge path is changed. A toy builds a repo whose main run is red on one row, a pull request whose own run is green on every required check with no new red, and runs the merge command's gate on it; it merges. Negative controls: a PR run that is red on a row that passes on main, and a PR that touches a safety class, are still refused. The plan names the merge-gate files the toy reads (below) so a later change to one of them cannot silently break the proof.
E. See and change the order (TSK-1.5). The queue view and the live board add, after the slug cell, a `task NAME` or `fix` mark and, for a fix ahead of a task goal, the reason from B; a fix behind the task goals says so. The marks are left out when the repo has no task briefs, so every existing board fixture prints byte for byte what it prints today. One owner line reorders: `schedule.py order SLUG [SLUG ...] --by RECORD` writes an order file next to the workaround record (slugs, the owner's record id, the time); those goals sort before everything else, the board shows "ordered by owner (RECORD)", and `schedule.py order --clear` removes it. A reorder that moves a fix behind its task goal is the "moves it back" case in the test.

### Signatures
- `kinds(root) -> {slug: (kind, task name, priority)}`; `order(goals, kinds, owner, first) -> ordered goals`, pure and stable; `why(goal) -> text or ""`.
- `workaround add|use|list`, `order SLUGS|--clear`, `show` (prints the schedule with its reasons). Exit 0 on success, 2 on a refusal with one line.
- Queue key (optional, additive): `first: TASK_SLUG: WHY` or `first: safety: CLASS`.
- Brief line (optional, additive): `- Priority: N` (a whole number; lower first). A brief without it is unchanged and still valid.

### Errors, agent-ready
Every refusal prints what, the fix and the recovery on one line: an unknown slug in `order` names it and lists the queued slugs; a `first:` that names a goal that is not queued is shown as "first: names an unknown goal X" on the board and is ignored for ordering; a duplicate workaround key names the existing line; a workaround that skips a safety item names the word and the class. A brief or record file that cannot be read gives one note and the rest of the schedule still prints (the existing task-list rule: a bad brief is named, never hidden).

### Hooks and byte rule
The new module is one new file under skills/, within the file count the package allows. Five existing scripts get a one-line call each (the start-path reader, the monitor reader, the board-status queue reader, the queue view and the live board section); every one of them is within a few dozen bytes of the 19,000 line, so each hook is paid for by moving one whole function, unchanged, into the new module or the task-list module, with a test that calls the moved function from its new home and one that shows the old name is still importable where a toy imports it. No script crosses 19,000 and none passes 20,480; a size row proves it. No hook is paid for by trimming or reformatting.

### Tests (each a real test linked to its requirement; each passes and fails on a fixture that breaks only its rule)
TSK-1.1: with a ready task goal and a ready patch goal that does not block it, the slot goes to the task goal and the record names the reason; with the order function replaced by file order the same fixture picks the patch. Ties go by priority, then closest to merging.
TSK-1.2: a fix that blocks a queued task goal sorts ahead and names it; a fix with a recorded workaround, or with no reason, sorts behind; a `first: safety:` fix sorts first of all; a `first:` naming an unqueued goal is ignored and shown.
TSK-1.3: the first goal to hit a bug records a workaround and opens one issue; the second `use` returns the same words without a second issue and the fix stays queued behind the task goals; a workaround that skips a safety item is refused.
TSK-1.4: main red on one row, a pull request green with no new red, the merge goes ahead; red on a row that is green on main, or a safety class, still refuses.
TSK-1.5: the queue view and the live board show each goal marked task or fix with the reason; the owner line moves a fix behind its task goal; with no briefs both boards print today's text byte for byte; `show` and the board agree.
Done line 3 is covered by the existing size, no-loosened-test, no-red-row and private-name checks, plus the byte checks above.

### NOT in scope
A change to the release workflow's publishing hold; a classification of goals beyond task and fix; automatic detection of a tool bug (the operation names it); a priority for fixes; a new wiki page (the text goal owns the TSK page); any change to how pull requests are ordered for merging.

### Decisions (the planner's, for review)
1. Priority is an optional line in the task brief, not a new file: additive, and a brief without it keeps today's behaviour. Alternative: the brief's file order. Chosen the line because a priority that has to be read from a file name is invisible.
2. The workaround record and the owner order live in the git common directory's loop folder, next to run records, because text there never merges and the touch list does not include tracked state files. Alternative: a tracked file under the repo's loop folder; set aside because a workaround for one goal must not be a tracked change in another.
3. A fix is "ahead" only for a stored reason; the reason is text on the goal, so the board never invents one. Alternative: compute blocking from the dependency graph alone; set aside because a tool bug that stops every merge is not a dependency.
4. TSK-1.4 is a proof by test, not a new gate: the merge path already goes on a green PR run, and a new hold would add the thing the requirement removes.

### Alternatives weighed and set aside
Sorting inside the start path only (the board would then disagree with the start order); a priority for every goal (the brief names the tasks, everything else is a fix); a daemon that reorders on its own (the owner's line is the one way to change the order).

### Sources quoted word for word
The reviewed TSK-1 unit and its five requirements; the owner's priority ruling of 2026-11-23 (tasks 12 to 14 first) and the deliver-first rule; DLF-1.3's safety list, quoted by class name only. All are cited by file name in the owner-approved reworded features file.

### Risks
Byte room is the dominant risk: five hooks each need a moved function and a test that it still works from its new home. Existing board fixtures must stay byte for byte (the marks are omitted when there are no briefs). A brief priority line must not make the task list flag a brief as incomplete. A new toy and row must run inside the row time limit.
