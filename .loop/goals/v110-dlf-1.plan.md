# Plan: v110-dlf-1

## Implementation plan

Design: .loop/designs/v110-dlf-1.md (Approach A: one stop table, one ledger function, one budget rule). Requirement text: the
owner-approved DLF-1 unit in reviewed-features-2026-11-23-reworded-DRAFT.md (DLF-1.1 to DLF-1.5). The goal's three done lines
are frozen and met as written: (1) each DLF-1 case is a real linked test, passing, and red on a fixture that breaks only that
rule; (2) the budget raises to measured spend plus the estimate of what is left, capped at 2x the goal's estimate, logged with
old and new figures, one owner line past the cap while the goal keeps working at the cap; (3) package checks hold.

Build blocks, in order (each toy is written red first, then the code that turns it green):

1. **The stop table.** One small data table in the delivery skill classifies a stop by its SUBJECT: safety-list subjects wait
   (the safety classes, a change to what a feature promises, a loosened or deleted test, private data), everything else
   becomes a line; an unclassifiable stop waits (fail closed); the board names the class of every wait. The leak read and the
   full GitHub run stay gates, never stops this table can turn into lines. Test: a case per row plus an unclassifiable case.
2. **The ledger routine.** One function files a line on the release's single deliver-first issue (created at the first line)
   as a checklist item: goal, which of the five stops, the exact settle words, a recommendation, a state (open, accepted,
   converted). It returns a line id, which the goal records on its run record before it continues. Tests use the fake GitHub
   client the other toys use, in a temp home, never the real one.
3. **Wire the five stops** through the table: a red-team break at the plan gate, a plan past its review cap, a budget the goal
   has outgrown, a test failing outside the goal's own rows, an open design choice in a step reply. Each former stop now calls
   the routine and continues, unless the table says it waits. Fixture per stop: the stop still waits (red), then continues
   with one line (green). A safety subject (a loosened test) still waits and the board says why.
4. **The budget rule.** A single function: new budget = measured spend + the estimate of what is left, never above 2x the
   goal's estimate; the estimate of what is left is the goal's estimate minus the estimate share of the steps already recorded
   done (never the spend on them). A raise inside the cap is logged with the old and new figures and files no line; past the cap the goal keeps working
   at the cap and exactly one line asks the owner. Used wherever the time or token budget is checked. Test: 240 of 240
   with 100 left goes to 340 and the log shows both figures; a goal needing more than the cap stays at the cap with one line.
5. **The release cut.** The cut reads the ledger and refuses while any line is open: it prints the whole list once, grouped by
   goal, each line with its recommendation, plus one accept-all line. A line not accepted becomes a patch goal (queued by the
   release step); a converted line keeps the cut refused until its patch goal has merged. Test: three goals, five open lines,
   cut refused with one list of five plus one accept-all line; a converted line holds the cut until its patch goal merges.
6. **The setting.** One setting, scopes goal, task and release, default on, written only with a recorded owner reference;
   scopes nest and the most specific value wins. Test: off for one goal, its first break waits and the others' do not; release
   off, one task on, one goal off inside it: the goal waits, the task's other goals do not, the release's other tasks wait;
   a change with no owner reference is refused.
7. **Rows.** Each DLF-1 case is a regression row linked to its requirement id (DLF-1.1 to DLF-1.5), each backed by a toy with
   a red fixture that breaks only that rule and a negative control (the same toy passes on the unbroken code). Added to the
   regression rows file in the same change.

Placement and size: new code goes where the existing stop, budget and cut code lives, plus the toys; no new file under the
package unless one is removed; every script touched stays under the size rules (the build measures headroom first and trims
or moves code rather than crossing a cap; if a needed change cannot fit, the goal stops and reports before building it).
No test is loosened; no row turns red; committed text never names the service repo.

Evidence: the pull request's full GitHub run is the merge evidence; the toys above run in temp homes; no local test lane.

Risks: (a) a stop site the table does not list is found at build: it is added to the table with a case, never left out;
(b) a safety subject misclassified as a line: the table is data pinned by tests and every row has a red fixture;
(c) the cut reading a ledger that does not exist yet: a release with no issue is clean, and the read is tested both ways.

- BINDING (this block replaces any conflicting statement in the plan above): the seven build blocks stay, refined as follows.
- Subjects. Every stop site sets a mandatory `subject` from one fixed list: the safety subjects (deleting what cannot be restored, money, security and sandbox settings, private data, steward merges, a change to what a feature promises, a test loosened or deleted) or `other`. The subject is derived mechanically, never from the agent's own label: the table's rules read the paths the diff touches, the settings files it changes and secret patterns (the path and pattern lists are part of the table, pinned by fixtures), and the agent's label may only raise a stop to a safety subject, never lower one the rule found. Each site's rule is written in the table and pinned by that site's fixture (a red-team break takes its recorded class; a test failure is a loosened or deleted test when the diff removed or weakened an assertion, else `other`; a design choice is a promise change when it names what a feature promises). A second check scans the stop's text for the safety subjects' words (the word list is part of the table and pinned by a fixture) and forces a wait when a stop labelled `other` hits one; the exemption holds only for a text built from the table's own template with no free-text field, and a fixture pins that any free-text field in it is scanned. A missing or unknown subject is unclassifiable and waits. One red fixture per safety subject. The leak read before any push and the full GitHub run before a merge are gates, not subjects.
- What continuing means, per stop: a red-team break is recorded as unresolved on its line and the plan proceeds; a plan past its review cap proceeds with the current plan and a line; an open design choice takes the recommended answer and the line records the option chosen; a test failing outside the goal's own rows files a line and the goal keeps building, while merge stays gated on the full GitHub run so a real red never merges; a failure that is itself a loosened or deleted test is a safety subject and waits; a budget past the cap works at the cap (below).
- Line key and states. A line is keyed by (goal, stop, subject, occurrence), the occurrence being the id or content hash of the break, choice or failing test, so three breaks in one goal are three lines (a plan past its cap and a budget past the cap each have one occurrence per goal); filing finds or creates by that key, so a resumed goal files no second line and a crash between filing and recording the id is repaired by the key. The release issue is found by its release label before it is created, so two goals never make two issues. States: open, accepted, converted, closed. Transitions: open to accepted (the owner's accept, one line or accept-all); open to converted (the owner's decline, or the release step on a recorded decline, which queues the patch goal at that moment); converted to closed (the patch goal has merged); accepted to closed (at the cut); a cap line is an ordinary line and closes the same way. Both accept channels and the decline require a recorded owner reference; the cut ignores any tick or comment without one (red fixture). The cut refuses while any line is open, converted or still queued unfiled.
- When the issue cannot be reached: a stop that waits by subject keeps waiting; a line for a stop that would continue (including the cap line) is queued in the goal's run record, the goal keeps working, filing retries at the next step and at the cut. Every text posted to the issue passes the private-name scan first.
- Budget. Old budget is the budget held for the goal (the margin-inclusive ETA in minutes when the goal has no value of its own); the estimate is the goal's recorded estimate before the margin; remaining = the estimate of the steps not yet recorded done (the goal's estimate minus the estimate share of the steps recorded done, never the spend on them; floor 0); new budget = max(old budget, min(spend + remaining, 2 x estimate)). A goal whose recorded-done steps already cover the whole estimate (remaining 0) and is not finished gets a floor of 25% of the estimate as remaining, so held 360 with a 288 estimate and 360 spent gives max(360, min(360 + 72, 576)) = 432. The cap line is filed only when spend has reached 2 x estimate (the cap): the goal then files its one cap line, works at the cap: the cap binds, spend is held there and no further raise is made, and the cap line is found by its key so the stop never re-fires. Inside the cap no line is ever filed. A token budget uses the same rule on its own estimate, or on the repo's token budget when the goal records none. Fixtures: 240 spent with steps worth 140 of the estimate recorded done and a 240 estimate gives 340 with both figures logged; remaining 0 with held 360, estimate 288, spend 360 gives 432 and no line; spend at or above 2 x estimate files exactly one cap line and holds the budget at the cap. A budget outgrown in DLF-1.1 means past the cap.
- Setting. With it off for a scope, that scope's stops (the budget stop included) wait for the owner as today, because DLF-1.5 returns that scope to today's behaviour; the frozen budget line describes the default (on). Scopes nest goal, task, release; the most specific value wins.
- What waits, named: the safety subjects; a stop that cannot be classified; a waiting stop whose issue cannot be reached; a scope whose setting is off. Each is named on the board; nothing else waits for the owner. A size stop or a failed premise halts the build at one block (never the merge path of another goal) and files one line.

The first build task records each touched script's headroom and names the host script of each block; toys are not shipped and have no per-file cap; only these extras may be split into a follow-up goal when they cannot fit, with a line: local queueing of unreachable lines, the token fallback (the second word-scan check is NOT an extra: it is the fail-closed check and ships with block 1; the release-label lookup is NOT an extra: it is part of block 2, because DLF-1.1's one issue and DLF-1.4's one list across goals depend on it; the fallback if the lookup cannot be built is the release's issue number recorded in the queue data and read by every goal); any block that a DLF-1 case or a done line needs that cannot fit stops the goal at that block with one line and a report that the done lines are unmet (the owner decides at the release).
- Premises are checked first and recorded in the build brief: each stop site, the fake client the toys use, that goals belong to tasks belong to releases in the queue data, that the page carrying DLF-1.1 to DLF-1.5 exists; a failed premise stops the goal at the block that depends on it and files one line.

- Release issue: created once, by the first filing; after creating, the goal re-lists by label across all pages and keeps the lowest issue number, posts there, and closes its own duplicate. A lookup that fails or whose pages are incomplete is never read as "no issue": the filing is queued (a stop that would wait keeps waiting). Fixture: two goals creating at once end with one open issue.
- Filing: every comment carries a hidden marker with its line key; lookup paginates fully and the earliest comment for a key wins; the occurrence is the stable break, choice or test id, never a hash of reworded text; after an ambiguous write (timeout after a possible success) the goal re-reads by key before posting again. Fixtures: concurrent same-key filing, a post followed by a timeout.
- States are event comments: each transition is an append-only comment carrying the line key and the new state, authored by the owner or the loop's own login; the state is derived at read time from the latest event by an allowed login, and events by anyone else are ignored (red fixture). Conversion keeps a stable patch-goal key derived from the line key, so conversion and queueing are reconciled on resume and a crash between them never orphans or doubles a patch goal.
- Accept-all is bound to the line ids that existed when it was posted; a line filed after it stays open (red fixture). The cut proceeds only after complete, successful reads of the issue (all pages) and of every goal's pending run records; a failed or partial read refuses the cut and names the read; confirmed absence (a successful label lookup that lists zero) is the only clean empty.
- Cap line: filed only when spend has reached the cap and the goal is still unfinished with remaining work at the next budget check; a goal that finishes at the cap files none (fixture: spend exactly at the cap, goal finishes). A goal at the cap ends by its own finish or a step failure.
- Budget bound: a raise never takes the budget above 2 x the estimate; a held budget already above it (an owner's explicit value) is kept, not lowered, and no raise is made (fixture: held 600, estimate 240); a token budget of zero or none means unlimited and the rule does not apply (fixture).
- Sites with no diff (the plan gate, a design choice in a step reply) classify by the goal's declared touches and the stop's recorded class; if neither is available the stop is unclassifiable and waits. A loosened or deleted test, mechanically: any removed or changed line in a test file, any row removed from or edited in the regression rows file, any added skip or expected-failure marker; in doubt it waits; one red fixture per pattern.
- The table takes a scope check from block 1 (default on), which block 6 fills; each block adds its regression rows as it lands, so a goal that stops early still leaves linked rows. The word list has a negative-control fixture of benign text that must pass as `other`, and the build records the false-wait rate on recorded stops in the pull request notes.
- Owner-facing wording (all additive, each pinned by a fixture on the exact text): (1) board wait line: `WAITING <goal>: <class> - <one-sentence reason> - owner action: <exact reply>`, the class from the fixed list (a safety subject name, unclassifiable, issue unreachable, setting off). (2) Ledger line, visible: `[ ] <id> <goal> | <stop> | <subject> - <what happened>; settle with: "<words>"; recommend: <x>`, the id short and stable (`<goal>-<stop>-<n>`), the key marker in a hidden comment, event comments plain sentences ("<id> accepted by <owner login>"). (3) The cut's refusal is one list: open lines first with a copy-paste `accept-all <id> <id> ...` comment, the issue URL and "post as <owner login>", then blockers accept-all cannot clear (a converted line with its patch goal, a failed or partial read, queued unfiled lines), each as one line of cause, object and next action; a bare `accept-all` with no ids is rejected. (4) The next cut reports what it ignored and why (not the owner, unknown id, filed after the accept-all with the time) and lists each accepted id with its accept time. (5) Setting refusal: `refused: set <name> <value> for <scope> <id> needs an owner reference; unchanged (<current value>, from <scope>)`, exit non-zero; the setting's name, scopes and default are documented in the loop's start file and shown on the board's setting-off wait. (6) A cap line reads: goal, "reached its 2x cap at <spend> of <estimate>", old and new figures, "keeps working at the cap; accept to continue or decline to queue a patch goal". (7) "Verify by hand" steps give isolated setup, the exact command or board place, the exact expected text and cleanup, including the wrong-author and late-accept cases. (8) The pull-request notes have one "DLF-1 notes" block with fixed headings: lines filed, minutes waited, owner overrides, false-wait rate, script headroom, deferred follow-ups.
- Allowed writer per transition (pinned, one fixture each): only the owner's login may write an accept or a decline; the loop's login may write only open, filed, and closed after an accept (and closed when the patch goal has merged); an event from a disallowed writer is ignored and reported at the next cut. A toy, seen red first, shows that a loop-written accept after an owner decline leaves the line declined.
- Source of the requirement text: the page and the DLF-1 unit named in this plan are the owner-approved text, merged to main by the text goal that runs first; the DRAFT in the notes file name is only that file's old name.
- Owner decisions (TD1431): breaks go on the release issue and do not hold a merge (DLF-1.1 as written); reversal-cost bounding is a follow-up outside v1.1.0; this is one goal, not split. The owner's accept for DLF-1.4 is only the one list and its accept-all line at the cut, typed by the owner with an id agents cannot write; the plan adds no per-goal owner step.

- Release issue: created once, by the first filing; after creating, the goal re-lists by label across all pages and keeps the lowest issue number, posts there, and closes its own duplicate. A lookup that fails or whose pages are incomplete is never read as "no issue": the filing is queued (a stop that would wait keeps waiting). Fixture: two goals creating at once end with one open issue.
- Filing: every comment carries a hidden marker with its line key; lookup paginates fully and the earliest comment for a key wins; the occurrence is the stable break, choice or test id, never a hash of reworded text; after an ambiguous write (timeout after a possible success) the goal re-reads by key before posting again. Fixtures: concurrent same-key filing, a post followed by a timeout.
- States are event comments: each transition is an append-only comment carrying the line key and the new state, authored by the owner or the loop's own login; the state is derived at read time from the latest event by an allowed login, and events by anyone else are ignored (red fixture). Conversion keeps a stable patch-goal key derived from the line key, so conversion and queueing are reconciled on resume and a crash between them never orphans or doubles a patch goal.
- Accept-all is bound to the line ids that existed when it was posted; a line filed after it stays open (red fixture). The cut proceeds only after complete, successful reads of the issue (all pages) and of every goal's pending run records; a failed or partial read refuses the cut and names the read; confirmed absence (a successful label lookup that lists zero) is the only clean empty.
- Cap line: filed only when spend has reached the cap and the goal is still unfinished with remaining work at the next budget check; a goal that finishes at the cap files none (fixture: spend exactly at the cap, goal finishes). A goal at the cap ends by its own finish or a step failure.
- Budget bound: a raise never takes the budget above 2 x the estimate; a held budget already above it (an owner's explicit value) is kept, not lowered, and no raise is made (fixture: held 600, estimate 240); a token budget of zero or none means unlimited and the rule does not apply (fixture).
- Sites with no diff (the plan gate, a design choice in a step reply) classify by the goal's declared touches and the stop's recorded class; if neither is available the stop is unclassifiable and waits. A loosened or deleted test, mechanically: any removed or changed line in a test file, any row removed from or edited in the regression rows file, any added skip or expected-failure marker; in doubt it waits; one red fixture per pattern.
- The table takes a scope check from block 1 (default on), which block 6 fills; each block adds its regression rows as it lands, so a goal that stops early still leaves linked rows. The word list has a negative-control fixture of benign text that must pass as `other`, and the build records the false-wait rate on recorded stops in the pull request notes.
- Owner-facing wording (all additive, each pinned by a fixture on the exact text): (1) board wait line: `WAITING <goal>: <class> - <one-sentence reason> - owner action: <exact reply>`, the class from the fixed list (a safety subject name, unclassifiable, issue unreachable, setting off). (2) Ledger line, visible: `[ ] <id> <goal> | <stop> | <subject> - <what happened>; settle with: "<words>"; recommend: <x>`, the id short and stable (`<goal>-<stop>-<n>`), the key marker in a hidden comment, event comments plain sentences ("<id> accepted by <owner login>"). (3) The cut's refusal is one list: open lines first with a copy-paste `accept-all <id> <id> ...` comment, the issue URL and "post as <owner login>", then blockers accept-all cannot clear (a converted line with its patch goal, a failed or partial read, queued unfiled lines), each as one line of cause, object and next action; a bare `accept-all` with no ids is rejected. (4) The next cut reports what it ignored and why (not the owner, unknown id, filed after the accept-all with the time) and lists each accepted id with its accept time. (5) Setting refusal: `refused: set <name> <value> for <scope> <id> needs an owner reference; unchanged (<current value>, from <scope>)`, exit non-zero; the setting's name, scopes and default are documented in the loop's start file and shown on the board's setting-off wait. (6) A cap line reads: goal, "reached its 2x cap at <spend> of <estimate>", old and new figures, "keeps working at the cap; accept to continue or decline to queue a patch goal". (7) "Verify by hand" steps give isolated setup, the exact command or board place, the exact expected text and cleanup, including the wrong-author and late-accept cases. (8) The pull-request notes have one "DLF-1 notes" block with fixed headings: lines filed, minutes waited, owner overrides, false-wait rate, script headroom, deferred follow-ups.
- Allowed writer per transition (pinned, one fixture each): only the owner's login may write an accept or a decline; the loop's login may write only open, filed, and closed after an accept (and closed when the patch goal has merged); an event from a disallowed writer is ignored and reported at the next cut. A toy, seen red first, shows that a loop-written accept after an owner decline leaves the line declined.
