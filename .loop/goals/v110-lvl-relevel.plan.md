Sixteen scripts in four skills and 58 toys compare the OLD level words (land, nightly, draft, covered) as literals or build fixture rows with them (runs.py:279-282, actions.py's workflow render, lanes_cli.py, completion.py, tiers.py, lane.py, health's lean.py/rules.py/enforce.py/milestone.py, docs' criteria.py/render.py, settings.py's `goal_levels` and `ci_levels`). - So the table stays byte for byte, and the new words live in a RECORD FILE keyed by row id, `.loop/regression-relevel.tsv`, with one line per row: `id TAB old word TAB stage TAB risk TAB covers TAB seconds TAB reason` (`stage` is L0, L1 or L2; `risk` is security, private or none; `covers` is the comma list of row ids that prove a covered row; `seconds` is the measured time recorded when the row was re-levelled, empty when it has none). The old word stays in the table's `level` column and in the record's "old word" column, so the record's old word is real. Whether the record is later merged into the table, and the old column and its words retired (`goal_levels`, `ci_levels`, the PR workflow's level map, the Regression runbook's labels, the draft state column), is G4's call and is kept out of G1.
- THE SENTENCE (TD1756, word for word): the level record is part of the table for done lines 1 to 3; every reader of a row's level reads the row table and its level record together through levels.py; a row with no record entry reads as blank and is refused.
- The new refusals are ARMED by an explicit marker, not by the data: the record file exists. A fixture table, an adopted repo's table or a table that was never re-levelled has no record file, and reads exactly as today. Once the record exists (written by the re-levelling and committed with the table), every row of the table must have a record entry with a valid `stage` and `risk`; a row with no entry, or a blank or "L3" stage on any row, even every row at once, is refused; only deleting the tracked record disarms it, and that is a visible diff. `regression.py add` and `regression.py sync --write` in an armed table give a new row an entry (below), so a new row cannot arrive untagged.
- How the frozen done lines read: done lines 1 and 2 say "level"; in G1 they are tested on the record's `stage` and `risk` of an ARMED table (main's table with its record after the re-levelling, and the toys' armed fixtures); an unarmed table is outside them by design. The deviation is named in the PR body.

### Steps

1. `skills/workflow-regression/scripts/levels.py` (NEW, about 9,500 bytes, stdlib only): `STAGES = ("L0", "L1", "L2")`, `RISKS = ("security", "private", "none")`, `join(rows, root)` (adds `stage`, `risk` and `covers` to each row from the record; a row with no entry reads blank), `check(rows, root)`, `relevel(root, times, dry_run)`, `draft_fields(root, goal)` and `add_entry`. `check` returns nothing for an unarmed table (no record file); for an armed one it refuses, one line each and the first failure exits 2, with these codes: `LEVELS_BAD_STAGE` ("row <id> has stage <word>; the levels are L0, L1 and L2", for blank, for no entry and for "L3"); `LEVELS_NO_RISK` ("row <id> guards Principle 6 requirement <ID> and has no risk tag; the tags are security, private and none"); `LEVELS_BAD_RISK` for a word outside the three; `LEVELS_BAD_COVERS` ("covered row <id> lists <x>, which is not a row id"); `LEVELS_NO_EVIDENCE` (a defect row's issue labels could not be read at the re-levelling); and `LEVELS_L0_OVER` ("the L0 rows add up to <n> seconds; the limit is 45"). Every refusal prints the exact fix: the record line to write, and who acts (the worker edits the record).
2. The Principle 6 rows and the risk tag, with real sources: a row guards a Principle 6 requirement when its `goal` column names a requirement id in the Principle 6 table of `docs/wiki/Principles.md` ("## 6. Private and guarded", read, never edited, four requirement rows today); adding a requirement to that table arms the rule for its rows. Its tag is `private` when the requirement's own summary text in that table holds one of the words `private`, `private name`, `leak`, `home path`, `secret` (a fixed list in `levels.py`), else `security`; the reason is `risk: requirement`. A defect row's tag comes from the labels of the issue or issues in its `link` cell, read ONCE by the re-levelling (the one network read of this goal, never made by a test): the cell is parsed for `https://github.com/<owner>/<repo>/(issues|pull)/<N>` links (the repo comes from the URL, so the 110 links to the old repo and the 9 to the service repo each resolve in their own repo), for `[#N](...)` links (the URL inside), and for a bare `N` or `#N` (the repo of the `origin` remote); a cell with several links is tagged by all of them; each is read with `gh api repos/<owner>/<repo>/issues/<N>` (the issues API answers for pull requests too, so a pull-request link needs no other call). A label named `security` gives `security` and `private` gives `private` (security wins when both); any other labels give `none` with the reason `no security label`. If `gh` cannot be reached or answers an error for any link of a row, the re-levelling REFUSES to write and names the row and the link (`LEVELS_NO_EVIDENCE`), so a defect never turns `none` for want of evidence; a cell with no parsable link is `none` with the reason `no link`. The result is recorded, and a second run reuses the recorded risk of every row and makes no `gh` call. `regression-issues.tsv` is not used (it holds only link, state, date and reopened_at). A Principle 6 row must have `risk` security or private; a row with `none` or blank is refused (`LEVELS_NO_RISK`), at any time, not only at the re-levelling.
3. `regression.py` (20,447 B, 33 B left), with `FIELDS` unchanged, gets, in order: `read_rows` calls `levels.join(rows, root)` and `levels.check(rows, root)` once; `cmd_add` takes `--stage` and `--risk` and writes the row's record entry through `levels.add_entry` when the table is armed (the table write and the entry write stay in the same `slots.edit` lock); `draft()` (regression.py:104, which `regression.py sync --write` calls to draft a row for a done line with none) writes its entry with `levels.draft_fields(root, goal)`: stage L1, and risk `security` for a Principle 6 requirement and `none` otherwise, so the draft workflow keeps working on an armed table; a new subcommand `relevel [--dry-run]` calls `levels.relevel`. To pay for this without trimming text, the two self-contained whole functions `merged` (502 B) and `split` (501 B), which use no name from regression.py and are called only by `cmd_run`, move whole into `completion.py` (1,909 B), with one re-export line in regression.py (the toys call `regression.merged` and `regression.split`, which the re-export keeps working); the move check covers both.
4. The re-levelling (`levels.relevel`), applied to the 744 rows, never drops, reorders or edits a row of the table and writes only the record, with the rules the approved page gives (LVL-1.5): `land` becomes L1 by default; a `land` row goes to L0 only when its measured time (the 656 measured times in `.github/workflows/row-times.tsv`, read at the re-levelling only, never edited) is under 5 seconds, its command script and the helper files that script names (any `dev/toy` or `skills` path it mentions, followed to a depth of 3) use no network and no toy repo (a fixed word list in `levels.py`: `dev/toy/make.sh`, `gh `, `fakegh`, `git push`, `git clone`, `git init`, `curl`, `urllib`), and adding it keeps the L0 total at 45 seconds or less (rows are taken fastest first until the next would pass 45); a row with no measured time starts at L1; `nightly` becomes L1 when its measured time fits an L1 shard and L2 otherwise, where "fits" is the pull-request row limit that exists today, 200 seconds, and a row that `.loop/regression-limits.tsv` keeps out of the PR shards with the word `nightly` becomes L2 whatever its time; a nightly row with no measured time follows the page's untimed rule and starts at L1 unless that file keeps it out; all 27 nightly rows have a measured time at or under 200 seconds today, so only the limits-file row goes to L2. EVERY row tagged `security` or `private`, a Principle 6 requirement row or a defect row, is forced to stage L1 exactly (the page's minimum level and ceiling: never L0, and never L2 through the time or the limits file; LVL-1.3 and 1.4). `covered` is not a run of its own: `covers` is the list of row ids that prove it and its stage is the highest stage among them. On main 13 of the 23 covered rows name existing rows in their command or description text and `relevel` fills `covers` from those; 10 are hand-mapped (nine name none that exists: `done-hard-eta-2`, `done-judge-stable-keys-2`, `done-apply-rerender-2`, `done-homeguard-skills-main-1`, `done-homeguard-skills-main-2`, `done-docs-v2-3`, `done-docs-v2-5`, `done-docs-v2-6`, `done-gap-wave1-small-4`, because their text names a row that was renamed or is absent, or uses a wildcard; and `done-docs-v2-4` names one existing row beside prose that is not an id). So the build starts with a COVERS PRE-PASS: for each of those 10 the worker reads the row, names the existing rows that really prove it, writes them in the record's `covers` by hand, and records `covers: by hand` as the reason; the reviewers see the ten mappings. Merely keeping references that happen to exist is never enough: a row whose list drops part of the claimed proof is listed with the full text beside it. A row for which no existing row can be named stops the build and asks the owner (`LEVELS_BAD_COVERS` stays refused, never guessed). `draft` has no row on main, so the separate state column for drafts is left to G4. The reason column is one of `time`, `risk`, `default`, `covered`, `no time` or `covers: by hand`.
5. The L0 total check: `levels.check` sums the RECORDED `seconds` of the stage-L0 entries (the record, not the live times file, which CI refreshes and which would otherwise make every command refuse after a times refresh) and refuses over 45 seconds, naming the total (`LEVELS_L0_OVER`); `relevel` runs it against the times it just read, before writing, and refuses to write a record that fails. An L0 entry with no `seconds` is refused too (it has no time to add).

A table with no `levels` key reads as the defaults, so no repo's config breaks. `cutcheck.py` already calls `sizing.validate`, so the cut sees the refusal too.
