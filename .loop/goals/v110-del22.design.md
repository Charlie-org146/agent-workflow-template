## Problem
A plan has no level, no time limit, runs its reviews one after another, records no per-review cost, and a planning-tool
refusal that is not the goal's own (guard says "evidence", an old planned file is gone) stops the goal until a person
starts a fresh session.

- No script may reach 20,480; none may newly cross 19,000; and, by TD1059, every script this goal touches ends under 19,000. Measured on main 65e242e28: `fit.py` 20,443,
  `guards.py` 20,005, `goal.py` 18,997, `flow.py` 18,951, `board_lines.py` 18,980, `live_board.py` 18,349, `settings.py` 20,028. MAX_FILES is 200 (package 101 files).

  guard log does (decision deny, disposition fallback).

## Design
Two new modules and a few hooks; `goal.py`, `board_lines.py` and `settings.py` are not touched, `guards.py` gets one not-counted branch.
1. `planlevel.py` and `planfault.py` (each under 19,000 bytes; the fault side is split out): `LEVELS` defaults (small: eng, 10 minutes; normal: ceo, dx, eng, 30; large: those plus an outside review, 45; override by the setting
   `plan_levels`), `level_of` (the decision table in the plan; first match wins), `record` (minutes, missed with cause, the 2x flag against at least three earlier reviews of the same
   name from the last 50 plans), `plan_fault` and `fallback_ok`, `ask` (the per-goal plan prompt), `run_reviews` (the real concurrent runner), `stamp` (CLI), `note` (board text).
2. `fitkit.py` (under 19,000 bytes, no logic): self-contained helpers (the sizing family with its constants, `deadline`, `sidecar`, `view`, `pr_open`, `main_here`, `off_rows`, `off_reply`, `next_command`) moved whole and unchanged out of `fit.py`; `budget_stop` stays in `fit.py`.
3. Hooks: `fit.frozen_fields` (level at freeze), `fit.keep` (record on success), `fit.plan_ask` (a new function in `fit.py`; `flow.py` calls it where it builds the plan prompt), one not-counted branch in `guards.failed_try`, and one printed line in `live_board.py`. Every hook is guarded: `planlevel` is imported lazily inside `try`.
4. Fault: read from the planning tool's own guard log (never from agent-typed text); the fallback applies only while `plan_levels.fallback_approved` is `{"id": "o807", "release": "v1.1.0"}` and this goal is in the goal list of the frozen v1.1.0 release brief read from `origin/main` through implement-v110's own `brief.py` (a frozen release brief, sha256 checked, naming a task whose frozen task brief's Goals bullet lists the goal; TD1078; the run record's release field is not read; built; until `brief.py` is on main the fallback is off); the refusal is not counted as a try (one not-counted branch in `guards.failed_try`, once per
   goal); the issue is previewed from a worker (GRD-5), carried in the pull request body, and filed once by a step of the generated regression workflow on main (text in a new step file joined into `slots.py`).
5. Configuration: `plan_levels` is read from `origin/main`'s committed `.loop/config.json` after a bounded fetch of `origin main` (GRD-4); a failure gives defaults and the fallback off.
6. Parallel reviews: a real runner (a detached process started from the plan prompt build) where the worker is headless and `plan_levels.review_command` is set; in this repo's session-run plans no headless agent exists, so the prompt orders concurrent subagents, the stamps are self-reported, and that one place is an open item for top.

## Docs and tests
- Done line 1 is met by the merge of v110-fast-text-2 (its DEL-22 text and mark) plus the docs check; this goal writes none of it and waits if it has not merged.
- Four toy scripts, one row each keyed to DEL-22 with sub-IDs in the description, a `PLAN_BREAK=<case>` switch for each rule's negative control, an injected clock and a barrier instead of real

## Risks
- Time-scaled stand-in reviews must not make the toy slow: scale minutes to seconds.
- "Usual" for the 2x flag has no history yet: no flag until three recorded reviews of that name (stated in the page).
- The guard log's entry shape is a fact about the outside tool; its codes are a setting. Its residual risks are in a private note to the operation session (TD1113), not here.

Premises (taken as recommended): (1) a level fixed at freeze and the same input giving the same level is enough; drift is advisory.
(2) Missed is detect-only. (3) Minutes are measured from the goal's own step stamps, never typed by the agent being measured.
(4) No guard or hook is ever changed or bypassed; the fallback is the tool's own route and the owner's approval. (5) No test is loosened.

Landscape: not searched on the web (nothing in the plan depends on outside facts); the pin's own Reference gives the conventional
view: DORA lead time (measure the step), the circuit-breaker pattern (a known fault switches to a declared fallback and the switch is
recorded), Google's review-speed practice (a response-time limit). First-principles check: the usual circuit breaker switches
automatically; here the switch needs the owner's one-time approval, so the design ships it off and says so.

Second opinion: not run (declined as optional). The spec review below is the only independent read.

Approaches considered:

- C, lateral: put timing and fault handling in the outside planning tool. Rejected: the outside tool is not ours to change (the pin's
  non-goals say so).

### R2-1 — feasibility (blocking)

**Problem**

> In fit.py, surface (line 34) uses SURFACES (line 15), area (line 41) uses NOT_AREAS (line 14), and size_of (line 51) uses SMALL_DONE (line 16) and surface/area. None of these constants moves in the design, so planlevel.py cannot run the moved functions unchanged. Importing them from fit would be circular, because fit imports planlevel. SURFACES must also stay in fit.py: guards.py lines 186-187 read fit.SURFACES and fit.frozen_fields line 310 uses surface. The byte arithmetic (fit.py ends about 1,190 bytes smaller) leaves out the constants that must be duplicated or relocated. It also leaves out the change that fit.py needs to import them from planlevel, with callers still using fit.SURFACES.

**Remedy**

> Say where SURFACES, NOT_AREAS and SMALL_DONE live (for example, move them to planlevel and have fit.py re-export them). Say how guards.py's fit.SURFACES still resolves, and avoid a circular import. Recompute the fit.py and planlevel.py byte counts with the constants included.

### R2-2 — consistency (blocking)

**Problem**

> The hook calls record(g, state, step, text). The module section defines record(state, text, cfg, past) with no g or step parameter. The two signatures disagree on argument order and meaning, and the design never says where cfg or past come from at the call site. The design also does not say how record gets the step start/end stamps and the timing file path. planlevel.note(state), used in depth_for, is called a function but is not described in the module section.

**Remedy**

> Make the definition and the call site use one signature, and say where cfg, past and the step stamps are obtained. Add note(state) to the module's described functions.

### R2-3 — completeness (blocking)

**Problem**

> Done line 6 is now met only through a 'fallback approval setting' that the toy supplies as a fixture. The plan_levels setting lists needs, minutes, safety_words, fault_markers and timing_file, and no key for the approval. The design never names the setting, where it is read from, or who may write it. Without that, the toy fixture and the owner's real approval cannot be shown to use the same path.

**Remedy**

> Name the approval setting and its location. Read it from the base branch's committed config, like the other plan_levels keys, so a worker cannot set it. Say what the toy's fixture sets.

### R2-4 — clarity (minor)

**Problem**

> Done line 5 is acknowledged as not enforced. The design's header says it 'changes no frozen done line', and does not say whether the owner needs to rule that an instruction plus a measurement meets the frozen wording. The serial threshold (beyond > 5) is also unexplained.

**Remedy**

> State that done line 5 is met as measure-and-flag, or record it as needing the owner's ruling like line 6. Say why 5 minutes.
