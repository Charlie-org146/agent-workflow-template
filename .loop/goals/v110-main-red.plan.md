Issues 5870, 5871, 5872 and 5895.

What "the clean environment" means for each done line (top's reading on o1014, TD1705 and TD1710; a reading, not a change of the done lines). For the three history rows: BOTH GitHub's scheduled regression job and the local clean-environment lane (the environment emptied but for HOME, PATH, TERM and LOOP_ROLE), and each must pass. Where a needed ref such as the base branch's remote ref is missing, a row FAILS, naming the ref and the fix, and never passes vacuously. For codex-key-commands ONLY: PASS means the local clean-environment lane on this machine with a signed-in Codex; on GitHub the row stays main's existing by-design skip (the skip list already says it exits 77 where Codex is not installed or not signed in on the runner). This goal adds no skip line, changes no skip and adds no CI sign-in.

Size of the change: medium (seven files; one new module). One line added to the checkout of the regression job in the generator of the scheduled workflow and the workflow regenerated from it; one function of the generator moved whole into a new sibling module to keep its size under the line; tightened checks and error text in the three history toys and in the live Codex toy; a bounded diagnosis of the live Codex row with a timeout.

### Depends on (order)
Nothing. It shares no file with the goals in flight (their changes are in the schedule scripts and the delivery scripts).

### What exists
- Three of the four rows are history rows: each reads a past goal's own merge on the base branch and compares it with its first parent. With no remote-tracking ref for the base branch, or a shallow history, each fails ("the base ref is missing here", "the change this row was written for adds no file under skills"). Given the ref and full history, all three print ALL PASS locally.
- The scheduled workflow has three checkout steps: the regression job (it runs the rows in sixteen shards, so the history rows run there), the summary job (it downloads the shards' result files and writes one table; it runs no row and reads no history) and the matrix-smoke job (it runs the smoke set, not the history rows). All use the default depth of one commit. The pull request and release workflows use full history. The scheduled run on main shows exactly the three history rows red, each on its own shard.
- The workflow file is GENERATED: skills/workflow-regression/scripts/actions.py holds its template (its checkout step carries persist-credentials: false) and writes it; a toy in dev/toy (test-regression.sh) asserts the generator's output equals the committed file. So the workflow cannot be changed by editing the YAML alone: that fails the parity check and is undone by the next regeneration.
- actions.py is 18,997 bytes, 3 bytes under the 19,000 line (hard fail 20,480); it holds the template, a render function (1,062 bytes), a write function (1,212 bytes) and constants.
- The history toys call git diff and treat a failed diff as an empty change (a vacuous pass), and the live Codex toy verifies matching output without checking that the child command succeeded. Both are defects this goal must close (tightening only).
- The live Codex row (codex-key-commands) is red on main in the clean environment with six failed checks and its cause is not known. It already skips by design (exit 77) when Codex is not installed or not signed in; the issue is that it fails here.

### Design
A. Generator. Add fetch-depth: 0 beside persist-credentials: false in the checkout of the regression job in actions.py ONLY (TD1697: the summary and matrix-smoke checkouts stay unless the build shows a history row runs or is read there, and then that one is named here with its evidence first); regenerate the workflow with the tool's own write command; the parity toy stays green. No other line of any workflow changes (owner o966).
B. Byte plan for actions.py (a pure move: the moved body is not edited). Move ONE function, write (1,212 bytes), whole, into a NEW sibling module of the same folder, actions_write.py (about 1,380 bytes with its header and imports). The new module imports ONLY the standard library at its top (no import of actions), so there is no import cycle at load. It carries a small lazy wrapper above the moved function, `def render(*args, **kwargs)`, that imports actions at CALL time and returns actions.render(*args, **kwargs); the moved body's bare use of render therefore resolves to that wrapper and the body itself is not edited. actions.py, at its bottom after render is defined, adds `from actions_write import write`, so every existing caller of actions.write keeps working. Imported alone, actions_write works: calling write imports actions on demand, which finds actions_write already loaded and its write already defined. (The wrapper adds about 140 bytes to the new module, now about 1,520.) actions.py goes from 18,997 to about 17,830 bytes after the move and about 17,860 with the one added template line; the new module is about 1,520; both stay under 19,000. Toy cases (in the parity toy, test-regression.sh): import actions_write ALONE (nothing else imported) and call write by its old name; import actions first and call it; import both orders; run actions.py with --help. The new file is the owner's (o970, ledger, from o1034): allowed for this goal.
   Registration, stated: the new module is a package file (the package limit is 200 files; 107 are tracked under skills now; the 99-file headroom row is already known red, issue 4497, and does not change); it has no command line, so listing.json's commands and the skill Command map do not apply; the build runs the package rows (package-passes, package-caps-held, package-headroom-held, package-rows-tracked), listing-names-every-command and pods-size singly from the clean environment.
C. History toys. A failed git diff, or any failed child command, is a FAILURE, never an empty change. One code table, defined here once, each toy printing its code and fix on its first line of failure, saying side effects none, and exiting non-zero:
   HIST-E01 the base ref is missing (the repository, ref and merge it was reading are named). Fix: git fetch origin main:refs/remotes/origin/main; in the scheduled job the checkout's fetch-depth 0 supplies it.
   HIST-E02 the history is shallow. Fix: git fetch --unshallow (then rerun once); a dispatched run from a non-main ref or a fork needs the base ref fetched explicitly first, as in HIST-E01, because fetch-depth 0 alone does not bring another repository's ref.
   HIST-E03 a git diff or another child command failed (the operation, its exit status and the sanitized cause are printed). Fix: the fix of E01 or E02 if the cause is history; otherwise escalate with that line.
   HIST-E04 a fixture could not be built (a fixture-construction failure, kept apart from history-read failures so its text does not tell anyone to fetch history).
   The table lives in this plan and in each toy's own header comment (no new shared file). Every existing assertion and negative control is kept; the new checks only tighten. A toy prints ALL PASS only when every child command succeeded and exits non-zero otherwise, so a failing toy cannot pass its row through the row's tail-and-grep wrapper; the three rows' commands do not change. Negative controls, run end to end through the row's own command: a fixture where git diff fails after a success marker was printed must fail the toy and the row; a shallow fixture must print HIST-E02 and its fix.
   Where the history rows run, and what each lane does (the evidence before the pull request: the three history rows run once in a worker worktree and once in the pull request workflow's form, singly):
   - the scheduled regression job: the checkout of the regression job gets fetch-depth 0 (this goal), so the base ref and history exist and the rows pass; the summary and matrix-smoke jobs run no history row and stay at the default depth.
   - the pull request workflow: its checkouts already use fetch-depth 0 (unchanged); the rows run there and must stay green.
   - the merge-group run of the pull request workflow: its checkout uses fetch-depth 0 (unchanged); same.
   - a worker worktree (the local clean-environment lane): the worktree's repository has the base ref from its remote, so the rows pass; with no base ref at all the row FAILS with HIST-E01 naming the ref and the fix.
   - a clone with no remote, a shallow clone, or a dispatched run from a non-main ref or a fork: the row FAILS with HIST-E01 or HIST-E02 and its fix (never passes vacuously).
D. The live Codex row. First a bounded diagnosis: run the row from the clean environment with a timeout and closed standard input (so Codex can never prompt), retain the invocation, versions, the names (not values) of the environment variables involved and the command artifacts, and name the cause of the six failures. Distinct codes, each with the human command and the reason on its first line:
   CODEX-E01 Codex is not installed (exit 77 as today for a host with no Codex; never the goal's pass).
   CODEX-E02 Codex is installed but not signed in: the build STOPS and asks the operation (a sign-in is a safety-class question); there is no skip as the goal's pass and no CI sign-in. Human command: codex login.
   CODEX-E03 timeout: a 300-second deadline for the whole live row (30 seconds for the admission probes). Against the limits: the scheduled job's shard limit is 30 minutes (1,800 seconds) and the lane's own budget is 15 minutes; the row limit is 540 seconds as top's decision TD1712 states it (the limits file shows 200 seconds as the pull request shards' row limit and gives one row a 300-second exception; the Codex row does not run on those shards because the existing skip list keeps it out on GitHub). So 300 seconds is under 540 and under both budgets, and no limit exception line is needed; the child is killed; side effects PARTIAL (artifacts may be half written); no automatic retry, one rerun by a person after the cause is named.
   CODEX-E04 a child command exited non-zero, with its exit status.
   CODEX-E05 verification failed after the commands ran (matching output with a failing status is a failure).
   Every new error line of this goal (the HIST and CODEX codes) passes through the private-name scan (private.py) and the secret screen before it is printed or kept, so a local path, a repository name or a secret-shaped value is replaced by its class, and a toy proves it (a fixture with a planted private name and a token-shaped value in a ref, a path and a command output is screened in every code's text). Retained command artifacts and diagnostics pass the same secret screen the operation uses before they are kept, with tokens and authentication paths redacted. The verification checks every command's expected exit status together with its existing assertions and validates the Codex process status; add controls for a failure after a success marker and after result files are written. The row must PASS in the local clean environment on this machine with a signed-in Codex. If the cause needs a guard change, a secret or a sign-in in CI, the build STOPS and asks; nothing is converted to a skip.
E. No loosening. No row is changed, skipped, added to the known list or removed; the regression table changes only if a row's command must change, with the same checks and negative controls and its approved-row-changes line.

### Decisions (the planner's, for review)
- The generator is the source; the YAML is regenerated, not edited.
- write (not render) is the function that moves: it depends only on render and the standard library, so the move is pure; render depends on the template and many constants.
- The Codex row must truly pass in the local clean-environment lane with a signed-in Codex; on GitHub it stays the existing skip; the exit-77 skip stays only for hosts with no Codex and is never the goal's pass. No skip line is added or changed and no CI sign-in is added.
- The new module imports only the standard library and actions.py injects render, so the moved body stays unedited and the import order does not matter.
- The done lines mean both GitHub's job and the local lane.

### Alternatives weighed and set aside
- Editing the YAML only: fails the parity toy and is undone by regeneration.
- Trimming 25 bytes elsewhere in actions.py: it is a whole-file trim to fit, which the size rule refuses.
- Toys that fetch the one merge they read, or skip where history is missing: skipping loosens a row; fetching needs network in a toy.
- Adding the rows to the known list or the skip list: forbidden by the goal.

### Risks
The Codex cause may need a guard, a secret or a sign-in in CI; then the build stops and the owner is asked. The new file and the workflow change are safety-class and wait for the owner's word.
