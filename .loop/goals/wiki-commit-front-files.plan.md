### Fix 1: the one commit includes every file its render changed (done line 1)
- Cause: `wiki.py prepare --commit` runs the docs audit, whose full render rewrites the front files (README and Home generated parts, section pages); then the wiki commit takes the wiki folder only, so a rewritten README stays modified and the lane refuses it with a message that names the wrong cause. The record step renders with `--tables`, which never writes front files; it is not changed.
- Change, in the wiki commit only: it renders the front files in a throwaway tree (a temporary checkout of HEAD with the working wiki folder copied in, the stored confidence figure kept, no network), compares each front file outside the wiki folder (the README) there with the working file, running the render scripts that live inside that tree (the render picks its repository identity from where its scripts live and from the origin, so both renders must run their own tree's scripts), and commits, in the same commit as the wiki folder, every such file that is modified and byte-equal to that render. Front files inside the wiki folder (Home, Principles) are committed with the folder exactly as today and are not compared. A modified front file that differs from the render (an edit the renderer would not make, or data not yet committed) is left dirty and named. The decision is derived from file contents on every run, so after the owner reverts the foreign edit the next run commits the file. Nothing equal and modified means no extra file and no empty commit. The commit subject stays "Wiki: update pages for <slug>"; its body names the front files.
- Failure line, on STDOUT, with the wiki step exiting 1 in this case only (the pr step prints the wiki step's stdout as a NOTE only when the step exits non-zero, shows nothing of stderr, and carries on; today a dirty front file exits 0, which would hide the line): `WIKI_FRONT_DIRTY: <file> differs from a render of the committed tree, so the wiki commit left it. Fix: commit or revert the extra edits (or commit the data they come from), then run wiki.py prepare <slug> --commit again (nothing was committed for that file; safe to rerun)`. No delivery script changes. What the pr step then does is existing behavior and is stated as it is: it prints the line as its NOTE, the lane refuses on the same file with its existing dirty refusal (which names the file), and the step records one failed try and prints its generic advice ("fix the failing rows, commit, then run pr again"), which is the wrong advice for this case. The cause is in the NOTE above it. The rule for an unattended worker is therefore stated here and not left to the tool: on WIKI_FRONT_DIRTY it stops and reports both lines and does not rerun the pr step. Making the pr step stop before the lane, without a try, needs a change in the delivery scripts (outside this goal's touches) and is recorded as a follow-up, not done here. The toy runs the real pr step in the foreign case and asserts the NOTE appears above the lane refusal.
- Safety rules for the comparison and the commit: (1) the comparison runs after the audit's fix render has written the file, as the wiki step's second commit call; the audit's overwrite of the generated parts is existing behavior and is not changed here; (2) a front file that also has staged changes is left dirty and named, and the commit names its paths so unrelated staged files stay staged; (3) the render in the tree runs the same scripts the audit's render uses (the repository's own when it has them, the installed package's otherwise, so a repository without its own docs scripts still works) and a render that fails marks every front file as differing; (4) every git command in the tree runs with GIT_DIR, GIT_WORK_TREE and GIT_INDEX_FILE removed from its environment, the tree is made with `git worktree add --detach`, removed in a finally block, and a registration left by a killed run is pruned (`git worktree prune`) at the start of the next run; (5) the record step is unchanged: it renders the Tests tables only, and the pages' content above Tests is already committed by the wiki step that runs first (the pr step's regen), which a toy asserts by running record after the wiki step and checking a clean tree; an edit between the comparison and the commit is not defended against beyond the staged-file rule (one actor, a window of milliseconds), and the plan says so.
- Docs: the page that describes the confidence figures says where the figure comes from and which existing command refreshes it (below); no other doc text changes.
- Toy (the real chain: wiki.py prepare --commit in a toy repo with a toy origin only): README generated parts go stale; today's code leaves README modified (seen red); the fix leaves the tree clean. Controls: nothing stale makes no commit; an unrelated prose edit in README is left dirty, named, non-zero exit; reverting it and rerunning commits README (retry); a renderer change outside the marker blocks (a table cell, a link, the opening paragraph) is committed; a repository whose origin differs from its configured template repository gives the same links in both renders; an unrelated staged file is never committed; the existing record, lane and merge-repair toys stay unchanged and green (mend unchanged); an ordering control shows the front-file commit is made before the pr lane runs (the pr step's regen runs the wiki step first), because a README change outside the generated blocks that lands after the lane has passed is not a wiki-only head move for the merge step and would force the pr lane to run again.

### Fix 2: the render keeps the stored figure and stays stable (done line 2)
- Cause: the render rewrites the confidence figure in the front-page tables from the latest finished full run on main, read from GitHub through `gh`; with no `gh` it keeps the figure already in the page. The same committed files give different cells depending on the network and on which workflow run finished last. A missing local PRD copy is a second network read.
- Requirements: HLT-2 "The scheduled health routine computes the Adoption and Confidence scores, and the docs render writes them into the tables." and DOC-25 "Adoption and Confidence: each feature shows both scores. Health generates them from the references and the tests, and no one types them." Reading (decided by operation-mac; top agrees): the figure's source does not change: it stays the latest finished full run on main, read from GitHub. The render keeps the STORED figure in the committed page and never reads GitHub; only an explicit refresh asks for a new one. Done line 2's "rendered from committed run data, not the working copy's": the committed page figure is that data, so two renders on one commit write the same values.
- The refresh: the scheduled health routine is read-only today and has no command that writes the figure. The one existing writer is the plain docs render run on purpose (`criteria.py render`; the docs publish, `docs.py publish`, also calls the same render function and so refreshes it too); it keeps refreshing the figure from GitHub exactly as today.
