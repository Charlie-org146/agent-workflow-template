# Design: record-commit-ci

## Problem

`goal.py pr` ends with a bookkeeping commit ("pr: record issue states and the lane's results", made in role.py `record()`)
that touches only `.loop/regression-issues.tsv` and the generated result lines in the Tests and Documentation pages. Pushing
it is a new head, so the `regression-pr` workflow starts a full 15-minute `affected` round on a head whose rows the lane
already ran, and the `cancel-in-progress` group cancels the round that was running on the lane head. merge.py needs a green
check on the final head, so every goal pays a second full round (o156).

## Approaches

1. **Skip in CI, on proof from the parent** (chosen). The workflow gains a first step, `recordonly.py`, that decides from
   the checkout alone whether HEAD is a record-only commit on a parent whose `affected` check already passed, and if so the
   row step is skipped, so the job is green in seconds. Cost: one small new script, three workflow lines, `checks: read`.
   Risk: the parent's check may still be running, so the script waits for it (bounded), and a failed or missing parent check
   means the full round runs.
2. Make merge.py accept the parent's check for a record-only head. Cost: merge.py is at its size line (18,994 LF bytes) and
   GitHub's required checks would still show the new head pending or cancelled. Rejected.
3. Carry the lane's result in the record commit as a trailer and trust it in CI. Cost: small. Rejected: a head would pass
   CI on a claim nobody checked, which is how an unrun round gets merged.

## Chosen: approach 1

- `skills/workflow-regression/scripts/recordonly.py HEAD` prints `RECORD-ONLY <parent>` and exits 0, or `FULL <why>` and
  exits 1. It never exits 0 unless all of these hold: HEAD has exactly one parent; HEAD's subject is the record commit's
  subject; every file HEAD changes is `.loop/regression-issues.tsv`, or a wiki page's changed lines are only its result
  lines (the Tests table and `Documentation` result lines); and the parent has a successful `affected` check run
  (`gh api repos/{repo}/commits/{parent}/check-runs`, polled for up to 25 minutes while it is queued or in progress). Any
  other state is FULL, so a record commit that touches anything else gets the full round (done line 2).
- `lanes_cli.py` writes the workflow with the step and `if: steps.rec.outcome == 'failure'` on the rows step, and
  `checks: read`; the committed `regression-pr.yml` is regenerated by `regression.py workflow` so health's drift check holds.
- `cancel-in-progress` stays true for the pull-request run and becomes false for a push whose head commit is the record
  commit, so the record push does not cancel the lane head's round that its proof depends on.
- `pr` pushes the lane head before the record commit, so CI has a parent head to run on. (Today both go in one push; with
  one push there is no parent result, and the record head runs FULL, which is the safe fallback.)
- The Delivery page DEL-1 line ("v2.0 planned") is reworded as the rule; wording goes to the owner for review.
- Test rows (seen failing first): a record-only head is RECORD-ONLY with a passing parent; the same head with a failing or
  absent parent, with one extra file, with an unlisted wiki line changed, or with two parents is FULL. A toy builds a temp repo and a fake `gh`.

## What each done line needs

1. recordonly.py, the workflow step, the push order in pr, and the toy rows above.
2. The FULL cases in the same toy, the DEL-1 rule on the Delivery page, and its regression row.

## Open questions

- Waiting up to 25 minutes for a parent still running keeps a runner idle; the alternative (FULL at once) loses the saving.
  Recommended: wait.
- Whether `pr` may push twice. Recommended: yes, the lane head first; the lane already requires a pushable branch.
