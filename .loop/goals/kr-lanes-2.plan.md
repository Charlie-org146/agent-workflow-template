Terms. The operation session is the coordinating session that governs this worker: its go-ahead arrives as a cross-session message and this worker reports to it. A retry is a rerun of a red row with no change to code, toys or environment. A hold means the worker reports its state, ends its turn and resumes only on a cross-session message from the operation session. The final head is the last commit that touches anything but the body file `.loop/goals/kr-lanes-2.pr.md`. The FAIL set of the repo-health check is the full list of FAIL lines it prints. A rebase in this plan means bringing origin/main into the branch by a merge (the delivery tool merges and does not rebase); its merge commit is a non-body commit. Every report and the body name the origin/main commit they were measured against (after `git fetch origin main`), and a block quoted in the body names the head it was produced on. #5693 and #5694 are GitHub issues.

Steps, in order. Steps 1 to 5 are the verification set (V).
1. Verify, as two sequential passes. A pass runs `regression.py run ROW` for each of the six rows, each alone and directly (no lane, no lane sandbox), from this worktree. The CLAUDE*, ANTHROPIC* and LOOP_* variables are dropped only for each run's child process, never in the worker's own shell, by one shell-independent line (it prints no variable): `python3 -c 'import os,subprocess,sys;e={k:v for k,v in os.environ.items() if not k.startswith(("CLAUDE","ANTHROPIC","LOOP_"))};sys.exit(subprocess.call(sys.argv[1:],env=e))' python3 skills/workflow-regression/scripts/regression.py run ROW`. Each pass uses its own `TMPDIR` (a fresh `mktemp -d`), so that the cached result of `dev/toy/tree-once.sh` is not replayed in pass two. Every run has the row's own time limit, and a hung row counts as red with an unexplained cause. Before and after each pass `git status --porcelain`, `git stash list` and `git worktree list` print the same lines, and the per-pass `TMPDIR`s are removed at the end. Both passes must be green for every claimed row (an unclaimed row, whose known line is restored, must read KNOWN with the same failing lines as on origin/main's tree): green is the row's own result line reading PASS in the output of a fresh run (no `--reuse`), read from the output and not from the exit status alone; SKIP, KNOWN or a replayed result is not green. A red pass is never retried (the runner itself reruns a silent failing command with its quiet greps made loud, to show a diagnosis; that is the tool's rerun, and the row's state stays the first attempt's). If its cause is in this goal, fix it and start again from pass one, at most three times and then `STOPPED:RESTARTS-EXHAUSTED`; if the cause is outside this goal (a bug on main, the environment, a flaky row; shown by running the same row in a detached worktree of origin/main and finding the same failing lines there, which is not a retry; a row red on both with different failing lines is not outside the goal), record it, do not claim that row, and stop and report to the operation session; a red pass that stays unexplained after investigation is treated the same way. The operation session may waive a stop with a recorded reason, which the body quotes. A row green directly but red in a lane is a known gap until the hermetic-lane work lands; qa reports the lane result as it is, and a row still red in the lane at qa gets its known line restored in this same pull request and is not claimed as fixed (the body names it). Partial claim: if fewer than six rows are claimed, the pull request title, the body's top block and the known-list gate say N of six, only the claimed rows' known lines are removed, each unclaimed row is listed with its reason, and the worker reports `NEEDS-DECISION` to the operation session before the pull request opens, since the frozen done lines name six. The body quotes the exact command line.
