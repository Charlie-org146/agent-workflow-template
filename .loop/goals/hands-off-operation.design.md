# hands-off-operation: design

## Problem
The operation session cannot start a worker from a scheduled check-in or a Remote Control turn (the app refuses a session start there), so `workers: app` goals sit unbound. Idle worker sessions hold memory until someone archives them by hand. A new operation session has no one clean start that checks readiness, it sets up no check-in timer of its own, and the check-in puts most goals under "no feature" because `feature_of` reads only a requirement ID in the goal text.

## Constraints found
- Monitoring.md already has MON-1..MON-19 and `criteria_max` is 19, so no new requirement fits: new sub-bullets go under existing ones. MON-5 and MON-11 are Unreviewed (free to edit); MON-6 (clean up after a goal) and MON-1 (start) are Reviewed and need an owner-words un-review (operation-pc cites o130).
- checkin.py is at its 19,495-byte cap and most monitoring scripts are within 300 bytes of 19,000 (LF bytes). Free room: monitor.py (~4.6k), mend.py (~4.8k), notify.py (~5k). No new shipped file (package at its cap), so new logic goes into those and into trims of the big files.
- The scripts cannot call the app's own tools. They can call `session_command` (`TOOL start|rename|send`); archive is the same shape (`TOOL archive ID`). Where the tool has no archive, the check-in prints one `ARCHIVE-NOW <id>` directive the operation session runs with its own archive tool, then confirms with `pool.py archived ID`.

## Approaches
A. New module per item (workers.py, archive.py, timer.py, readiness.py). Clean, but adds shipped files: refused by the 100-file cap.
B. Put each item in the script that already owns the concept, and make room by trimming comments and dead branches there: fallback start in watch.py/sessions.py, archive in pool.py, readiness and timer in operate.py, feature in board_status.py/batch.py. The big scripts have almost no room, so the code that must be new goes into monitor.py (read-only helpers: readiness table, timer state, archive candidates, feature lookup) and the big scripts only call it.
Chosen: B. The helpers live in monitor.py (already imported by pool/fit through `monitor("pool")`-style loaders, runs git only); each caller adds a line or two.

## What each done line needs
1. Fallback start. `workers: auto` (new value, `app` stays the strict default and `workers` unset keeps today's behaviour of launching a background agent): in `watch.start_round`, when `sessions.assign` returns False, `auto` launches `agent_command` through `launch()` (already worker.py loop, LOOP_ROLE=worker) and then binds it: the run record gets `worker: background`, a `worker_why` naming the reason (no app session could start: a scheduled or Remote Control turn), `bound_at` and a bumped `attempt`, so late reports from an older worker are ignored as with a session bind. `watch.py go --background` asks the same for one start under `workers: app` (the operator's own yes for that goal). With `workers: app` and no flag nothing launches.
2. Archive after merge and release. `pool.py archive` (run each pass by operate.py before the check-in): for each busy or free session whose goal is `merged` (gh says MERGED) and whose release is verified published (the run's `release` is `merged`/`cut` and a GitHub release tagged with the version exists, read with `gh release view`; no gh answer means not verified), call `TOOL archive ID` or print the `ARCHIVE-NOW` directive; mark the pool entry `archived`, append a row to `<loop>/archived.tsv` (time, session, goal, reason). The check-in reads rows newer than the last check-in and prints `Archived: <session> (<goal> released vX)`. Guard in one function `eligible(goal_state, sessions)`: never running, waiting, an open PR, a held goal, or a name starting `operation`.
3. Memory pressure. `pool.py archive` also runs when free memory (graph.memory_room source) is below `min_free_memory_gb`: idle (`free`) pool sessions whose last goal (`history`) is released or retired, oldest `since` first, one at a time until memory is back above the floor or none qualifies.
4. `operate.py start`: prints the readiness table (session tool, workers mode, skills version against the repo's `template_version`, hooks, free memory, pool) with ok or the fix; starts no goal; says that `workers: auto` is not set when it is not. Rows come from `monitor.readiness()`.
5. Timer. `operate.py timer` shows the owner the interval (`board.py cadence`), the steps each fire runs (checkin.py and board_page.py checkin for every followed repo, post the layout, SNAPSHOT on change or every 30 minutes) and what it never does (start goals, merge, answer owner questions, edit private-name lists); `operate.py timer created` records `<loop>/timer.json` {cadence, at} on the owner's yes. checkin.py adds a Needs you line when the file is missing or its cadence differs from the current one (`timer: missing` or `stale`), with the words to fix it. The reply hook is the existing `setup.py --reply-hook`; the readiness table reports whether it is installed.
6. Feature grouping. `feature_of(root, text, slug=None)` falls back: requirement ID, then the goal's `feature` stored by `batch.py add --feature PAGE` (queue line field `feature:`), then the issue's `feature:<Page>` label (`gh`, cached in `<loop>/features.json`, one lookup per issue), then the page whose `.loop/docs.tsv` paths cover the goal's touches; else `no feature`. Queued goals show an estimate from the size model (`auto.eta_new` style, size from done lines and touches) instead of `~?`.
7. Size/cap line: measured by the package check and `scripts-a-*-under-19000` rows.

## Open questions (all taken at the recommendation)
- Does the repo flip `workers` to `auto`? No: the check-in's approval batch offers it as one numbered item; `app` stays until the owner's batch answer. (#4507 wants no background worker without the owner's yes; setting `auto` is that yes.)
- Archive when the tool has no archive command: print the directive; the operation session runs it. Taken.
