### What exists (read on the base)

### Design

**A. Targets and codes**
1. L2 is only the schedule's default target (TD1798). `ci_levels`, settings.py, survey.py, autorelease.py and lanes_cli.py are not touched. For `ci_levels: nightly` the target is `${{ inputs.target || (inputs.cleanup && 'nightly' || 'L2') }}`; for `land` it stays `${{ inputs.target }}`. L2 selects every land and nightly row. An empty-target cleanup is `nightly`. SUITE_TIME is written when the target is `nightly` or `L2`.
2. An unknown target keeps today's `REFUSED (BAD_TARGET)`, with L2 added to the listed targets. `cleanup=true` with `L2` refuses `L2_CLEANUP_EXCLUSIVE` with a Fix line.
3. `L2_NO_ROWS` (exit 1) applies to L2 only and counts selected rows over the whole table before the shard split. Land, nightly and row-id targets, and empty tables on them, behave as today.
4. The summary job checks the target and cleanup itself, with the same rule as the runner, and on L2 it counts the selected rows as item 3 does. The check is its own l2.py call, made on every target at the start of the summary step, before the step reads any result file. On a refusal, `L2_NO_ROWS` included, the step prints that code as the summary's first line and exits 1, whatever the shards wrote: none of item 11's three commands and no fallback runs, and no issue, verdict or artifact is written.
5. The summary job runs the same routine check as the shard job: when the routine is off for this event it prints the OFF line, writes nothing (no issue, verdict or artifact) and exits 0.

**B. What counts as run (never-started rows are not run)**
6. At L2, execution comes first. A row that never started (job time) or was cut by the job budget is `SKIPPED` with cause `out of job time`, whether or not it is on the known list or the skip list. It turns the run red and is named. There is no exemption for a job-time skip (TD1825(b)).
7. At L2, a row that ran gets the first of these that fits: PASS; a by-design skip (a skip-list row with its reason that exits 77, or one flagged `notrun` that could not start under `runs.py`'s `unrunnable(code, text)` rule), which is `SKIPPED` plus `# exempt <id> <reason>` (o993: counts as run, shown apart), also when the row is on the known list, so the release review step reads it as it does today; KNOWN (any other known-list row that did not pass, exit 77 included); any other skip, which is `SKIPPED` plus `# skipped <id> cannot run here`; else FAIL. The runner gets `unrunnable` and the names it needs through the block of runs.py that the workflow already copies; runs.py behaves as before. States and the result-file schema are unchanged; today's parser already ignores comment lines. A shard keeps today's exit rule: a skipped row does not fail the shard; the summary job turns the run red (item 11). Land, nightly and row-id targets keep today's state order, printing and exit rule.
8. At L2 the printed line keeps the row id as its own word, `SKIPPED <id> (<reason>)`. `# unrun <id>` is written for every row that never started or was cut by the job budget, known-list and skip-list rows included; each counts in UNRUN and in SUITE_TIME's unrun count, and the `SHARDS n of m reported. UNRUN k` line stays.

**C. One verdict, with completeness apart from colour**
9. The summary job rebuilds the expected row ids itself, from the checked-out table at the run's commit, with the same selection and shard assignment as the runner. So a shard that was killed, timed out hard, lost its artifact or wrote a partial file still has every unfinished row named. A row with no result line is listed as `no result (shard did not finish)`; no result is invented. The shard's own `gh` calls get a 60-second timeout each, on every target; one that times out counts as a failed write.
10. `verdict()` is the only computation. It takes the expected ids, the shard count and the matrix size, and `needs.regression.result`, and returns: state (RED > INCOMPLETE > GREEN), `complete` (every expected id has a result line from a received file; every shard's file ends with the closing comment line the shard writes as its last act, after all its issue writes; the matrix result is success or failure, never cancelled or skipped; and there is no `# gh-failed` line), the non-exempt skipped ids with causes, and the unfinished ids. RED: any FAIL, non-exempt skip or unfinished row. INCOMPLETE: not RED, and the run is not complete or the matrix result is not success. GREEN needs all three: nothing RED, a complete run and a successful matrix result. So an L2 run is never reported green after a shard failed or when it selected nothing (item 4). At L2, every shard issue or label write that fails records `# gh-failed`, and so does a shard that cannot read the issues. The existing `defect` label create stays without `--force` and is not such a write: its failing because the label already exists records nothing. So a shard that failed only because a row failed leaves the run complete. A missing, empty or malformed result file never makes the summary stop before a verdict on L2: its rows are unfinished, and today's plain fallback table is still printed when the grouped summary cannot be written. On L2 the summary prints the tally `L2 <RED|INCOMPLETE|GREEN>: ran n, known n, exempt n, skipped n, failed n` first and, on main only, the line `L2_VERDICT <sha> red|incomplete|green`, which it also writes to a verdict file published as the artifact `l2-verdict` (30 days). On any other ref there is no verdict line, file or artifact. A reader finds it with `gh run download <id> -n l2-verdict`. A covered row is not run and files no issue. G1, which merges before this build, records which rows cover it, in the `covers` column of `.loop/regression-relevel.tsv`; the summary prints one `L2_COVERED <id> -> <worst state> via <cover id>` line for each, reading that record under the names G1's merged code uses. Worst first, the states are: no result, FAIL, skipped, KNOWN, exempt, PASS; a cover that L2 does not run counts as no result. With no record file, each covered row prints `unresolved` and the verdict is not affected. With the record, a covered row with no cover, or with a cover that has no result, makes the run incomplete. The build checks that every covered row on its base has covers that L2 runs, and stops and asks the operation if one does not.
11. The summary step keeps its name and its one working folder. It runs three commands in this order. First, the L2 issue writer (new, in l2.py): the naming of item 17, then the skipped issue of item 13. It gets the token. It has its own time limit of 4 minutes inside the job's 10, and it is guarded so that no failure or time-out of it can stop the step: either is recorded as a `# gh-failed` line, and only to record that line is the combined results file created when no shard wrote it. Second, today's `issues --write`, which reads issue states from GitHub into a local file; it keeps its token. Third, the summary command, with a blank token, and today's fallback and `SHARDS`/`UNRUN` line inside the exit-code capture. The step's exit code: on L2, 0 for GREEN and 1 for RED or INCOMPLETE; 1 for a refusal under item 4; 0 for every other target and with the routine off. The step no longer continues on error, and the `l2-verdict` upload runs on main even after the step fails.

**D. Issues: one writer at a time**
12. The L2 issue writer makes no `gh` call unless the target is exactly L2, cleanup is not true and the ref is main.
13. It files or updates one issue `Regression: L2 skipped rows (n)` (marker `<!-- loop-l2-skipped -->`, label regression) listing every non-exempt skipped and unfinished id with its cause and a fix line per cause. When the run is complete it rewrites the body to the current list, and closes the issue if the list is empty. When the run is not complete it only adds ids to the existing body and never removes one. Reasons come from the committed skip list and the runner's own causes; each line gets the length cap and code-fence replacement that `shown()` gives a row's output.
14. At L2, a failed row's one issue (existing code) gets the label `l2-red` when it is new and when it is already open. The shard creates the `l2-red` label with `--force`. A new issue's body adds the line "Labelled l2-red."; an open issue's body is not edited for this. The row marker and output stay. A new issue is filed even when the label cannot be set: it is then filed without `l2-red` and without that line. A label that cannot be set is reported in the log and recorded as `# gh-failed`.
15. Failure output keeps today's content on every target: `shown()`, its one second run for a silent row, and the last 40 lines. One change, on every target: the second run's time limit is the lesser of the row's limit and the job time left. With no time left it is not run, and the issue says the row printed nothing and gives its exit code.
16. **GRD-7 change (owner o1032).** The concurrency key stays per ref, `regression-${{ github.ref }}`, and `cancel-in-progress` is `${{ github.ref != 'refs/heads/main' }}`. So on main one run writes issues at a time: a newer run waits and never cancels a running one, and no cleanup, one-row or nightly dispatch writes beside it. Other branches keep today's cancelling. GitHub keeps one pending run per group, so a waiting run can be replaced by a newer one; the next schedule runs again. The change is written in the GRD-7 row of docs/wiki/How-to-use-Guardrails.md and in the comment beside the setting.
17. **Naming for done line 3** (TD1825(a), o1004, o1014, TD1987). Done by the L2 issue writer (item 12's limits), the one writer, after the shards, and only when at least one `l2-red` issue is open; otherwise it looks for no issue and opens none. The main-red goal's issue is, in this order: the open issue labelled `main-red` (the lowest number if there are several); else the open issue whose body carries `<!-- loop-l2-main-red -->`; else a new issue titled `Regression: L2 failing rows` that the writer opens with that marker and no label (owner o1032: unlabelled), so the release hold is unchanged (TD1767, TD1793 a). For each open `l2-red` issue, the writer adds to the main-red goal's issue the comment line `L2 red: #n`, where n is the `l2-red` issue's number, unless the goal issue's body or one of its comments already has that line. The run never closes the goal issue and never edits its body. A naming read or write that does not succeed is recorded as `# gh-failed`, so the run is not complete. release.yml and its toy are not touched. The runner runs no `git revert`, `reset` or `push`.

**E. Bytes and files**

The runner's new code (items 6 to 9 and 14) lives in l2.py, in a marked block that the generator copies into the workflow the way it copies runs.py's block. actions.py takes that copy step; a second source embed, of l2.py into the summary job, with the same unsafe-text check tests.py's embed has; the values the summary job now needs (the target, cleanup and the matrix result), whose placeholders in the job's text are in slots.py; and the changes to lines the template already has, among them the target and concurrency settings (items 1 and 16). By estimate, after main-red moves `write` out, actions.py has about 2,500 B under the limit for changes of about 2,200 B; v110-toy-leak-fixes adds about 120 B more. actions_write.py is not edited. The build measures this first. If any script this plan names would reach 20,480 B, the build stops and asks the operation, which takes it to top: a further module is allowed (TD2079; whole definitions move), under the same limit per script.
19. The new module l2.py (owner o1032) sits beside tests.py. It holds the runner's block (item 18) and the new summary-job code: the verdict with completeness, the rebuilt expected rows, the tally and covered lines, the target check, the skipped issue and the naming. It is needed because of the package's per-script limit: on the base, tests.py is 1,663 B under it and actions.py 1,483 B. The summary job embeds both sources, as it embeds tests.py today, and writes both files into its working folder. It runs Python in isolated mode, so tests.py loads l2.py by its file path, and only on the L2 path (item 4's check is l2.py's own call, on every target); what a shard builds from tests.py is unchanged. slots.py (1,498 B under) takes the step and routine changes, measured.
20. The package stays under its 200-file limit; the build runs the package checks. No text is trimmed or merged to save bytes or files (GRD-20, TD1246).
