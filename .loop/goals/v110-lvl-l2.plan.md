# Plan: v110-lvl-l2, L2 full runs every row and a skipped row is red

Goal: make the scheduled run (and the by-hand full run) the page's L2: it runs every row whatever a change reached and records each result; a row the run did not run turns the run red and is named; a row that fails gets one issue; nothing is ever reverted. Base: the pushed head of v110-no-size-cap-a (70cabc292, which holds main 7c6d69ffd), merged into this branch; at the build, main is merged again and every size and count is measured again.

### Design

**A. Targets and codes**
1. L2 is only the schedule's default target (TD1798). `ci_levels`, settings.py, survey.py, autorelease.py and lanes_cli.py are not touched. For `ci_levels: nightly` the target is `${{ inputs.target || (inputs.cleanup && 'nightly' || 'L2') }}`; for `land` it stays `${{ inputs.target }}`. L2 selects every land and nightly row. An empty-target cleanup is `nightly`. SUITE_TIME is written when the target is `nightly` or `L2`.
2. An unknown target keeps today's `REFUSED (BAD_TARGET)`, with L2 added to the listed targets. `cleanup=true` with `L2` refuses `L2_CLEANUP_EXCLUSIVE` with a Fix line.
3. `L2_NO_ROWS` (exit 1) applies to L2 only and counts selected rows over the whole table before the shard split. Land, nightly and row-id targets, and empty tables on them, behave as today.
4. The summary job checks the target and cleanup itself, before it reads any result file, with the same rule as the runner. On a refusal it prints that code as its first line and the job is red, whatever the shards wrote.
5. The summary job runs the same routine check as the shard job: when the routine is off for this event it prints the OFF line, writes nothing (no issue, verdict or artifact) and exits 0.

**B. What counts as run (never-started rows are not run)**
6. Execution comes first. A row that never started (job time) or was cut by the job budget is `SKIPPED` with cause `out of job time`, whether or not it is on the known list or the skip list. It turns the run red and is named. There is no exemption for a job-time skip (TD1825(b)).
7. For a row that ran: PASS; KNOWN (known list); a by-design skip (a skip-list row with its reason that exits 77, or one flagged `notrun` that could not start under `runs.py`'s `unrunnable(code, text)` rule) is `SKIPPED` plus `# exempt <id> <reason>` (o993: counts as run, shown apart); any other skip is `SKIPPED` plus `# skipped <id> cannot run here`; otherwise FAIL. The runner gets `unrunnable` and the names it needs through the block of runs.py that the workflow already copies; runs.py behaves as before. States and the result-file schema are unchanged; today's parser already ignores comment lines. Land, nightly and row-id targets keep today's state order, printing and exit rule.
8. The printed line keeps the row id as its own word, `SKIPPED <id> (<reason>)`. `# unrun <id>` is still written for every row not run for job time (known and exempt ones included), and the `SHARDS n of m reported. UNRUN k` line stays.

**C. One verdict, with completeness apart from colour**
9. The summary job rebuilds the expected row ids itself, from the checked-out table at the run's commit, with the same selection and shard assignment as the runner. So a shard that was killed, timed out hard, lost its artifact or wrote a partial file still has every unfinished row named. A row with no result line is listed as `no result (shard did not finish)`; no result is invented. The shard's own `gh` calls get a 60-second timeout each.
10. `verdict()` is the only computation. It takes the expected ids, the shard count and the matrix size, and `needs.regression.result`, and returns: state (RED > INCOMPLETE > GREEN), `complete` (every expected id has a result line from a received file, the matrix result is success, and no `# gh-failed` line), the non-exempt skipped ids with causes, and the unfinished ids. RED: any FAIL, non-exempt skip or unfinished row. INCOMPLETE: not complete and not RED. A missing, empty or malformed result file never makes the summary stop before a verdict on L2: its rows are unfinished, and today's plain fallback table is still printed when the grouped summary cannot be written. On L2 the summary prints the tally `L2 <RED|INCOMPLETE|GREEN>: ran n, known n, exempt n, skipped n, failed n` first and, on main only, the line `L2_VERDICT <sha> red|incomplete|green`, which it also writes to a verdict file published as the artifact `l2-verdict` (30 days). On any other ref there is no verdict line, file or artifact. A reader finds it with `gh run download <id> -n l2-verdict`. Covered rows print `L2_COVERED` lines; once G1's record exists on the base, a missing cover makes the run incomplete, and all covers are checked after G1 merges.
11. The summary step keeps its name and its one working folder. Order: the skipped-issue command first, guarded so no failure of it can stop the step (a failure is recorded as a `# gh-failed` line, and the combined results file is created if no shard wrote it); then the summary command, with today's fallback and `SHARDS`/`UNRUN` line inside the exit-code capture. Both commands that write to GitHub (`issues --write` and skipped-issue) get a token; the summary command runs with a blank one. The exit code reaches the job for L2 only; other targets exit 0 as today.

**D. Issues: one writer at a time**
12. The skipped-issue command makes no `gh` call unless the target is exactly L2, cleanup is not true and the ref is main.
13. It files or updates one issue `Regression: L2 skipped rows (n)` (marker `<!-- loop-l2-skipped -->`, label regression) listing every non-exempt skipped and unfinished id with its cause and a fix line per cause. It removes ids and closes the issue only when the run is complete and the list is empty. When the run is not complete it only adds ids to the existing body and never removes one. Reasons pass the same redaction as other issue bodies.
14. A failed row gets one issue (existing code) plus the label `l2-red`, added on all three paths: a new issue, an already-open one and a reopened one. A label that cannot be set is reported in the log and recorded as `# gh-failed`. The body keeps its row marker and output and adds the line "Labelled l2-red."
15. Failure output keeps today's behaviour on every target: `shown()`, its one second run for a silent row, and the last 40 lines. The second run's time limit is the lesser of the row's limit and the job time left.
16. **GRD-7 change (owner o1032).** The concurrency key stays per ref, `regression-${{ github.ref }}`, and `cancel-in-progress` is `${{ github.ref != 'refs/heads/main' }}`. So on main one run writes issues at a time: a newer run waits and never cancels a running one, and no cleanup, one-row or nightly dispatch writes beside it. Other branches keep today's cancelling. GitHub keeps one pending run per group, so a waiting run can be replaced by a newer one; the next schedule runs again. The change is written in the GRD-7 row of docs/wiki/How-to-use-Guardrails.md and in the comment beside the setting.
17. **Naming for done line 3** (TD1825(a), o1004, o1014, TD1987). After the shards, the summary job, as the one writer, names each open `l2-red` issue in the open main-red goal's issue, adding each number once. If no such issue is open, it opens one with the marker `<!-- loop-l2-main-red -->` and without the label `main-red` (owner o1032: unlabelled), so the release hold is unchanged (TD1767, TD1793 a). A naming write that does not succeed is recorded as `# gh-failed`, so the run is not complete. release.yml and its toy are not touched. The runner runs no `git revert`, `reset` or `push`.

**E. Bytes and files**
18. The `WORKFLOW` template stays in actions.py, because an existing row and existing toys read the generator's code there. The runner's new code (items 6 to 9 and 14) lives in l2.py, in a marked block that the generator copies into the workflow the way it copies runs.py's block. actions.py takes only that copy step and the changes to lines the template already has, among them the target and concurrency settings (items 1 and 16). By estimate, after main-red moves `write` out, actions.py has about 2,500 B under the limit for changes of about 2,000 B; v110-toy-leak-fixes adds about 120 B more. actions_write.py is not edited. The build measures this first. If any script this plan names would reach 20,480 B, the build stops and asks the operation, which takes it to top: a further module is allowed (TD2079; whole definitions move), under the same limit per script.
19. The new module l2.py (owner o1032) sits beside tests.py. It holds the runner's block (item 18) and the new summary-job code: the verdict with completeness, the rebuilt expected rows, the tally and covered lines, the target check, the skipped issue and the naming. It is needed because of the package's per-script limit: on the base, tests.py is 1,663 B under it and actions.py 1,483 B. tests.py calls l2.py for L2 only, and the summary job embeds both sources, as it embeds tests.py today. slots.py (1,498 B under) takes the step and routine changes, measured.
20. The package stays under its 200-file limit; the build runs the package checks. No text is trimmed or merged to save bytes or files (GRD-20, TD1246).

No assertion is loosened. Also run: test-ci-summary.py, test-regression-issues.py, test-issues-main-only.py, test-release-hold.py (unchanged), test-skip-list.py, test-gate-ci-suite.py and test-suite-time.sh. test-regression.sh and existing rows are not edited.
