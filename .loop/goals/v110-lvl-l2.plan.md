### Design
1. **L2 is only the schedule's default target (TD1798; RT-C1).** The setting `ci_levels`, settings.py, survey.py, autorelease.py and lanes_cli.py are NOT touched, and `L2` is not a `ci_levels` value. The generator renders the shard step's target as `REGRESSION_TARGET: ${{ inputs.target || (inputs.cleanup && 'nightly' || 'L2') }}` when `ci_levels` is `nightly` (the default and this repo's value) and as today's `${{ inputs.target }}` when it is `land`, so `ci_levels: land` keeps meaning the scheduled run takes `REGRESSION_LEVELS` land (the existing test-ci-target.sh `levels` case and milestone.py:332 stay true). On a nightly repo the schedule and an empty by-hand input run L2, an explicit `inputs.target` (`land`, `nightly`, a row id or `L2`) is honoured as before, and a CLEANUP dispatch with an empty target keeps today's `nightly` (so it is never L2). `land`, `nightly` and row ids keep today's behaviour byte for byte. The L2 set is named: `wanted(row)` (actions.py:98-99, today `row[0] == TARGET if TARGET not in ("land", "nightly") else row[1] in ("land", TARGET)`) gets one more case, `row[1] in ("land", "nightly")` when TARGET is `L2` (every row but drafts and covered ones, by the old words; the runner does not read levels.py or stages; the table's old column stays until G4), and the summary job and the dispatch input description render the same target (the description reads `L2, land, nightly or a row id; empty: L2` for a nightly repo and `empty: land` for a land repo). The SUITE_TIME condition becomes `TARGET in ("nightly", "L2")`. An unknown target exits 1 with `L2_BAD_TARGET <value> (quoted, cut to 40 characters, control characters stripped): the targets are L2, land, nightly or a row id. Fix: gh workflow run regression.yml -f target=L2`; a valid target that selects zero rows exits 1 with `L2_NO_ROWS`; `cleanup=true` together with the target `L2` exits 1 with `L2_CLEANUP_EXCLUSIVE: cleanup runs no L2. Fix: pass -f target=<row id>, land or nightly with cleanup, or leave cleanup false` (the two are mutually exclusive, so a cleanup dispatch can never write a result line for L2). New code in the runner never contains `${{`, `TESTS_PY_EOF` or the @TOKEN@ words in actions.py's UNSAFE list. A toy greps the generated file for any `${{ inputs` inside a `run:` body and runs a hostile value (quotes, `$(...)`, newline). The summary job gets `REGRESSION_TARGET`, `REGRESSION_CLEANUP` and the ref as env (item 3).
2. **States stay; EXEMPT is a comment list.** The result schema is unchanged (STATES stay PASS, FAIL, SKIPPED, KNOWN; `id TAB state`). Per row, only when TARGET is L2: PASS; KNOWN (known list, checked BEFORE skipped, so a known row that exits 77 or runs out of time is KNOWN and counts as run, as the page says); a row on `.loop/regression-skips.tsv` WITH its reason that exits 77 (the by-design skip: TOY_SKIP_FILE) or is not started for job time is written `id TAB SKIPPED` plus the comment line `# exempt <id> <reason>` (o993: counts as run, neither red nor incomplete, shown apart); an exempt row that FAILS TO START (exit 126 or 127) is FAIL and red, EXCEPT a row carrying the skip list's third-column flag `notrun` (today only `package-rows-tracked`, which the runner may not be able to start): that row is exempt, exactly as `cutgate.py` and `completion.py` already treat it (the runner reads the flag from the same file with the same rule, so the classification is not a second invention); any other skipped row is written `id TAB SKIPPED` plus `# skipped <id> <cause>` where cause is `out of job time` or `cannot run here`; FAIL. A skipped row prints a distinct line `SKIPPED <id>: <reason>`, not a failure-shaped line (TD1787). Each shard also writes `# expect <n>` (the number of rows it selected) before its first result, so the summary can compare. Comment lines are ignored by the existing parser, so no consumer of the results file changes. For land, nightly and row-id targets the state order, the printing, the exit rule and the issue branches are today's code, unchanged (F8).
3. **The verdict is computed only in ONE function, `verdict(results, env)` in tests.py, used by `cmd_summary` and by `skipped-issue` (TD1793 b; RT-C3).** The summary job passes `REGRESSION_RESULT: ${{ needs.regression.result }}`, `REGRESSION_TARGET`, `REGRESSION_CLEANUP` and the ref as env. `tests.py summary` reads the `#` comment lines of the combined results file in the same pass and, ONLY when the target is `L2`, prints first the tally `L2 <RED|INCOMPLETE|GREEN>: ran n, known n, exempt n, skipped n, failed n` and, only on main, ONE line `L2_VERDICT <sha> red|incomplete|green`, which it ALSO writes to the file named by `--verdict-file` (env `L2_VERDICT_FILE`, `$RUNNER_TEMP/l2-verdict.txt`); an upload step `uses: actions/upload-artifact` named `l2-verdict` (30 days) with `if: always() && github.ref == 'refs/heads/main'` and that file as its path publishes it (the file is the artifact's source; the tally and fallback text are not in it). A reader finds the artifact by run: `gh run list --workflow regression.yml` then `gh run download <id> -n l2-verdict` (G4's reader). On any other ref (a branch dispatch: the shards' gh writes are would-only there) the tally prints but there is NO `L2_VERDICT` line, no verdict file, no artifact and no issue. Land, nightly and row-id runs keep today's summary line, so a one-row run never reads `L2 GREEN`. **Verdict table, RED > INCOMPLETE > GREEN:** RED if any result line is FAIL or any non-exempt SKIPPED row is recorded (a job-time skip is red; skip-only is red); else INCOMPLETE if `needs.regression.result` is not `success` with no recorded red row (a shard that died, timed out, was cancelled or reported nothing), or fewer shard result files arrived than `SHARDS`, or the number of result lines differs from the sum of the shards' `# expect <n>` lines (a shard that wrote a partial file and still reported success), or any `# gh-failed <operation> <row or label>` line is present; else GREEN. Because the matrix result is an input, a failed or cancelled shard can never print GREEN. Exempt and known rows count as neither. No `L2_VERDICT` line for a sha means incomplete. When EVERY shard exits with the same `L2_BAD_TARGET` or `L2_CLEANUP_EXCLUSIVE`, the summary prints that code as its first line instead of per-shard noise. Covered rows: `L2_COVERED <id> -> <worst state> via <cover id>`, reading the covers from G1's record file (the build reads its real name and columns from G1's merged plan; until that file exists on the base, a covered row prints `unresolved` and does not make the verdict incomplete; once it exists, a missing cover is incomplete); known or exempt covers are named; a covered row files no issue. Layout: verdict and tally first, then failed rows, skipped, missing, then covered and exempt lines. **The exit code survives, for L2 only (RT-C2):** the summary command becomes `rc=0; GH_TOKEN= python3 tests.py summary ... > "$out" || rc=$?; cat "$out" | tee -a "$GITHUB_STEP_SUMMARY"; [ "$REGRESSION_TARGET" = L2 ] || rc=0; exit $rc`, with `continue-on-error` removed from the step, so RED and INCOMPLETE fail the job on an L2 run and land, nightly and row-id runs keep swallowing a malformed-file exit as today; the summary job's own target env is rendered by the same expression as the shard's. A toy runs the generated step text under `bash -e`.
4. **One issue for every skipped row (TD1793 c): ONE step with TWO commands.** The existing step "Write one run summary, one table per feature" keeps its name (dev/toy/test-summary.sh lines 87-100 extract it by that name) and its single `here=$(mktemp -d)`, so the combined file `$all` and `$here/tests.py` stay where both commands can read them. Inside it, in order: (1) the token-ful command `GH_TOKEN="$ISSUE_TOKEN" python3 "$here/tests.py" skipped-issue --results "$all"` (main only; the token is passed to this command alone through that one variable, the summary command below runs with `GH_TOKEN=` blank); (2) the token-less summary command of item 3. No separate step is added. `skipped-issue` calls the SAME `verdict(results, env)` as the summary (same shard files, same `needs.regression.result`, same `# expect` lines), so it knows whether the run is full: it files or updates ONE issue `Regression: L2 skipped rows (n)`, marker `<!-- loop-l2-skipped -->`, label regression, whose body lists EVERY non-exempt skipped row id with its cause and a fix line per cause (time skips: the matrix size `SHARDS` in actions.py and `regression.py workflow`, raised only if the bytes allow; cannot-run-here: the row's own prerequisite, or put it on `.loop/regression-skips.tsv` with its reason, which the owner approves). The body is edited in place only when the set of ids changes; no comment is added while the same rows stay skipped (F7). It CLOSES the issue only when `verdict` is not INCOMPLETE and there are zero non-exempt skipped rows; a cancelled run, a dead shard or a partial shard (INCOMPLETE) never closes it. The `gh` calls have a 60-second timeout each and a 3-minute budget; a failed or unknown write appends `# gh-failed <operation> skipped-issue` to `$all`, which the summary command (run next, in the same step) then reads, and an unknown write is looked up once before one retry. Exempt reasons and causes from the skip list are free text from a repo file: they pass the same redaction as other issue bodies. No per-row skip issue, no roll-up, no rotation. Done line 2 is met literally: one issue names each skipped row.
