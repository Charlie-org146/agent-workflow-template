### Design
1. **Target L2 through the setting `ci_levels`, adopters unchanged.** `L2` becomes a third allowed value of `ci_levels` (actions.py:336 check, settings.py:50 text, survey.py ENUMS); the DEFAULT stays `nightly`, so adopters and this repo's committed config keep today's behaviour until a repo sets `ci_levels` to `L2` (this repo's own flip in .loop/config.json is a settings change: a separate step the operation and owner take, not made by this goal). With `ci_levels: L2` the generated file carries `REGRESSION_LEVELS: "L2"`, so the schedule and an empty by-hand input run L2, while `inputs.target` (`land`, `nightly`, a row id, or `L2`) still overrides it: the shard step's `REGRESSION_TARGET: ${{ inputs.target }}` stays. `land`, `nightly` and row ids keep today's behaviour byte for byte, so the old toys (test-regression.sh lines 201-202, the test-ci-target.sh `levels` case) stay and pass. The L2 set is every row except drafts and covered rows, by the old words (the runner does not read levels.py or stages; the table's old column stays until G4). The SUITE_TIME condition becomes `TARGET in ("nightly", "L2")`. An unknown target exits 1 with `L2_BAD_TARGET <value> (quoted, cut to 40 characters, control characters stripped): the targets are L2, land, nightly or a row id. Fix: gh workflow run regression.yml -f target=L2`; a valid target that selects zero rows exits 1 with `L2_NO_ROWS`. A toy greps the generated file for any `${{ inputs` inside a `run:` body and runs a hostile value (quotes, `$(...)`, newline). The CI summary job gets `REGRESSION_TARGET` and `REGRESSION_LEVELS` env too (item 3).
2. **States stay; EXEMPT is a comment list.** The result schema is unchanged (STATES stay PASS, FAIL, SKIPPED, KNOWN; `id TAB state`). Per row: PASS; KNOWN (known list, checked BEFORE skipped, so a known row that exits 77 or runs out of time is KNOWN and counts as run, as the page says; the order change applies only when TARGET is L2); a row on `.loop/regression-skips.tsv` WITH its reason that exits 77 or does not start is written `id TAB SKIPPED` plus the comment line `# exempt <id> <reason>` (o993: counts as run, neither red nor incomplete, shown apart); any other skipped row is written `id TAB SKIPPED` plus `# skipped <id> <cause>` where cause is `out of job time` or `cannot run here`; FAIL. A skipped row prints a distinct line `SKIPPED <id>: <reason>`, not a failure-shaped line (TD1787). Comment lines are ignored by the existing parser, so no consumer of the results file changes.
3. **The verdict comes from GitHub's own result plus the artifacts (TD1793 b).** The summary job passes `REGRESSION_RESULT: ${{ needs.regression.result }}` and the target into its step and, ONLY when the target is `L2`, prints first the tally `L2 <RED|INCOMPLETE|GREEN>: ran n, known n, exempt n, skipped n, failed n` and ONE line `L2_VERDICT <sha> red|incomplete|green`, kept as the artifact `l2-verdict` (30 days). Land, nightly and row-id runs keep today's summary line, so a one-row run never reads `L2 GREEN`. **Verdict table, RED > INCOMPLETE > GREEN:** RED if any result line is FAIL or any non-exempt SKIPPED row is recorded (a job-time skip is red; skip-only is red); else INCOMPLETE if `needs.regression.result` is not `success` with no recorded red row (a shard that died, was cancelled or reported nothing), or fewer shard result files arrived than `SHARDS`, or any `# gh-failed <operation> <row or label>` line is present (an issue or label write failed, or its outcome is unknown), or a cover of a covered row is missing; else GREEN. Because the result of the shard matrix is an input, a failed or cancelled shard can never print GREEN. Exempt and known rows count as neither. No `L2_VERDICT` line for a sha means incomplete. When EVERY shard exits with the same `L2_BAD_TARGET`, the summary prints that code as its first line instead of per-shard noise. Covered rows: `L2_COVERED <id> -> <worst state> via <cover id>` (the summary reads the covers from G1's record `.loop/regression-relevel.tsv`, which the summary job's checkout has; a missing cover is "missing" and makes the verdict incomplete; known or exempt covers are named; ties go to the first cover id); a covered row files no issue of its own. Layout: verdict and tally first, then failed rows, skipped, missing, then covered and exempt lines. The step is made able to fail: its `continue-on-error` is removed from the summary step only for the L2 verdict, and the shell runs with `set -o pipefail`, so the job's conclusion matches the verdict (RED or INCOMPLETE exits 1).
4. **One issue for every skipped row (TD1793 c).** The summary job, once, files or updates ONE issue `Regression: L2 skipped rows (n)`, marker `<!-- loop-l2-skipped -->`, label regression, whose body lists EVERY skipped (not exempt) row id with its cause (`out of job time` or `cannot run here`) and a fix line per cause: for time skips, the matrix size `SHARDS` in actions.py and the command `regression.py workflow` (raise SHARDS only if the bytes allow; the build reads the real command that lists slow rows first); for cannot-run-here, the row's own prerequisite, or put it on `.loop/regression-skips.tsv` with its reason, which the owner approves. It closes only when a full L2 run has zero non-exempt skipped rows. No per-row skip issue, no roll-up, no rotation of the tail rows (the one issue lists them all). The write is made by new code in tests.py (the only source embedded in the summary job), with a bounded `gh` timeout; a failed or unknown write adds a `# gh-failed` outcome handled as in item 3, and an unknown write is looked up once before one retry. Done line 2 is met literally: one issue names each skipped row.
5. **Failing rows and issue transitions.** A FAIL row keeps its per-row issue from the shard (existing code), plus the label `l2-red` (`gh label create --force`, so 16 shards racing do not fail; a label failure prints a `FILED ... FAILED` line and records `# gh-failed`) and the line "Labelled l2-red; the main-red goal reads this label." (a fact the code can check; nothing claims a goal names it, and nothing opens a main-red goal). `main-red` is not used, so release.yml's hold is unchanged. Transitions: a skipped row that later FAILs is listed in the skipped issue until the failure issue exists, then leaves it; pass closes the failure issue "Passing again." and removes l2-red; the cleanup mode (code 125) is excluded from every count, files nothing and no longer closes the current skipped issue (it closes only issues of rows removed from the table), and a toy proves skip, cleanup, skip keeps the one issue. Issues written by the old code are left alone and replaced by the new body at the next skip. `shown()` is given the first execution's captured output (a fixture counts invocations and fails if a failed row runs twice); issue bodies are redacted for known token shapes and cut to the last 20 lines. The runner runs no `git revert`, `reset` or `push` (a toy greps the generated workflow and asserts the permissions block: contents read, issues write, pull-requests read, no delta).
6. **Toys and existing assertions.** test-regression.sh lines 201-202 and the existing rows are NOT edited (the default target stays nightly). dev/toy/test-ci-target.sh keeps its cases and gets: its BAD_TARGET assertion migrated to the new text (L2 joins the list), a case for `ci_levels: L2`, aliases and zero selection; its no-work and shell-safety checks stay. The PR body names the replaced clauses and the rulings: done line 2's "one issue names each skipped row" is met by the one issue that lists every id; done line 3's "the main-red goal names it" is replaced by the label l2-red read by that goal (TD1767), nothing else; TD1787 (a distinct SKIPPED line; RED > INCOMPLETE > GREEN) and TD1793 (autorelease.py untouched, needs.regression.result, one skipped issue, L2 as a ci_levels value, STATES unchanged); and that nothing opens a main-red goal.
7. **Regenerate and check.** The workflow is regenerated with `regression.py workflow`; the parity toy passes; no Reviewed wiki text is edited (docs/wiki/Regression.md's "draft and covered rows are not run" stays true); the codes `L2_BAD_TARGET`, `L2_NO_ROWS` and the `# gh-failed` operations go in skills/loop-files.md's codes table with a short runbook paragraph (how to dispatch `-f target=L2`, how to read the tally and the skipped issue).
