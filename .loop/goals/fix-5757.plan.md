# Plan: a row cut or left on a shard is rerun by `affected`, or fails the run (a patch for #5757, REG-4)

## Implementation plan

Goal: in the generated pull-request workflow, a selected row that a shard reports LEFT or CUT is rerun by the `affected` job, and the run is green only if that rerun passes; a row still unfinished after its rerun fails the run. The four frozen done lines in the goal file are met without change. This is a patch: the fix is a few bytes of the generator's template, a toy that is red on the parent commit, one regression row, and a regenerated workflow. No new file under skills/.

What exists today, checked in the worktree:
- The workflow `.github/workflows/regression-pr.yml` is written by `lanes_cli.py` from its `NARROW` template (`regression.py workflow`). Each shard job runs `regression.py run <levels> --reuse --tier goal` with `--budget 120` and `--timeout 200` and writes `t.tsv` rows `id<TAB>seconds<TAB>status` where status is RAN (this shard ran it), SEL (another shard's), CUT (the shard's budget ran out first) or LEFT (it passed the row time limit; regression.py:320 removes such a row from the failures).
- The `affected` job builds `ran.txt` from every row whose status matches `RAN|LEFT|CUT` (the generator's `awk '$3 ~ /^(RAN|LEFT|CUT)$/'`), reruns each selected row that is not in it, and echoes "LEFT (row limit or budget), not failed:". So a LEFT or CUT row counts as accounted for and is never rerun: every check can be green while a selected row never ran.
- The `tree` shard runs `regression.py run ... --tree --timeout 200` without `LOOP_ROW_TIMES`, so it writes no `t.tsv`: a tree row cut at the default 15-minute budget is invisible to `affected`.
- Bytes against the 20,480 fail line [measured: wc -c]: lanes_cli.py 20,477 (3 free), regression.py 20,479 (1 free). `dev/` is not in the shipped package (`SHIPPED` in `dev/package.py` is skills, listing.json, README.md, LICENSE), so a new toy file does not count toward MAX_FILES.

Decisions:
1. The fix lives only in the template text of the `affected` job and the tree shard in lanes_cli.py: `ran.txt` takes only rows whose status is RAN (`awk '$3 == "RAN"'`), so a LEFT or CUT row is rerun by the existing loop with the existing `--timeout 200`; a rerun that times out or fails fails that loop's `bad` flag and so the job. This shortens the line by about 13 bytes.
2. The echo that says "LEFT (row limit or budget), not failed" is reworded to say the rows are rerun below, so the message no longer says they are not failed.
3. The tree shard gets the same `t.tsv`: the run block exports `LOOP_ROW_TIMES=${{ runner.temp }}/t.tsv` once at its top and the two inline assignments are removed, so a tree row that is CUT or LEFT is seen and rerun like any other. The upload step already uploads that path.
4. The `affected` job's `timeout-minutes` rises from 8 to 20 (the shard job's own limit is 20), because it now reruns the rows that used to be dropped; a rerun that runs past the job limit is a red run, never a green one.
5. regression.py is not edited (1 byte free). If the byte count of lanes_cli.py after the edits is not at most 20,480, the build stops and reports the numbers before adding anything; a new file is not added, and any new file waits for operation-mac and the owner. The edits are expected to shorten the file by 20 to 30 bytes.
6. The workflow file is regenerated with `regression.py workflow` (never hand-edited), and the generator's check passes: the new toy compares the generator's text with the file on disk, and `package.py --static` and the existing workflow toys stay green.

Steps:
1. Measure lanes_cli.py and regression.py first; apply the generator edits in a scratch copy and measure again.
2. Toy first: `dev/toy/test-affected-rerun.py`. It takes the `affected` job's run block and the tree shard line from the generator's template text (`lanes_cli.NARROW`), runs the block with bash in a temp directory that holds `s/shard-0/t.tsv` and `s/shard-1/t.tsv` and a stub `skills/workflow-regression/scripts/regression.py` that records its arguments and fails for one chosen row. Cases: a row LEFT on a shard whose rerun fails ends not green (the control, line 2); the same row CUT ends not green; a LEFT row whose rerun passes is rerun once and ends green; rows with status RAN are not rerun; a row SEL on one shard and RAN on another is not rerun; the generated tree line sets `LOOP_ROW_TIMES` before its run; the generated text equals `regression-pr.yml` on disk. Run it first against the unedited tree: the control must fail there (it ends green on the parent commit), recorded as the seen-red date.
3. Edit the template; regenerate the workflow; run the toy green; run the existing workflow and package toys (`dev/toy/test-package-static.py`, `dev/toy/test-regression.sh`) unchanged and green.
4. One regression row `affected-reruns-cut-rows` (category defect, link the issue) running the toy and grepping its PASS lines, with the seen-red date from step 2; `regression.py` asserts the row. Docs: the generated pages that say a LEFT row is "not failed" are updated through the docs tool (`docs.py audit`, `docs.py check`).
5. Size and checks: `dev/toy/size-check.py` on lanes_cli.py and regression.py (none over 20,480; lanes_cli.py goes down); the package, docs and private-name checks green; no row red; no test loosened.
6. PR notes in the goal file before any lane: the measured bytes, the red proof, and the LEFT and CUT rows from this PR's own CI run.

Test plan: the toy cases in step 2, the existing workflow and package toys, the size check, and the PR's own first CI run. Failure modes: a shard with many cut rows makes `affected` run long (the 20-minute job limit turns that into a red run, never green); a row that cannot finish in 200 seconds fails the PR every time (the intended result: the row is slow and must be fixed or moved off the PR path); a missing artifact (a crashed shard) is still caught by the final `needs.shard.result` check; a documents-only diff exits early with no `t.tsv` and no rerun, as today. Not in scope: a new gate that reads the check runs (the held lane-gate goal), raising the 120-second shard budget, splitting shards by recorded row times, a per-row outcome artifact, any file under skills/. Known limits: the PR's own run is the end-to-end proof; the toy runs the real shell block with a stub runner, so it proves the rerun and failure logic, not GitHub's runner.
