# Plan (revision 3, the last): `affected` reruns a selected row that a shard left or cut, and fails the run unless the rerun passes (a patch for #5757, REG-4)

This revision replaces revisions 1 and 2 (commits e5aba57c0 and 18b745224) on operation-mac's order, taking the red-team gate's own alternative: the shard budgets, the tree line, `runs.py` and the TD512 control are all left as they are; only the `affected` job changes. Done line 1 is met word for word: `affected` reruns the row.

## Implementation plan

Goal: when a selected row is written LEFT or CUT by a shard, `affected` reruns it; the PR's checks are green only if that rerun passes, and a row that does not pass its rerun fails the run, named, with its time and what to do. A row that passes only on its rerun is never plain green: it is printed and counted as a warning.

What exists today (read in this worktree, parent 0eee7e484):
- `lanes_cli.py` writes `regression-pr.yml` from its `NARROW` template. Each shard runs `regression.py run ... --reuse --tier goal --budget $B --timeout 200` (B is 120, or -1 when the diff touches the row table or known list, TD512) and writes `t.tsv` rows `id<TAB>seconds<TAB>status`: RAN (this shard ran it), SEL (another shard's), CUT (the budget ran out first) or LEFT (it passed the 200 s row limit; regression.py:320 takes such a row out of the failures when more than one shard runs). Every non-tree shard writes every selected row as RAN, CUT, LEFT or SEL. The row-times cache restores the previous `all.tsv` into `t.tsv`; it holds RAN, LEFT and CUT but never SEL, and regression.py:252 keeps a restored CUT for a row that is no longer selected.
- The `affected` job treats RAN, LEFT and CUT rows as accounted for, echoes "LEFT (row limit or budget), not failed" and reruns only a row no shard wrote at all. So a LEFT or CUT row is never rerun and every check can be green with the row never finished (#5757).
- Bytes [measured: wc -c]: lanes_cli.py 20,477, regression.py 20,479. Moving the affected block inline into the template as the fix would take lanes_cli.py to 20,684 [replayed in a scratch copy], far over the 100-byte headroom operation-mac asked for (20,380 at most), so the bytes force a file; see change 1.

Changes:
1. New file `skills/workflow-regression/scripts/affected.sh` (the bytes force it: measured first; the package then has 98 of the 100 files MAX_FILES allows, 97 today). The `affected` job's inline shell moves into it and `lanes_cli.py` calls `bash skills/workflow-regression/scripts/affected.sh`; lanes_cli.py then measures 19,952 bytes [replayed], 528 free, and `timeout-minutes` of the `affected` job rises from 8 to 20 (the reruns can be long, a job past the limit is red, never green; +1 byte). The script keeps today's two cache lines and the "run twice:" echo (the existing toy and a row read it), and:
   - `ran.txt` holds only rows written RAN; the ids to consider are those written SEL or RAN by some shard (a stale CUT for a row no longer selected is never SEL or RAN, so it is not rerun; neither is anything in a restored documents-only file, which never holds SEL), minus `ran.txt`: a row cut or left on its shard (it is SEL on every other shard) and a row no shard wrote.
   - each such id is rerun once with `regression.py run <id> --timeout 200`, its output shown. The prior status and seconds come from `all.tsv` (`LEFT 200s`, `CUT 0s`, or none for a row no shard ran).
   - the rerun counts as passed only if its output has a `PASS <id>` line: a failure, a timeout, a SKIPPED row and a known-failure row that times out (KNOWN, exit zero) are all not passed. A pass prints `passed on rerun after LEFT 200s: <id>` (or `after no shard ran it`), as a `::warning::` annotation (shown on the run and its check, counted by GitHub) and a line in the job summary, never plain green.
   - a row not passed prints `FAIL <id> after <LEFT|CUT> <seconds>s, still unfinished on rerun: fix or move the row`, sets the job red, and the loop still reruns the others so every failing row is named. No issue is filed by the job.

Failure modes: a PR with many CUT rows now runs them serially in `affected` (up to 200 s each, 20-minute job limit; a job past it is red, never green); a row that cannot finish in 200 seconds on its rerun fails every PR that reaches it, with its name and the fix-or-move text (filing issues for it is out of scope); a crashed shard is still caught by the final `needs.shard.result` check; no artifacts at all stays green (#5759).

Not in scope: changing any budget, the tree line, runs.py, TD512, regenerating adopters' workflows (v120-set1's scope, SET-1), automatic issue filing, a per-row outcome record, a merge gate, and #5759's fix.
