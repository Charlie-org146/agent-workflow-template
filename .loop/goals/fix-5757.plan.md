# Plan (revision 2): PR shards never cut a selected row, and `affected` fails any row left unfinished (a patch for #5757, REG-4)

This revision replaces the first plan (commit e5aba57c0) on operation-mac's order after its red-team gate. It takes the cheaper path that gate named. There is no rerun, no stale-status handling and no 20-minute job; the first plan's eng and ceo blocks no longer apply.

## Implementation plan

Goal: a selected row that a PR shard does not finish makes the pull request's checks red, and no PR shard has a time budget that can cut a row. The four frozen done lines are met as follows (line 1 differs in one word, see "For operation-mac").

What exists today (read in this worktree, parent 0eee7e484):
- The workflow `.github/workflows/regression-pr.yml` is written by `lanes_cli.py` from its `NARROW` template (`regression.py workflow`). Each shard runs `regression.py run ... --reuse --tier goal` with `--budget $B --timeout 200`; `B` is 120 unless the diff touches the row table or known list (then -1, TD512). A row that passes the per-row limit (rc 124) when more than one shard runs is removed from the failures and written LEFT in the shard's `t.tsv`; a row the budget cuts is CUT. Every non-tree shard writes every selected row as RAN, CUT, LEFT or SEL.
- The `affected` job echoes "LEFT (row limit or budget), not failed", puts RAN, LEFT and CUT rows into `ran.txt`, and reruns only rows no shard ran. So a LEFT or CUT row is counted as accounted for and every check can be green with the row never finished (#5757).
- A row in the known-failure table that times out is classified KNOWN (runs.py:213), not FAIL, so it exits zero and is never LEFT.
- The tree shard is `exec $R --tree --timeout 200` with the default budget and writes no times file.
- Bytes [measured: wc -c]: lanes_cli.py 20,477, regression.py 20,479, runs.py 18,852.

Changes (all measured by replay in a scratch copy before any edit; the build re-measures after each edit):
1. lanes_cli.py, template only. (a) The `B=120; git diff ... && B=-1` line is deleted and the shard's `--budget $B` becomes `--budget -1`: no PR shard has a time cut, so no selected row is CUT. (b) The tree line becomes `exec $R --tree --budget -1 --timeout 200`. (c) The affected job's "LEFT ... not failed" echo line is replaced by these two lines:
   `U=$(awk '$3=="SEL"{s[$1]}$3~/LEFT|CUT/{c[$1]}END{for(k in c)if(k in s)print k}' s/*/t.tsv | sort)` and `test -z "$U" || { echo unfinished $U; exit 1; }`
   A row counts as unfinished only if some shard wrote it LEFT or CUT and some shard wrote it SEL (a row selected now). A stale CUT kept by the row-times cache for a row no longer selected has no SEL and is ignored; so is a restored file from a documents-only run (the cache never holds SEL). The trailing `| sort` keeps the step's status zero when `s/*/t.tsv` does not exist (no artifacts at all): the Actions shell is `bash -e` without pipefail, and a bare `U=$(awk ... missing)` would abort the step. `ran.txt` and the rest of the job are unchanged, so the job reruns nothing for a LEFT or CUT row: it fails first. (Dropping LEFT and CUT from `ran.txt` would make stale CUT rows rerun; the explicit check gives the same outcome without that hazard.)
   Replay of (a) to (c): lanes_cli.py 20,477 to 20,370 bytes, 110 free under 20,480 (the 100 asked for).
2. regression.py: the message at line 323 loses ", not failed": `LEFT %d over the %d s row limit: %s`. Nothing else changes. 20,479 to 20,467 bytes, 13 free (not lower than before, never a new file).
3. runs.py: one change at line 213: a KNOWN row that exits 124 is FAIL: `"KNOWN" if key in expected and code != 124 else "FAIL"` (+14 bytes, about 18,866, under 19,000). So a timed-out known row is LEFT on a shard (n over 1) and fails `affected`, and on the tree or a single run is a plain FAIL: an unfinished row fails whatever its table status. A known row that finishes red stays KNOWN (exit 0, as today). Slow rows are not routed into the known table. No other code or file under skills/ changes; no new file under skills/.
4. The workflow is regenerated with `regression.py workflow` (never hand-edited).
5. Toy `dev/toy/test-affected-unfinished.py` (dev/ is not shipped). It reads the generator text from the path in `LOOP_TOY_GEN` (default the tree's lanes_cli.py) and runs `LOOP_TOY_ONLY=control` for the red proof alone. It extracts the affected run block from `NARROW` by text and fails hard if the extraction is empty or holds a `${{` expression; the block runs under `bash -e` with a stub `regression.py` that records any call. Cases:
   - control (real producer): the real `regression.py` runs as two shards (`LOOP_PR_SHARD=0/2` and `1/2`, `--budget -1`, `--timeout 2`) on a fixture repo with one row that sleeps past 2 seconds; the toy first asserts that the real `t.tsv` files hold that row as LEFT on one shard and SEL on the other (a missing precondition fails the case), then runs the block on them: it must exit non-zero, name the row, and call the stub runner zero times. On the parent generator the block exits zero, so this is red there.
   - the same with a CUT row.
   - a KNOWN row (in a fixture known table) that times out: LEFT on a shard, block fails; as a single run (no shard variable) it exits 1; a KNOWN row that finishes red exits 0.
   - ignored, exit 0: a stale CUT for a row no shard selects; a restored documents-only file (RAN, LEFT and CUT, no SEL); all rows RAN; no `t.tsv` at all under `bash -e`.
   - the template: the shard line has `--budget -1` and no `B=`; the tree line has `--budget -1`; the matrix is 0 to 7 plus tree with `/8` and the artifact glob covering them; the generator's output equals `.github/workflows/regression-pr.yml` on disk.

Test plan: the new toy; `test-shard-balance.py`, `test-package-static.py`, `test-regression.sh` and the size check green; `regression.py` rows: none red; PR's own CI run.

Failure modes: a row that cannot finish in 200 seconds now fails the PR (intended; the row is slow and must be fixed or moved by a person, never routed into the known table); an unbudgeted shard can run until its 20-minute job limit and then the shard job is red, never green; a crashed shard is still caught by the final `needs.shard.result` check; no artifacts at all (a download that fails) still ends green if the shard check is green, as today (named as a limit).

Not in scope: any rerun of cut rows, balancing by recorded time, regenerating adopters' workflows (that belongs to the v120-set1 goal, SET-1), a per-row outcome record, edits to `skills/loop-files.md` (its lines 746 and 933 describe the in-loop budgeted run, which is unchanged), and any gate that waits on a measurement.
