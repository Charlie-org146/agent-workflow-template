# Plan: v110-fast-clock, a time limit per step and change size, lead time and missed steps on the board, no release while main is known broken

## Implementation plan

Goal: every step has a time limit set in settings; lead time is measured per step and per goal and shown on the board and the check-in; a step over its limit shows as missed with its cause and the next starts; every ETA records who, when and on what basis from measured history; no release goes out while main is known broken, and merges go on. Source: the frozen final page, DEL-17.1 to DEL-17.5 (owner records o739, o744); new files under skills/ allowed within MAX_FILES by o745. Frozen done lines: (1) every DEL-17 test case on the page is a real test linked to its requirement, passes, and fails on a fixture that breaks only that rule; (2) the behaviours above; (3) every script under 20,480 bytes, none newly over 19,000, new files within MAX_FILES, no test loosened, no existing row red, committed text never names the service repo.

### Design (A to E; what is new is only what the code above lacks)
A. Limits (17.1). Settings: ONE new row `step_report_limits` (renamed from step_limits after both DX voices found step_limit in seconds and step_limits in minutes too easy to confuse; the key now says what it does: it reports), text "build=45,tests=20" in minutes. Step names are matched ignoring case and treating space, hyphen and underscore alike ("quick checks", "quick-checks", "quick_checks"), and shown in their canonical spelling; the three check names are health, docs check and board. `name=off` (or `name=0`) turns that one limit off by choice: clock.unset reports only limits that are missing, not ones switched off. A partial value overrides only the named entries: every other step keeps its template default. The 15-minute floor of the older budgets does NOT apply (1 to 1440). The units, the clock (wall time) and what stops a step are stated once in a "reports versus stops" table in the Delivery how-to page, which the settings reference links to (settings.py, 452 bytes of room), plus `python3 skills/workflow-setup/scripts/settings.py reference --write` to regenerate the settings reference page (listed in Files; the docs check fails if it is stale). Grammar, parsed by `clock.parse(text)` in clock.py: comma-separated name=minutes; an entry is `[doc:|code:]name=minutes`; a name must be in steps.STEPS, `PR checks`, `push to main`, or one of three check names (health, docs check, board); minutes an integer 1 to 1440; a bad name, a non-integer, a duplicate or an out-of-range value is refused with the STEP_LIMITS_BAD text in the error table below by settings.py fill-repo (see "settings wiring" below). A hand-edited .loop/config.json is read through the same parse on every display: a bad value never crashes the board or check-in; it prints the one display-fallback line from the error table below and the template defaults apply. The setting text, the settings reference row and every refusal call step_report_limits REPORTING limits (display-only, they do not stop a step; the older budgets do), so a repo does not expect enforcement; enforcement through the existing budget mechanism is recorded as a follow-up row (alternative weighed and deferred: it would change what an existing budget stops). Limits are PER CHANGE SIZE (owner words o748, top's reading TD807; nothing hard-coded in a script): a value may carry a size prefix, `doc:tests=5,code:tests=30`, and an entry with no prefix applies to both sizes; precedence is the size-specific entry, then the unprefixed entry, then the template default. The sizes are two, doc and code. The names are the eight steps, `PR checks` (wall minutes from the push to the last required check going green, Delivery.md:31's "push and PR CI", TD829) and the composite `push to main` (wall minutes from the start of tests to the end of merge, so it spans push, PR checks and the merge queue; its limit is set here and its time is measured once fast-ci-2 records those events), and the checks health, docs check and board. The template default table lives in one data table in clock.py that a repo overrides in settings, and ships exactly the owner's named values (o755, which corrects o751; both quoted under Sources): quick checks 1 (DEL-25.2); tests 5; PR checks 5, or 30 for a code change; merge 5; push to main 3, or 35 for a code change (doc-only keeps the values of Delivery.md:31 and o748). a step or check with no named value (freeze, plan, build, after the merge, release, health, docs check, board) starts at its measured usual and shows that it did: clock.limit returns (minutes, source) with source named, usual or setting, and every display of a limit taken from the measured usual says so, e.g. "limit 40m (measured usual on <machine>)". The marker names the machine (the LOOP_MACHINE_NAME setting, else mac or pc by platform), because the usual comes from that machine's own run history, so the same goal can show different limits on two machines and the difference is visible, as the owner's o751 text stays as written. The measured usual of a step is the median of its wall minutes over the last 20 finished goals from steps.entries, computed once per render and reused (the board_model backtest is not rerun); with fewer than 3 finished goals it is unknown and the step shows "no limit yet (no measured usual)", listed by clock.unset as "awaiting history" (never silently absent). `PR checks` has its own source: clock.pr_checks(run) reads the pull request's required checks through read-only gh (`gh pr checks <pr> --required --json startedAt,completedAt,state`, the earliest start to the latest completion), with one shared 10-second allowance per render; when gh fails or the run has no pull request the card says "PR checks unavailable", never a guessed number. "Missed" for a step with no named value means slower than that step's own usual; a chronically slow step is not flagged missed (that is o755's wording) and shows in DEL-17.2's per-step lead time instead, and a fresh repo shows "awaiting history" until 3 goals have finished (TD830). `clock.unset` reports a step with no limit and no usual yet as "awaiting history", so the metric "steps with no limit, target 0" is not met by hiding it. Change size is decided from the goal's recorded touches (the run record's own "touches" list, so the same record gives the same answer on every machine, before and after a branch is deleted, with no git or gh call): the goal is doc-only when every touch outside .loop/ matches release.auto_need's own pattern (release.py:136-140, `^(docs|tests?|dev/toy)/|\.md$|(^|/)test[-_.]|[-_.]test\.`, applied to the touch entry with a trailing slash), else code; no touches means code; a drift row compares the pattern with release.py's source text. This reads the goal's declared directories, coarser than the diff release.auto_need reads, and the PR notes say so (the git-diff reading was dropped after the red team found it renders differently by machine and after merge). clock.py holds the template defaults, so a repo changes one entry in settings with no code change. `clock.limit(cfg, step)` returns minutes. The three check limits are settable, validated and returned by clock.limit; the time of a check is measured by its caller, which passes the seconds it took to `clock.check_missed(name, seconds, cfg)` (a pure function the -checks goal calls); this goal does not wrap health, the docs check or the board itself (byte room), and a toy proves the function. Older keys: step_budget_minutes, test_budget_minutes and prep_budget_minutes keep doing exactly what they do now (they stop a running lane or step, with their 15-minute floor); step_report_limits governs the measuring and the "missed" display only, so the two never conflict. `clock.unset(cfg)` returns the steps and checks with no limit (the metric, target 0): with the template defaults it is empty, and a test fixture with one default removed proves it lists it (a limit switched off by name=off is not listed).
B. Lead time (17.2). Lead time is wall-clock time (held and idle time included, as DORA lead time is), not the active minutes the older budgets use. `clock.lead(run)` reads steps.entries(run) (minutes per step; a step done twice sums its attempts; a record with no end lines counts that step to its next start, else to now while running) and the goal's wall time from board_log.wall_minutes, and returns the per-step minutes and the total. Shown as a CARD per goal (CHK-1, quoted under Sources: every item is a card, no tables, no plain lists, every claim carries what it was read from and its clock time, plain text that reads on a phone). A card is kept compact: a header line that carries the time in all, `[lead] <slug> 3h10m in all` (the word "total" is one the older live-board check bans), one indented line of the steps (`  freeze 12m, plan 41m, build 1h05m`, wrapped at step boundaries only when it passes 60 columns, steps with no data left out), one `  missed (was 41m, limit 30m): <cause>` line per missed step, one `  PR checks 28m` or `  PR checks unavailable` line for a goal with a pull request, and the last line `  read from <slug>.json log, 18:59`, naming the record and the render's clock time (clock.begin's time; check-in: its `at`); every line at most 60 columns. A missed line is a line of the card that holds it, never a separate list item. Two hooks, because the two surfaces build their lines differently: (1) the live board: live_board.flow_lines(run) (live_board.py:108, receives the run record) appends the line; (2) the check-in: board_lines.bars (board_lines.py:107, which gets the goal's item) appends `clock.lead_for(slug, at)`, which reads the run record of the repository the check-in runs in; checkin.py is not edited. A goal of another repository in a multi-repository check-in gets no lead card: that read is deferred to the queue and CI goals (TD1154). board_lines.bars is not hooked for the board; the live board does not call it. D9 (operation, 2026-11-21): the page's test "after a toy goal merges, the board shows its minutes for each step" needs merged goals on the board, which live_board.render leaves out by design; so live_board.render gets the CHK-1 section "Shipped", which CHK-1 lists last, appended after Finish (hook `+ ["", "Shipped"] + clock.merged_lines(runs, gone)` on the return line; each shipped goal is one card in the format above with the header `[shipped] <slug> <time> in all`, and with nothing merged there is no Shipped section, never a "(none)" list; it uses the `gone` set it already computes; the merge time and an empty card were cut under TD1035), which also reaches the HTML board because board_page.py runs live_board.py --html; board_page.py itself stays untouched. The byte cost in live_board.py fits under 19,000 on main as it is (main already takes parse_at from board_tasks); a row proves live_board.parse_at and graph.parse_at give the same answers on the same inputs.
C. Missed (17.3). Operation's ruling (2026-11-21, DEL-19.3 owned by -steps): clock owns the DECISION and writes nothing; -steps owns the WRITE. `clock.missed(entry, cfg)` returns the line or None, where entry is {step, attempt, minutes, causes (the entries() cause list), waiting (the record's waiting reason or None), budget_hits (the record's hits for that step)}, so the decision needs nothing else from the record and -steps supplies all of it; a logged miss is identified by (step, attempt) so a retry never logs twice; -steps' step-end writer (in role.py, its revision) calls it and logs the returned line, so the line is in the run log for every goal finished after both land. The format is exactly "missed (was <N>m, limit <L>m): <cause>", pinned by ONE toy that both goals' rows use (the contract row, which belongs to the v1.2.0 steps goal). The display (`clock.lead_line`) reads the logged line where one exists and derives the same text with clock.missed where none does (older goals, a step still running); a step over its limit therefore shows once. The cause is taken in this order: the step's cause list from steps.entries, the record's `waiting` reason, `budget_hits` (lanekit.hit), else "no cause recorded", always through the one-line strip described under Errors. A raised limit does not erase a logged miss (the limit in force at the time is in the logged line); a derived miss prints the identical pinned text behind the display prefix "(derived) ", so the persisted format never carries a display annotation and a logged and a derived line are byte-identical apart from that prefix. Reading a logged line back parses only `^missed \(was (\d+)m, limit (\d+)m\): ` and treats the cause as opaque text. Retries: a step done twice compares the SUM of its attempts to its one limit (stated in the "reports versus stops" table), and a retry that stays under the limit per attempt but misses in total is a test row. Waiting counts: lead time and misses are wall-clock, so a step that waited overnight for review shows as missed with the cause "waiting: <reason>"; that is the reported fact, not noise, and the table says so (D10). A step with no start line is skipped; a running step is compared only while its goal is running. "The next step starts" is satisfied by design: nothing stops or holds a step for a step_report_limits miss (the older budgets still stop a lane or step). steps.py does not import clock (D3); clock imports steps lazily, by path from workflow-delivery's scripts folder.
D. ETAs from history (17.4). The ledger already records who (board_status.py:300 "who"), when ("said") and basis. The change is the basis text only: auto.eta_new's basis ("estimate %dm plus a %d%% margin%s", auto.py:248) gets a suffix naming its history, using the finished-goal count from board_model's backtest (the n that accuracy_text prints, board_model.py:255) and its typical error: ", scored on N past goals, typically off by a factor of K (repo-wide)", or ", too few finished goals (N of 10)" under board_model's MIN_BACKTEST (10); with no estimate it keeps today's "no estimate yet, so the time budget". The goal ETA entries inherit the suffix through run["eta"]["basis"] (layers.py:91); the board and status ETA entries (board_status.py:318, layers.py:92) keep their derivation basis ("latest finish among N goals", "STATUS to top") and link to the goal ETAs through the ledger's `goals` field, which carry the history, so no extra hook is paid (D11). Consumers of the basis text were checked: dev/toy/test-eta-header-margin.py:125-126 and test-eta-preflight.py:113 match substrings or build their own, and fit.py:313 only prints it, so a suffix breaks none of them. One count and one source; no per-step median is computed (that stays deferred). A passed ETA already shows as missed (auto.py:366); a toy asserts it.
E. Main red (17.5). The releases come from three local doors plus the CI door: release.py cmd_cut (manual), review.py promote (review.py:282, which pushes main and a tag and calls gh release create at :301), and, after a merge, autorelease.py finish (autorelease.py:359, reached from merge.py:302 onward, which records a failure as release_error and keeps the goal mergeable); the CI door is release.yml. `gate.main_red(top)` (new skills/workflow-release/scripts/gate.py, beside release.py, so the release side needs no cross-skill import; release.py already puts its own folder on sys.path, release.py:18) runs `gh issue list --repo <owner/repo of the github.com origin remote> --state open --label main-red --limit 200 --json number,title` (a result of exactly 200 is treated as truncated and unreadable; the repository is the github.com repository the origin names: the one the origin's effective, push and configured addresses name, because the project's main-red issues live on the repository the origin names, whatever mirror or alias address a clone uses; if none names a github.com repository, or they name different ones, the hold fails closed with MAIN_RED_UNREADABLE (TD1175); --repo is explicit so a fork remote cannot pick the wrong repository); milestone.py is not imported, takes the lowest number as the named issue, collapses its title to one line of at most 80 characters, and returns the tuple given under Signatures. Every local door (cmd_cut, review.py promote and autorelease.finish) calls it before any release change (autorelease.finish: before stage_notes, D5): cmd_cut and promote refuse and autorelease.finish records through autorelease.fail as release_error, each with its own door-specific MAIN_RED text from the error table below (the merge has already happened at the autorelease door, so its recovery is rerunning merge.py, not cutting), and a later merge.py SLUG run for that goal, once the issue is resolved, releases it (merge.py skips the merge for a pull request that is already merged and the goal's staged notes and verify steps are kept). autorelease.fail already records release_error and exits (the goal's status stays done because the merge is done, and it stays mergeable: autorelease.py mergeable), exactly as for any release failure today (the wiki publish after it is skipped the same way); batch cuts (release.cmd_ask calling cmd_cut) catch the exit as they do now. The definition of "main red" is release.yml's (operation, 2026-11-21): an open issue labelled main-red; one toy row asserts that the cut door, the autorelease door and release.yml (the workflow's hold step run against a gh stub, as dev/toy/test-release-hold.py does) all refuse on the same fixture. release.yml is NOT edited: it is hand-written, already holds (release.yml:26-34) and is left alone, and the PR notes say the CI door was already gated. The rule is release.yml's hold rule, read by gate.main_red(top) itself, computed exactly as release.yml does it (read at release time by the shared gate.py function, so a delayed retry, a manual cut and promote all use the same definition as CI; tests cover each door; a closing reference counts only when it names this repository's issue, so another repository's issue with the same number clears nothing). If what the hold reads cannot be read, the door fails closed with MAIN_RED_UNREADABLE. Every door exits non-zero (cut and promote: SystemExit with the message on stderr; autorelease: autorelease.fail records release_error, merge.py has already printed MERGED and then exits non-zero with the refusal, so the output says the merge is done and the release is held). An unreadable list fails closed with the MAIN_RED_UNREADABLE text from the error table below (a release needs gh anyway). merge.py's merge step is untouched. gate.py also receives the moved verify_steps. The label name comes from the page text.

### Errors, agent-ready (what, fix, recovery, code, context, redaction, channel)
Text printed from outside the loop goes through one tiny strip in each place that prints it (`"".join(ch for ch in text if ch.isprintable())`, cut to 80 characters for an issue title and to 120 for a cause); gate.py has its own one-line strip, so the release side needs no cross-skill import. gh's own error text is NEVER printed or stored: a failed gh call is named by its class (auth, permission, timeout, bad reply) and its exit code only, which leaves no token shape to redact (TD830, in place of the denylist, its copy in gate.py, its drift row and the HTML fixture; the HTML board escapes whole fragments already, live_board.fragment, and a row proves one title with markup stays inert). Titles and causes are printed quoted (title="...") so a reader treats them as data. Channel: refusals go to stderr with a non-zero exit; display lines go to stdout and the exit stays 0.
- STEP_LIMITS_BAD (settings.py fill-repo, exit non-zero, stderr): "REFUSED (STEP_LIMITS_BAD): step_report_limits entry 'x=y' is not <name>=<minutes>. Names: freeze, plan, build, quick checks, tests, merge, after the merge, release, PR checks, push to main, health, docs check, board; optional prefix doc: or code:; minutes 1 to 1440. Fix: edit .loop/config.json and run settings.py fill-repo again. Nothing was changed. See docs/wiki/How-to-use-Delivery.md#step-report-limits" Side effects none; retry after the edit.
- Display fallback (board or check-in, stdout, exit 0): "step_report_limits unreadable (STEP_LIMITS_BAD): 'x=y'; template defaults apply. Fix: edit .loop/config.json, then run settings.py fill-repo." One line, once per render.
- MAIN_RED at cut (stderr, non-zero): "REFUSED (MAIN_RED): issue N is open: <title>. Nothing was released or changed. Fix: the owner, or the goal that filed issue N, resolves it once main is repaired and green; an automated session never does (hold=main-red:N). Then run release.py cut SLUG again. See docs/wiki/How-to-use-Release.md#main-red"
- MAIN_RED at autorelease (recorded as release_error, status stays done, goal stays mergeable; autorelease.fail prints it after "REFUSED: "): "(MAIN_RED) hold=main-red:N the merge is done; the release is held by open issue N \"<title>\". Fix: the owner or the goal that filed it resolves it once main is green; an automated session never does. Then run merge.py SLUG again; it does not merge twice." (the marker leads the text so a long goal name cannot push it out of the length the record keeps) (at most 400 characters, the length the record keeps)
- MAIN_RED_UNREADABLE: "REFUSED (MAIN_RED_UNREADABLE) cannot read main-red issues (<auth|permission|timeout|bad reply>, gh exit code <n>). Nothing was released or changed. Fix: <the fix for that class: gh auth login or a GH_TOKEN; check the network; point the origin remote at a github.com repository; resolve fixed main-red issues so fewer than 200 are open; rerun with LOOP_DEBUG=1>, then run the same command again (promote: review.py promote; autorelease: the text starts (MAIN_RED_UNREADABLE) the merge is done and says to run merge.py SLUG again)." The classes are auth, permission, timeout, bad reply, no GitHub origin, 200 or more open issues and unexpected <class>. Every gh call has a 30-second limit and the whole gate (issue list, closing references, retries) shares ONE monotonic 70-second deadline, then this refusal; no call can hang. The two limits are module constants of gate.py (30 s per call, 70 s for the whole gate); the hang row patches the constants for its run and one row asserts their defaults; there is no cache, and a batch (cmd_ask) stops at the first unreadable result.
- Unexpected failure in clock.py (a display function): caught inside clock.py by one wrapper around begin, lead_line, lead_for and merged_lines, one stdout line "clock unavailable (CLOCK_ERROR: <class>); LOOP_DEBUG=1 prints the trace"; the board and check-in still render; the traceback goes to stderr only when LOOP_DEBUG is set.

### Hooks and byte rule
