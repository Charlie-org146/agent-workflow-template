### 1. New module `skills/workflow-delivery/scripts/sizing.py` (new file, under 15,000 bytes; every existing delivery script is within a few hundred bytes of the cap, so each hook is one call)
- `size_of(plan_text, changed, config, safety)` is a pure function. Inputs: the plan's `Files:` list (each entry one file path; a directory, a glob or a missing list counts as large with that reason), its `Lines:` estimate (a missing estimate counts as large), its `Gates:` line (a gate is a named merge or build gate; none listed means none), and `safety`, the safety classes judged on the Files list, the Gates line, the plan's stated classes line and every changed path against the repo's risky-path list (not on all prose, so a plan that says it removes a typo stays small), using the monitoring skill's class table, loaded the way the delivery code already loads monitoring modules (importing it sets process environment values) and never copied. It returns `(size, reason)`. Small: 3 files or fewer, 150 lines or fewer, no gate and no safety class. Medium: 10 files or fewer and no safety class. Large: everything else, and always large when `safety` is non-empty. The reason names each number and the line it crossed.
- `read_table(base)` reads `.loop/config.json` from `origin/<base>`, then the base branch, the way the review-depth setting is read, so a worker's own branch cannot lighten the table it is judged by. A missing table takes the shipped defaults; a row that drops or lightens a fixed check (build gate, full test run before merge, two leak readers before any push, every safety class) is refused with a message naming the row and the check. It is called by `size`, by `resize` and by the record check, and each refuses on a bad row.
- Refusal contract: every refusal sizing adds uses the existing form `REFUSED (no try used): <rule and cause naming the row, check or form>. Fix: <next command> (<code>)` with a stable code under the `sizing` rule id and a non-zero exit; the Fix always names a runnable command. A bad table row: edit the row on the base branch with the owner's words, then run `sizing.py size SLUG`. A missing `sized` field: `python3 skills/workflow-delivery/scripts/sizing.py size SLUG`. An unmet added check: run `sizing.py rule SLUG`, run the added check, record its CHECK line. A request for a smaller size: sizes only go up, so raise with `sizeline.py set SLUG SIZE --owner-record ID`. A missing owner record id: record the owner's words first through the operation's owner-words record, then rerun with `--owner-record ID`.
- Opt-in: sizing is active only when the base config (read the way the review-depth setting is read) carries the key `checks_by_size`. Without it, `rule`, `check`, `resize` and `at_pr` do nothing, and `read_table` returns the defaults only to the `size` command; existing fixtures and goals behave exactly as today. A new record-check rule id `sizing` exempts a goal whose plan step started before the rule existed. Toy cases: a fixture repo with no key behaves as today; an old goal is not refused.
- `size(slug)`: reads the plan file, writes the stored `sized` (`size`, `reason`, `checks` with each check's named form and pass count, the plan sha, `added`, `owner`). It runs in the plan step after the plan file is written and before any review phase of that step, so the plan's own reviews run at the size's forms. The plan record re-checks the plan's sha; a changed sha re-runs it. On every re-run the stored checks are a ratchet: the union of the old and new checks, each at the stronger form, so a large plan edited down to small keeps the large checks (negative controls: a plan edit, a table change). Every write of `sized` stores `grow(old, new)` for the size and the checks ratchet together. A test edits a large plan down and re-records, and the stored size must stay large. `size`, `override` and `resize` take the goal's state-file lock and compute `grow` and the checks ratchet against the freshly read stored state inside the lock, so two writers cannot lose the ratchet; the stored field `sized` collides with no existing key (the DEL-5 field is `size`).
- `resize(state)`: diffs against the base for files and lines and stores `grow(old, new)`; when the size rose, the checks the new size adds go to `added`. A failed diff read or a failed config read never keeps the stored size silently: it refuses (no try used) with the stable code `SIZING_READ_FAILED`, names the failing read, and its Fix is `rerun after git diff against the base works, then run sizing.py size SLUG`. A size never goes down.
- `grow(old, new)` returns the larger of two sizes (small < medium < large).
- `check(state, step, text)` owns two refusals, both no-try: a ship record while any check in `sized.added` has no evidence line, and a reply whose `CHECK:` lines are missing, unknown, of another form or of a different pass count than the stored form. The record check calls it before its budget-stop early return, so a step stopped at its budget still has to carry the lines (negative control: a budget-stopped reply without them is refused). A form's pass count is validated against the shipped defaults, so a form cannot be redefined under the same name. Each form in `forms` lists its required phases or marker strings; `check` also refuses a `CHECK:` line on a reply whose step is `skipped` or `pending`, or that lacks those phases. The existing full-review marker check stays and runs as well.
- `override(state, size, record)` needs a record id from the owner-words record (the one `plan-accept` already takes), stores the id with the old and new size and applies `grow`. A request for a smaller size, or for any size under a safety-class goal, is refused. After an override the same ship gate runs the added checks.
- `skipped(states)` prints one list across goals of every check skipped or run light, with its named form, for the pull request body.
- `rule(step, state)` and `sizing.py rule SLUG [STEP]` print the one block that tells a step which forms to run: each check by name, its form, its pass count, its `covers` text and its `run` command. STEP is taken from the state file when omitted. For a goal with no `sized` field, `rule` prints nothing when sizing is off and prints `NOT SIZED: run sizing.py size SLUG` when sizing is on. `sizing.py size SLUG` and `show` print the same block, headed by `SIZE <size>: <reason>` (the reason names each missing plan field). The plan record refuses (no try used) a goal that has no `sized` field, once sizing is active for the repo. For a sized goal the form's pass count is the depth (a one-round form writes `DEPTH: condensed`, a full form writes `DEPTH: full`), and `rule` prints the DEPTH line to write beside the CHECK lines.

### 2. Table and defaults: `.loop/config.json` key `checks_by_size`
- Rows `small`, `medium`, `large`, each listing its checks with a named form; `forms` defines each form once, with its pass count and a one-line `covers` text (CBS-1.3): for example plan review `one-round`, `full`; red team `one-pass-no-rerun`, `full`; review `normal`, `full`.
- Defaults: small runs the fixed list plus one-round plan review, one-pass red team and normal review; medium runs the fixed list plus full plan review, one-pass red team and normal review; large runs every check in its full form. The defaults are written in `sizing.py`, and the repo config repeats them; a toy case compares the two so they cannot drift. Each form also carries a `run` command (the shipped command for that check), which `cutcheck.py --require-full` uses.
- Strength order of the forms is their pass count (a form with more passes is stronger), and each form's required phases or marker strings are written once, in `forms`.
- Only the owner's words change the table: a table change on a worker branch is not read (it is read from the base).
